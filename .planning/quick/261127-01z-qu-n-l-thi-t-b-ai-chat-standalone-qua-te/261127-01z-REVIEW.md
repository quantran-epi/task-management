# Review: 261127-01z Telegram device control

**Reviewed:** 2026-11-27
**Depth:** deep
**Files Reviewed:** 15
**Status:** issues_found

## Summary

Reviewed full diff `3cee379c..HEAD` plus surrounding source for call chains: Rust Telegram payload → `telegram-inbound` Tauri event → `processTelegramInboundMessage` → enrollment/policy services → standalone chat model enforcement → DB migration. Three blocking defects: the identity field never crosses the Rust/TS boundary so the whole feature falls back to legacy behavior in production; revoked devices can still obtain a policy because the whitelist check keys on chatId; and stale tab models plus the retry path bypass the whitelist. Several smaller enrollment/UI defects follow.

## Critical Issues

### CR-01: Rust emits `from_id`, TS reads `fromUserId` — device identity never reaches worker

**Files:** `src-tauri/src/telegram_gateway.rs:22,206,219` · `src/services/telegram/telegramTypes.ts:66` · `src/services/telegram/telegramHeadlessWorker.ts:709`

**Issue:** `TelegramInboundPayload` serializes `from_id` (snake_case, no serde rename). `TelegramInboundEvent` declares `fromUserId?: string` and the worker reads only `event.fromUserId`. No mapping exists anywhere (grep: `fromUserId` appears only in the type, the identity line, and the admin notification). At runtime `event.fromUserId` is always `undefined`, so `identity = chat_id` on every real Telegram message. Failure scenario: every device registers and is approved by `chatId`, not `from.id`. The feature's stated purpose (identity independent of reply address) never activates; a user who changes chat address re-registers as a new device. Tests pass because `event()` in `tests/telegram/telegramDeviceEnrollment.test.ts:25` injects `fromUserId` directly, bypassing the Tauri boundary. Additionally the Rust field is `i64` while TS expects `string`; even a correct rename would produce a number, failing `.trim()`.

**Fix:** Emit the field name the consumer reads, as a string:
```rust
// telegram_gateway.rs
#[serde(rename = "fromUserId")]
pub from_id: String,
// ...
let from_id = msg.from.as_ref().map(|u| u.id.to_string()).unwrap_or_default();
```
Or, minimal TS-only alternative: add `from_id?: number | string` to `TelegramInboundEvent` and normalize `const identity = String(event.fromUserId ?? event.from_id ?? '').trim() || chat_id;`. Keep the tests honest by asserting the emitted event shape, not only the injected one.

### CR-02: Policy eligibility never checks `status: 'blocked'` — revoked users keep bot access and keep minting policy tokens

**Files:** `src/services/telegram/telegramSettingsService.ts:268-276` · `src/services/telegram/telegramHeadlessWorker.ts:938-970,1034-1094`

**Issue:** `blockPendingUser` sets `status: 'blocked'` and only conditionally sets `deviceStatus: 'revoked'` (when `existing?.telegramUserId` is present). For legacy rows (no `telegramUserId`, e.g. admin-added whitelist) `deviceStatus` stays `approved`. `/policy` is handled before `checkAndConsumeCommandQuota`, so `status: 'blocked'` is never evaluated. Failure scenario: admin blocks a legacy whitelisted device; the user sends `/policy`, `findWhitelistByIdentity(identity)` resolves the row by chatId, `deviceStatus === 'approved'` and `allowedModels.length > 0`, so a fresh valid policy is emitted. The device keeps chat access too only if quota allows — but the policy token remains usable in standalone indefinitely until expiry. Even for new rows with `deviceStatus: 'revoked'`, a blocked user can still run `/policy` (receives a refusal, no token) but consumes no quota and is never routed through `quota.reason === 'blocked'`.

**Fix:** Gate `/policy` on the authorization row, not just `deviceStatus`:
```ts
const device = await findWhitelistByIdentity(identity, db);
if (!device || device.status === 'blocked' || device.status === 'pending' || device.deviceStatus !== 'approved') {
  // reply "Chưa thể phát chính sách", log, return
}
```
And make `blockPendingUser` unconditional on `deviceStatus: 'revoked'` for all whitelist rows:
```ts
return upsertWhitelistUser({ chatId, status: 'blocked', deviceStatus: 'revoked' }, db);
```

### CR-03: Model whitelist bypass via retry and stale per-tab model — enforcement is UI-layer only

**Files:** `src/components/ai/AIChatDrawer.tsx:811-822,909-915,1317-1328,1494,1780,1798,1860` · `src/components/ai/runtime/chatTurnRuntime.ts:623-628`

**Issue:** `resolveActiveModel()` clamps a disallowed model to `allowedModels[0]` only at the moment `handleSendTurn` is called. (a) `handleRetry` (line 2098) calls `turnRuntime.retry()` directly, which replays `lastRequest.model` unchanged (`chatTurnRuntime.ts:625-628`); a turn started before the policy was applied, or with a model later removed from the whitelist, keeps sending with the disallowed model. (b) Tabs created with arbitrary `config.model` (the seeding loop writes `cfg.defaultModel` regardless of policy at lines 870-883) hold a stale model in `tabRuntimes`; `resolveActiveModel` clamps *at call time* but `writeTabModel` never persists the clamped value, so any path that reads `activeTab.config.model` or the runtime mirror directly instead of `resolveActiveModel()` uses the disallowed model. (c) The `blocked` guard exists only in `handleSendTurn`; `handleRetry`, the auto-send effect, and any programmatic `runtime.start()` call bypass it. Enforcement must live at the single choke point where the model is handed to the LLM.

**Fix:** Enforce in the turn request builder used by all send/retry paths (around lines 1494/1780/1798/1860), e.g.
```ts
function enforcePolicyModel(model: string): string {
  if (policyState === 'active' && devicePolicy?.allowedModels.length &&
      !devicePolicy.allowedModels.includes(model)) {
    return devicePolicy.allowedModels[0]!;
  }
  return model;
}
```
Apply it to `lastRequest.model` inside the retry wrapper before calling `turnRuntime.retry()` — or better, pass a resolver into the runtime so every `start()` re-validates. Add the `blocked` guard to `handleRetry` and all programmatic sends. Note: client-side policy is not cryptographically signed (`telegramDevicePolicy.ts:5`); a determined user can edit IndexedDB directly. This is acknowledged in the design; the fix above closes accidental/existing-path bypasses, not deliberate tampering.

## Warnings

### WR-01: Approve with empty model list is silently rejected by `/policy`, device stuck pending-forever

**File:** `src/views/TelegramMonitorView.tsx:1118-1129`

**Issue:** The admin "Duyệt" button passes `allowedModels: modelDrafts[row.chatId] ?? row.allowedModels ?? []`. With no model selected, this writes `deviceStatus: 'approved'` with `allowedModels: []`. `buildPolicyPayload` then throws `Thiếu whitelist model` (device never gets a policy) and `/policy` replies "chưa thể phát chính sách" forever with no indication that models are missing. Message "Đã duyệt thiết bị và phát mã ghép cặp" is misleading.

**Fix:** Disable the Duyệt button when the effective model list is empty, or validate in the handler: `if (!models.length) { message.error('Chọn ít nhất một model trước khi duyệt.'); return; }`. Consider an `approved` status that requires `allowedModels.length > 0` as an invariant in `upsertDeviceEnrollment`.

### WR-02: `upsertDeviceEnrollment` drops `isAdmin`, `sessionResetAt` and any future row fields on approve/revoke

**File:** `src/services/telegram/telegramSettingsService.ts:152-179`

**Issue:** The function constructs a fresh `record` literal listing a fixed subset of fields instead of spreading `current`. Fields present on the existing row but not copied (`isAdmin`, `sessionResetAt`) are deleted. Failure scenario: an admin account is enrolled as a device via the AI Chat Devices tab → `isAdmin` is lost → admin can no longer run bot admin commands (`telegramAdminWizard.ts:68`), and pending mutations/session resets break. This is exactly the class of data loss the sibling `upsertWhitelistUser` avoids.

**Fix:** Build from the current row:
```ts
const record: TelegramWhitelistUser = {
  ...current,
  chatId: targetChatId,
  name: current?.name ?? `User_${targetChatId}`,
  status: approved ? 'active' : current?.status ?? 'active',
  updatedAt: now,
  ...(existing ? { telegramUserId: identity } : {}),
  deviceStatus: input.deviceStatus,
  allowedModels: input.allowedModels ?? current?.allowedModels ?? [],
  remoteSettings: input.remoteSettings ?? current?.remoteSettings,
  ...(approved ? { pairingCode: ..., pairingCodeExpiresAt: ... } : {}),
};
```
For the non-approved branch, deleting stale pairing data may be desirable — do that with explicit `delete` rather than setting `undefined` into an indexed field.

### WR-03: `availableModels` filter can empty the model selector when policy lists a model not in the live catalog

**File:** `src/components/ai/AIChatDrawer.tsx:2369-2373`

**Issue:** `availableModels.filter((m) => devicePolicy.allowedModels.includes(m))` intersects the live catalog with the policy whitelist. If admin whitelists a model string that 9router does not currently return (typo, model retired, cached list stale), the selector renders with zero options while `resolveActiveModel` still returns `allowedModels[0]`. User sees an empty dropdown and cannot pick anything; sends proceed with an unlisted-in-catalog model. Also `handleRefreshModels` (838-856) writes an arbitrary live model to the tab with `writeTabModel` without policy validation.

**Fix:** Show the union with policy models or render an explicit "model không có trong danh sách 9router" tag. In `handleRefreshModels`, choose from `liveModels.filter(m => isModelAllowed(policy, m))` when policy is active, falling back to `allowedModels[0]` with a warning.

### WR-04: Expired policy shows a success badge in the settings card; `parsePolicyPayload` rejects re-pasting it

**File:** `src/components/settings/StandaloneDevicePolicyCard.tsx:36-37,69,101`

**Issue:** `status` correctly computes "Hết hạn", but the Badge uses `expired ? 'danger' : policy ? 'success' : 'info'` — which is consistent — while `loadDevicePolicy` keeps the expired row in IndexedDB and `applyPolicy` calls `parsePolicyPayload`, which refuses expired tokens. To renew, the user must paste the new payload *and* type the matching Telegram User ID; the card pre-fills the ID, so that part works. The real problem: `AIPopoutView` reloads policy only on `settingsOpen` change; applying a new policy while the drawer is open updates the card but not the chat's `devicePolicy` prop until settings is closed/reopened. Failure scenario: paste renewed policy, close settings, chat still reports "hết hạn" until another settings toggle.

**Fix:** Either reload policy on `visibilitychange`/focus and after apply (lift state to a shared store or emit a custom event), or have `AIPopoutView` use a live query on `db.settings.get(DEVICE_POLICY_SETTINGS_KEY)` so changes propagate automatically.

## Info

### IN-01: `resolveEffectiveChatConfig` and `isModelAllowed` are dead code

**File:** `src/services/telegram/telegramDevicePolicy.ts:87-110`

**Issue:** Exported and tested but never imported by production code. The standalone chat implements its own inline `policyState` logic in `AIPopoutView.tsx:66-70`, diverging from the helper's `'expired'` state and from `isModelAllowed`'s `model.trim()` normalization. Two sources of truth for policy semantics invite drift.

**Fix:** Use `resolveEffectiveChatConfig` in `AIPopoutView` (mapping `'expired'` → `'blocked'` for the UI, or change UI to accept `'expired'`) and call `isModelAllowed` in `AIChatDrawer`; delete the inline logic.

### IN-02: Remote settings `defaultModel`/`maxHistoryTurns`/`dataScope` are shipped but never enforced in standalone

**Files:** `src/services/telegram/telegramDevicePolicy.ts:9-13,102-108` · `src/views/AIPopoutView.tsx:66-70` · `src/components/ai/AIChatDrawer.tsx:811-822`

**Issue:** `remoteSettings` is parsed, validated, persisted and displayed in the admin table but no consumer applies it. Admin "turns: N" and "model: X" columns are informational only. Feature scope may intentionally defer this; document it or wire it in.

**Fix:** If intentional, add a comment in `resolveEffectiveChatConfig` noting standalone does not consume it yet. If not, pass resolved config into `AIChatDrawer` and apply `defaultModel` (clamped by whitelist), `maxHistoryTurns`, `dataScope` at the send boundary.
