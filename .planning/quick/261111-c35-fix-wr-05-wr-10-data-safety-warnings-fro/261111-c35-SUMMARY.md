# Quick 261111-c35: Fix WR-10 and WR-05 data-safety warnings

## One-liner

Partial AI Office restore payloads are now refused before any table clear, and team/skill-version writers reject dangling foreign ids inside their own write transactions.

## What Changed

### Task 1 — WR-10: partial AI Office payload refused before any clear

`replaceTables` in `src/services/backup/restoreBackup.ts` now filters `AI_OFFICE_TABLE_KEYS` against the incoming `tables` before the `targetDb.transaction(...)` call opens. A count that is neither 0 nor 7 throws:

```
Backup thiếu bảng AI Office — từ chối nhập để tránh mất dữ liệu.
```

Throwing outside the transaction is the point: no `clear()` and no `bulkAdd` is ever issued for a malformed payload (D-20). The `clearAiOffice` ternary stayed, so a complete payload still clears-and-replaces and a pre-AI-Office payload still leaves the group untouched.

A comment records why the rollback path is safe: `captureSnapshot` always emits all seven AI keys, so a snapshot replay is always all-present and can never trip the guard.

Regression test in `tests/services/backup/officeBackup.test.ts` seeds all seven tables, restores a payload carrying only `aiSkillVersions: []` (which passes the validator), asserts `rejects.toThrow(/thiếu bảng AI Office/)`, then asserts all six seeded tables still hold their rows.

### Task 2 — WR-05: dangling ids refused at the repository boundary

`src/db/repositories/aiTeamRepo.ts`:
- Added `MISSING_LEAD_MESSAGE` / `MISSING_EMPLOYEE_MESSAGE` module consts in the `LEADER_LOCKED_MESSAGE` style, Vietnamese, no id interpolated.
- Added `assertAgentsExist(leadId, employeeIds, db)` — `db.aiLeads.get` plus `db.aiEmployees.bulkGet`.
- `createTeam` calls it as the first statement inside its `rw` transaction and now scopes `db.aiLeads` and `db.aiEmployees`.
- `updateTeam` calls it right after `assertLeaderUnlocked`, gated on `validated.leadId !== undefined` so an id-omitting patch stays legal; `db.aiLeads` added to its scope.
- `assignLeader` untouched — it already checked.

`src/db/repositories/aiSkillVersionRepo.ts`:
- Added `MISSING_SKILL_MESSAGE`; `db.aiSkills.get(validated.skillId)` is the first statement inside `createSkillVersion`'s transaction, with `db.aiSkills` added to its scope.
- `decideSkillVersion` untouched (WR-08, deferred).

Fixtures: both test files previously seeded bare `generateId()` values with no backing rows. `aiTeamRepo.test.ts` now seeds a real lead and three real employees via `createLead`/`createEmployee` in `beforeEach`, and the four cases that hand-rolled `db.aiLeads.bulkAdd` now use `createLead`. `aiSkillVersionRepo.test.ts` seeds a real skill via `createSkill` and its "another skill" case does the same. No guard was weakened to accommodate stale fixtures.

New negative cases assert both the throw and the absence of writes: no `aiTeams`/`aiTeamMembers` row after a dangling create, unchanged `leadId` after a dangling patch, empty `aiSkillVersions` after a dangling skill.
