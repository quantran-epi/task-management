# Quick 261116-e62: AI mutation tools for Systems Summary

Adds `create_system`, `update_system` and `delete_system` to the AI tool registry, mirroring the
existing change-request trio: three definitions in `AI_DATABASE_TOOLS`, three `executeAiTool`
cases writing through `systemRepo`, three `MUTATION_TOOLS` entries so the approval card parks
them, plus approval-card and status-line copy that names the system rather than only its UUID.

## What Changed

- `src/services/ai/aiTools.ts`
  - Imports `createSystem`, `updateSystem`, `deleteSystem` alongside `getAllSystems`, and
    `SYSTEM_TYPES` from `validation/schemas`.
  - Three tool definitions inserted immediately after `delete_change_request`. The `type`
    property enum is `[...SYSTEM_TYPES]` so the literal list has one source. Descriptions state
    the invariants the repo already enforces (LOGICAL_GROUP takes no SSH/repo and no parent;
    a subsystem's parent must be a LOGICAL_GROUP; code unique; delete is permanent and refuses
    while children exist).
  - Three `executeAiTool` cases: a missing-argument JSON error guard each, then `createSystem` /
    `updateSystem` / `deleteSystem`. The update patch is built only from keys the model sent, and
    the four nullable fields pass `null` through unchanged — `updateSystem` branches on
    `'key' in patch` to tell set from delete. No per-case try/catch: the outer catch already
    turns a repo throw into `{ error: 'Tool execution failed: …' }`.
  - `MUTATION_TOOLS` gains the three names next to the CR entries.
  - `describeToolMutation` gains three cases (create names name/code/type, update names the id
    plus the field diff, delete states it is permanent and unlinks CRs/tasks).
  - `describeToolMutationWithContext` gains `update_system` and `delete_system`, resolving the
    stored row through `db.systems` and falling back to the id-only sentence when the row is
    absent. `create_system` needs no context case — the fallback already names the new system.
- `src/services/ai/aiOrchestratorLoop.ts`: `getFriendlyToolLabel` cases for the trio and the
  function is now exported so tests can pin the three distinct labels.
- `tests/ai/aiTools.test.ts`: pinned count 73 → 76, three name assertions, three
  `isMutationTool` assertions (one cloaked with `_ide`), and one new `it` covering the approval
  sentences and the exported labels.
- `tests/ai/aiToolsSystemMutations.test.ts` (new): fake-indexeddb tool-level tests over a real
  `TaskPlannerDatabase` — create a LOGICAL_GROUP, refuse a SERVICE parent, refuse a duplicate
  code, refuse a LOGICAL_GROUP with `remoteRepoPath`, `null` clears `remoteRepoPath` while a
  name-only update preserves it, delete refuses with a child and succeeds on a leaf while
  emptying CR `targets` and dropping task `systemId`, and the missing-argument errors. Every
  error case asserts the promise resolved with a string `error` field.
