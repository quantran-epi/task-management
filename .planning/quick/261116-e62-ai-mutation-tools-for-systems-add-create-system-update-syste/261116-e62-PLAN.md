# AI mutation tools for Systems

Add `create_system`, `update_system`, `delete_system` to the AI tool registry, mirroring the
existing `create_change_request` / `update_change_request` / `delete_change_request` trio.

Locked scope (from the task brief):

- Reuse `createSystem` / `updateSystem` / `deleteSystem` from `src/db/repositories/systemRepo.ts`.
  No new repo function, no schema change, no Dexie version bump.
- Tool args must map onto `SystemInput` / `SystemUpdate` semantics. `updateSystem` branches on
  `'parentId' in patch`, `'sshConfigId' in patch`, `'remoteRepoPath' in patch`,
  `'defaultBaseBranch' in patch`, so the executor builds the patch from keys the model actually
  sent and never pads with `undefined`.
- Invariants (`LOGICAL_GROUP` has no SSH/repo, subsystem parent must be a `LOGICAL_GROUP`, code
  unique, no cycle, no delete with children) already live in the repo. The tools do not
  re-implement them; they only guarantee the failure comes back as a JSON string. The outer
  `catch` in `executeAiTool` already stringifies a repo throw — the only per-tool error returns
  needed are the missing-argument guards, matching `update_change_request` / `delete_change_request`.
- Type enum comes from `SYSTEM_TYPES` (`src/validation/schemas.ts`) instead of a fourth hardcoded
  literal list. `query_systems` keeps its existing hardcoded enum: that list is
  `261116-e64`'s scope and this item does not widen into it.

Out of scope: allowlists (`EMPLOYEE_READ_ONLY_ALLOWLIST` / `LEAD_TOOL_ALLOWLIST`) stay untouched —
mutation tools are appended to the lead payload by `teamRunCoordinator.leadTools()` through
`isMutationTool`, and employees stay read-only by design.
