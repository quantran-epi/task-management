Output: an `ensureDocsReady` hook, `memberFolderIds` state, an extended `toolContext`, the lead payload's `EMPLOYEE_ONLY_TEAM_TOOLS` filter, prompt wiring, and coordinator tests.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| turn start → `db.notes` | The backfill writes folder rows on a path the user did not explicitly request |
| coordinator context → tool handler | `folderId` is the only thing standing between an agent and another member's folder |
| docs failure → turn lifecycle | A throwing backfill must not kill a chat turn |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigate / rationale |
|-----------|----------|-----------|-------------|----------------------|
| T-41-25 | Tampering | concurrent backfill | mitigate | `ensureTeamDocsReady` re-reads `docsFolderId` and runs `isLiveFolder` INSIDE its own `rw` transaction over `[aiTeams, aiTeamMembers, aiEmployees, notes, settings]` (plan 41-02). Two turns racing on the same team serialise there, so the second observes the first's id and creates nothing. The store list names `aiEmployees` because the function resolves member names from it — omitting it makes every backfill throw, which `ensureDocsReady`'s catch would swallow into a permanently absent folder id. |
| T-41-26 | Elevation of privilege | `toolContext.folderId` | mitigate | The id is resolved from `memberFolderIds` only (built from the member rows) and is never read from `args`. The leader gets NO `folderId` at all: `toolContext` computes `isLead ? undefined : memberFolderIds.get(agentId)`, so the map's entry for the lead's own member row (plan 41-04 creates one) is deliberately not spread. Two independent belts therefore hold: the `role: 'lead'` handler guard refuses first, and the absent folder would refuse `TEAM_DOCS_NOT_READY` second. An agent id not in the map yields no `folderId`, and `write_doc` then refuses rather than defaulting to a broader folder. |
| T-41-33 | Elevation of privilege | lead payload advertising `write_doc` | mitigate | `leadTools()` filters `EMPLOYEE_ONLY_TEAM_TOOLS` out of its team-tool spread, so the model is never offered the tool; the handler's `role === 'lead'` guard refuses a call that arrives anyway. A test asserts the lead payload omits `write_doc` and the employee payload contains it, and the pre-existing "every team tool is in the lead payload" loop is inverted to the filtered form so a future edit that widens the lead payload fails loudly. Without this, a lead turn could write a document into the team folder with no approval card — the exact second write path D-06 forbids. |
| T-41-27 | Denial of service | backfill throw | mitigate | `ensureDocsReady` catches and empties the map. A failing tree degrades to a refusal on the write tool, never to a failed turn — the user's chat still works, which is the higher-value capability. |
| T-41-28 | Tampering | `memberFolders` in the lead prompt | mitigate | Only `roster.employees` ids are looked up, and only members present in `memberFolderIds` are emitted. A member removed mid-turn has no entry, so the lead is never told about a folder that no longer belongs to the roster. Names are wrapped by the prompt builder (plan 41-05). |
| T-41-29 | Elevation of privilege | `write_doc` bypassing the read-only gate | accept, by design | `write_doc` is deliberately absent from `MUTATION_TOOLS` (D-01), so `onMutationCheck` never sees it. The compensating control is the handler's folder guard (plan 41-03) plus the fact that the tool can only write `type: 'document'` into `ctx.folderId`. A test pins `isMutationTool('write_doc') === false` so a future edit that classifies it would fail loudly rather than silently parking every agent write on an approval card. |
| T-41-SC | Tampering | npm/pip/cargo installs | accept | No package install in this phase. |
