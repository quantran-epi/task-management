Output: `write_doc` in `TEAM_TOOL_DEFINITIONS` plus its handler, the `EMPLOYEE_ONLY_TEAM_TOOLS` set the lead payload filters on, and handler-level tests.

| Threat ID | Category | Component | Disposition | Mitigate / rationale |

| T-41-11 | Tampering | `write_doc` update | mitigate | The handler reads the row and refuses with `DOC_NOT_IN_YOUR_FOLDER` unless `parentId === ctx.folderId` and the row is not soft-deleted. The comparison is against the context id, never an arg. |
| T-41-12 | Information disclosure | `write_doc` list | mitigate | `list` filters by `ctx.folderId`, so an agent cannot enumerate another member's folder. Titles are wrapped with `wrapField` because a title written by another model is data, not instructions. |
| T-41-13 | Elevation of privilege | `EMPLOYEE_READ_ONLY_ALLOWLIST` | mitigate | Not modified (D-03). A test asserts `create_note`/`update_note`/`delete_note` stay absent, so a future edit that widens the allowlist fails here rather than silently opening a second write path. |
| T-41-30 | Elevation of privilege | lead calling `write_doc` | mitigate | Two independent guards. The tool is subtracted from the lead payload by `EMPLOYEE_ONLY_TEAM_TOOLS` (plan 41-06's `leadTools()` filter), so the model is never offered it; and the handler refuses any `ctx.role === 'lead'` call with `LEAD_USES_DB_TOOLS` before reading `action`, so a leaked or hand-crafted call still writes nothing. An oversized write is a validation throw from the repo — the handler does not pre-validate body size, so a throw escapes to the tool-error path; accepted, because the repo is the single owner of that ceiling and duplicating it would drift. |
| T-41-SC | Tampering | npm/pip/cargo installs | accept | No package install in this phase. |
