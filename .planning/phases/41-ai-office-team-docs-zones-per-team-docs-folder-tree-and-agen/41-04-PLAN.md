Wire the folder tree into the three team lifecycle writes that must own it: create, delete, and add-member.

Purpose: D-09/D-10/D-11 — the tree must be created and destroyed in the SAME transaction as the row it belongs to, so there is never an orphan team without folders or folders without a team. Output: three modified repo functions, one deliberately unmodified, and lifecycle tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| UI input → `createTeam` | Team name and roster ids are user-supplied |
| team delete → `db.notes` | A delete now reaches the Docs tree, which holds the owner's documents |
| member removal → `db.notes` | Deliberately does NOT reach the tree |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigate / rationale |
|-----------|----------|-----------|-------------|----------------------|
| T-41-16 | Tampering | `createTeam` partial write | mitigate | `db.notes` and `db.settings` join the existing `rw` transaction, so a throw after the team row is added rolls back the folders and the root setting too. Proven by a forced-throw test asserting all three counts are zero. |
| T-41-17 | Tampering | `deleteTeam` scope | mitigate | The delete reads the team row inside the same transaction and passes only that `docsFolderId` to `deleteTeamDocsTree`, which deletes one level of children. The shared `AI Teams` root is never named, and the setting is never touched — both asserted by test. |
| T-41-18 | Denial of service | `deleteTeam` breadth | accept | Deleting a team now also deletes its documents. This is the owner's explicit choice (D-10) and is stated in the UI-facing behaviour; the alternative (soft delete) would leave the tree visible in Trash and re-attachable. |
| T-41-19 | Tampering | `addTeamMember` on a team with a dead folder | mitigate | `isLiveFolder` gates the reuse; a dead id routes through `ensureTeamDocsReady`, which recreates the tree inside the same transaction rather than writing a member folder under a deleted parent. |
| T-41-20 | Repudiation | `removeTeamMember` folder retention | accept | The folder and its documents survive by design (D-11), so a removed member's output stays readable. No audit trail is added because the note rows carry their own `createdAt`/`updatedAt`. |
| T-41-SC | Tampering | npm/pip/cargo installs | accept | No package install in this phase. |
</threat_model>
