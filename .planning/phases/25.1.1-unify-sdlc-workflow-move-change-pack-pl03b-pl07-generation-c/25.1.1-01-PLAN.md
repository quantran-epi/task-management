<objective>
Remove the wizard-snapshot precondition from artifact persistence and make the idempotency key content-addressed, so the SDLC hub can write Notes without a wizard session and regenerate a document at a new version.

Purpose: `artifactRepo.ts` currently refuses to persist unless a chat message in the same thread carries a matching `wizard` snapshot (`currentWizardSnapshot`, `WIZARD_SESSION_MISMATCH` / `WIZARD_APPROVAL_REQUIRED`). That gate is the single reason the hub cannot own DOCX export and change-pack persistence. Separately, the key `${sessionId}:${draftRevision}:${kind}` (`wizardSchemas.ts:210-216`) makes any second write of a *different* body under the same revision fail with `ARTIFACT_IDEMPOTENCY_CONFLICT` — which would kill "Tạo lại PL03B & PL07", a second CAB, and a PL02 re-export. The wizard coordinator still compiles against these APIs until plan 09, so signatures must not change.
Output: `artifactRepo.ts` gated on project/thread/commit identity instead of wizard state, an idempotency key addressed by `inputHash`, plus a regression suite that survives the wizard deletion.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| chat thread → artifact store | caller-supplied `projectId`/`threadId`/`sessionId` decide which project a Note is written under |
| artifact Note body → backup export | Note body carries canonical Markdown plus an arbitrary `exportPayload` JSON |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25.1.1-01 | Tampering | `commitArtifact` / `persistConfirmedPack` | mitigate | After removing the snapshot gate, `assertProjectThread` plus the existing `validatedSources` check keep every write inside a thread whose `scopeType === 'project'` and `entityId === projectId`; no caller-supplied project id is trusted on its own. |
| T-25.1.1-02 | Information disclosure | artifact Note body | mitigate | Body remains `{markdown, exportPayload}` only; no API key, endpoint, or passphrase is ever placed in `exportPayload` (builders receive document content only). |
| T-25.1.1-03 | Repudiation | idempotent replay | mitigate | The key is content-addressed (`${sessionId}:${kind}:${inputHash}`), so an identical body replays to the same Note and a changed body is a new version. The `ARTIFACT_IDEMPOTENCY_CONFLICT` gate remains for a caller that supplies a key whose body or hash disagrees with the stored Note. |
| T-25.1.1-04 | Denial of service | change-pack entry loop | accept | Entry count/size caps already live in `ChangePackLimits` and are enforced before persistence; unchanged by this plan. |
| T-25.1.1-41 | Tampering | unbounded artifact versions | accept | Content-addressed keys allow an unbounded version chain per kind. The chain is bounded in practice by user action, each version is a normal Note inside the existing document set, and the backup size cap already governs export. |
</threat_model>
