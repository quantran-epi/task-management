<objective>
Remove the wizard-snapshot precondition from artifact persistence so the SDLC hub can write Notes without a wizard session.

Purpose: `artifactRepo.ts` currently refuses to persist unless a chat message in the same thread carries a matching `wizard` snapshot (`currentWizardSnapshot`, `WIZARD_SESSION_MISMATCH` / `WIZARD_APPROVAL_REQUIRED`). That gate is the single reason the hub cannot own DOCX export and change-pack persistence. The wizard coordinator still compiles against these APIs until plan 06, so signatures must not change.
Output: `artifactRepo.ts` gated on project/thread/commit identity instead of wizard state, plus a regression suite that survives the wizard deletion.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| chat thread → artifact store | caller-supplied `projectId`/`threadId`/`sessionId` decide which project a Note is written under |
| artifact Note body → backup export | Note body carries canonical Markdown plus an arbitrary `exportPayload` JSON |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25.1.1-01 | Tampering | `commitArtifact` / `persistConfirmedPack` | mitigate | After removing the snapshot gate, `assertProjectThread` plus the existing `validatedSources` check keep every write inside a thread whose `scopeType === 'project'` and `entityId === projectId`; no caller-supplied project id is trusted on its own. |
| T-25.1.1-02 | Information disclosure | artifact Note body | mitigate | Body remains `{markdown, exportPayload}` only; no API key, endpoint, or passphrase is ever placed in `exportPayload` (builders receive document content only). |
| T-25.1.1-03 | Repudiation | idempotent replay | accept | Replay identifies the same Note by `idempotencyKey` and rejects content drift with `ARTIFACT_IDEMPOTENCY_CONFLICT`; a single-user offline app has no separate audit party. |
| T-25.1.1-04 | Denial of service | change-pack entry loop | accept | Entry count/size caps already live in `ChangePackLimits` and are enforced before persistence; unchanged by this plan. |
</threat_model>
