`export async function saveHubSolution(input: HubSolutionInput): Promise<HubSolutionResult>`:
1. `const markdown = input.markdown.trim();` — if empty, `throw new Error('SOLUTION_CONTENT_EMPTY')`.
2. `const hash = await defaultSha256(markdown)` — import `defaultSha256` from `./workflowCoordinator`; do not re-implement SHA-256. This exact hash is what `commitSolution` recomputes, so the two must agree or `persistConfirmedPack`'s `PACK_SOLUTION_MISMATCH` gate fails later.
3. `const result = await saveSolutionVersion({ projectId, threadId, sessionId, inputRevision: input.draftRevision, draftRevision: input.draftRevision, inputHash: hash, markdown, exportPayload: {}, approvedAt: input.approvedAt ?? new Date().toISOString() }, input.db)`.
4. Return `{ noteId: result.note.id, version: result.note.sdlcArtifact!.version, hash, created: result.created }`.

Document one fact in a comment: after plan 01, `draftRevision` is **not** part of the addressed idempotency key (`${sessionId}:SOLUTION:${inputHash}`), so it is bookkeeping only — the same markdown always replays to the same Note and the stored version is always `max(existing versions) + 1`. That is what makes step 3's "commit only on content change" guard safe even though it derives `draftRevision` from `artifacts.solution.version ?? 0 + 1`.

Keep this module free of React, wizard snapshots, and workflow-state writes: the caller owns `commitSolution`. Add a comment stating that separation, so a future caller cannot silently skip the commit and leave `artifacts.solution` stale.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| assistant chat text → artifact Note | model output becomes the canonical SOLUTION.md body and the baseline every later step pins against |
| workflow state → later steps | the solution `hash` recorded here gates change-pack confirmation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25.1.1-42 | Tampering | `handleHubSaveSolution` | mitigate | The Note is written first and only its returned `noteId` is committed to workflow state, so state can never reference a Note that does not exist; the hash is recomputed from the same trimmed markdown by both writer and coordinator. |
| T-25.1.1-43 | Repudiation | `solutionDraftMarkdown` derivation | mitigate | Only assistant messages with no `wizard` payload and not matching the two persistence-event prefixes are eligible, so a system event or a historic wizard row can never be saved as a solution. |
| T-25.1.1-44 | Denial of service | repeated save clicks | mitigate | `solutionSaveBusyRef` blocks re-entry; the panel also disables the button while `saving`. |
| T-25.1.1-45 | Information disclosure | Note body | mitigate | `exportPayload` is `{}` and the body is the Markdown only; model endpoint and API key never enter the Note. |
</threat_model>
