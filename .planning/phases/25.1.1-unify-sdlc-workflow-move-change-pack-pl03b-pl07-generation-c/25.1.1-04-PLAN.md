`toPl03bDocxPayload(proposal: unknown, ctx: { metadata: SdlcWorkflowMetadata; inputRevision: number; draftRevision: number; reconciliation: ReconciliationResult }): Pl03bDocxPayload`:
- Narrow `proposal` with `WizardPl03ProposalSchema`; on failure throw `Error('PL03B_PROPOSAL_INVALID')`.
- Approved envelope: `schemaVersion: 1, kind: 'PL03B', status: 'approved', inputRevision, draftRevision, approvedRevision: draftRevision`.
- `metadata`: `{ crCode: metadata.cr, featureName: metadata.featureName, author: metadata.author, createdDate: metadata.date, version: String(draftRevision) }`.
- `introduction`: `{ purpose: first of approvedDesign, users: '(chưa cung cấp)', databases: tables from reconciliation.dbChangesRollback.affectedTables, k8sServices: [] }`.
- `technical.overview`: `approvedDesign.join('\n')`; `techStack: '(chưa cung cấp)'`; `flows: []`; `services: []`; `integrations: []`; `notifications: []`; `databases: []`.
- `reconciliation: ctx.reconciliation` (verbatim — that is the approved drift record).
- Missing values use `'(chưa cung cấp)'`, never `undefined` or invented data.

`toPl07DocxPayload(proposal, ctx)`:
- Narrow with `WizardPl07ProposalSchema`; on failure throw `Error('PL07_PROPOSAL_INVALID')`.
- `metadata`: `{ applicationName: metadata.featureName, applicationVersion: String(draftRevision), summary: '(chưa cung cấp)', reviewDate: metadata.date, developer: metadata.author, approver: '(chưa cung cấp)' }`.
- `marks`: map each proposal mark — `itemId` like `II.5` splits into `sectionId: 'II'`, `itemNumber: '5'`; a mark whose `itemId` does not match `/^[IV]+\.\d+$/` is dropped with no fabrication. Status maps `PASS→pass`, `FAIL→fail`, `NOT_APPLICABLE→not_applicable`, `UNKNOWN→unknown`; **downgrade `pass`/`not_applicable` to `unknown` when `evidenceIds` is empty** (the builder's `superRefine` requires evidence for positive statuses).
- `findings`: flatten `sectionVI` into `{ number: String(index+1), text: finding, evidenceIds, file: '(chưa cung cấp)', hunk: '(chưa cung cấp)' }` — the docx schema requires non-empty `file`/`hunk`, so use the literal placeholder rather than an empty string.

`generateHubTechDocs(input)`:
1. `const runStage = input.runStage ?? runWizardStage`.
2. `const evidence = await input.collectEvidence({ projectId, threadId, sessionId, inputRevision, query: \`${metadata.cr} ${metadata.featureName} PL03B PL07\`, resolvedSetIds: [] })` — collect once and reuse for both stages.
3. Run PL03 and PL07 sequentially (not `Promise.all`) so a failure of one aborts before any Note is written.
4. For each: `runStage({ kind: 'PL03' | 'PL07', projectId, threadId, sessionId, inputRevision, payload: { evidence, pinnedSolution: solution }, signal, isCurrent })`.
5. Build payloads, then derive markdown: `# {kind} v{draftRevision} — {featureName}\n\n` plus a bullet list of the mapped sections (deterministic, no JSON dump).
6. Persist with `saveApprovedArtifact({ projectId, threadId, sessionId, inputRevision, draftRevision, inputHash: await sha256Hex(markdown), markdown, exportPayload: payload, approvedAt: new Date().toISOString(), kind, sourceArtifacts: [{ id: solution.noteId, hash: solution.hash }] }, db)`. Use the same hash helper as `workflowCoordinator.defaultSha256` (import it; do not re-implement).
7. Return `HubTechDocsResult`.

Create `tests/ai/hubTechDocs.test.ts` with a real `TaskPlannerDatabase` (project + project-scoped thread + a SOLUTION Note whose `sdlcArtifact` matches the input solution pin), stub `collectEvidence`, and stub `runStage` returning schema-valid proposals. Assert every behaviour in `<behavior>`, plus that `buildWizardDocx('PL03B', payload)` and `('PL07', payload)` resolve.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AI model output → DOCX payload | model JSON becomes a document payload and a persisted Note body |
| workflow state → generation inputs | solution and pack pins decide which baseline the documents claim to describe |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25.1.1-14 | Tampering | `toPl03bDocxPayload` / `toPl07DocxPayload` | mitigate | Both adapters narrow with the strict Zod proposal schemas and throw on failure; unknown fields cannot pass into the payload. |
| T-25.1.1-15 | Repudiation | PL07 review marks | mitigate | A `PASS`/`NOT_APPLICABLE` mark with no evidence is downgraded to `unknown`, so the generated review can never assert an unproven pass. |
| T-25.1.1-16 | Information disclosure | artifact Note body | mitigate | `exportPayload` holds document content only; `getNineRouterApiKey` output is passed to the stage call and never written into the payload, markdown, or Note. |
| T-25.1.1-17 | Denial of service | sequential stage calls | accept | Two sequential 8k-token stages add latency; the hub keeps the drawer interactive and shows a status line, and a partial failure writes nothing. |
| T-25.1.1-18 | Tampering | `commitTechDoc` ordering | mitigate | Notes are persisted before the workflow commit, and the workflow commit only receives the persisted `noteId`; a failed commit leaves an orphan Note that is still a valid artifact, never a dangling workflow ref. |
</threat_model>
