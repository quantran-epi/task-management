<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-supplied zip → app | change-pack contents are untrusted bytes from the filesystem |
| pack metadata → workflow state | `meta.json` identity and CR decide which workflow the pack attaches to |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25.1.1-09 | Tampering | `validateChangePack` | mitigate | Removing the caller-supplied identity weakens nothing: zip parsing, path canonicalization, prohibited-entry policy, size caps and CRC checks are untouched, and `validateHubChangePack` still enforces `cr` equality against hub metadata before anything is persisted. |
| T-25.1.1-10 | Spoofing | pack CR | mitigate | The CR check compares the pack's own `meta.json` CR to `SdlcWorkflowState.metadata.cr`, so a pack built for a different CR cannot be confirmed into this workflow. |
| T-25.1.1-11 | Tampering | reconciliation status | mitigate | `buildHubReconciliation` downgrades to `PARTIAL_COVERAGE` when no requirement baseline exists, so the UI can never assert "không phát hiện drift" from coverage alone. |
| T-25.1.1-12 | Denial of service | pack entry writes | mitigate | Persistence stays inside one Dexie transaction with `injectFailure` rollback, so a mid-write error leaves no partial pack. |
| T-25.1.1-13 | Information disclosure | rendered pack content | accept | Pack entry bodies are never rendered in the hub; only CR, branch, counts, and drift tuples are shown. |
</threat_model>
