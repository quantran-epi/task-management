### Finding and fix: missing-source refusal raced the live query

`AIChatDrawerRestoreRecovery.test.tsx` → "refuses Continue while sources are missing and never
strands a running checkpoint" is **not** in the documented baseline list, so it was investigated
rather than accepted.

- First observation: it failed inside the 6-suite command (1 failed | 30 passed).
- Solo repeatability, interleaved HEAD vs pre-phase tree (`git archive 57d3688e`, the last commit
  before phase 25.1.1 code): HEAD **7 failures / 20 runs**; baseline **1 / 20**. Failure signature
  is always the same: `expected 'running' to be 'interrupted'` at
  `tests/ai/AIChatDrawerRestoreRecovery.test.tsx:197` — i.e. the checkpoint had already been
  replaced by `resumeCheckpoint`, so Continue got past the missing-source guard.
- Bisect by commit: `37cad244` (end of wave 7) 0/6 failures; `489d5ca4` (first wave-8 commit) 0/6;
  `e21c4d3a` (wave 8's drawer strip) 3/6. **Attributable to plan 08**, not a pre-existing flake.
- Cause: the guard read `restoredMissingSources`, a `useLiveQuery` value that is `[]` on the first
  render after a restore and only fills in on a later tick. A Continue click that lands in that
  window resumes past the guard. (The component-level suite is where the race surfaces; production
  shows the same window.)
- Fix (`src/components/ai/AIChatDrawer.tsx`, `handleSdlcCheckpointContinue`): derive the missing
  set synchronously from the coordinator's own state (`getState()` / `restore()`) plus
  `db.notes.bulkGet`, before `resumeCheckpoint` is ever called. The live-query value is still used
  for rendering the notice and for the send guard, so the UI is unchanged.
- After the fix: 16/16 consecutive solo runs green, the 6-suite command green ×3, and the send-path
  guard is untouched (`AIChatDrawer.tsx:1730` still blocks a plain send).

No test was added: the existing D-30 case covers exactly this behaviour and was the failing
subject. `npx tsc --noEmit` exit 0 after the change.
