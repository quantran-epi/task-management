`toPl07DocxPayload(proposal, ctx)`:
- Narrow with `WizardPl07ProposalSchema`; on failure throw `Error('PL07_PROPOSAL_INVALID')`.
- `metadata`: `{ applicationName: metadata.featureName, applicationVersion: String(draftRevision), summary: '(chưa cung cấp)', reviewDate: metadata.date, developer: metadata.author, approver: '(chưa cung cấp)' }`.
- `marks`: map each proposal mark — `itemId` like `II.5` splits into `sectionId: 'II'`, `itemNumber: '5'`. **Section filter must be an exact allowlist, not a character class:** drop any mark whose `sectionId` is not one of `'I' | 'II' | 'III' | 'IV' | 'V'` (equivalently, whose `itemId` does not match `/^(I|II|III|IV|V)\.\d+$/`). `pl07MarkSchema.sectionId` is `z.enum(['I','II','III','IV','V'])` (`wizardDocx.ts:145`), so a `[IV]+` class admits `VI.1`/`VII.1`/`IIII.1` and the dispatcher then rejects the whole payload with `WIZARD_DOCX_PAYLOAD_INVALID`. Status maps `PASS→pass`, `FAIL→fail`, `NOT_APPLICABLE→not_applicable`, `UNKNOWN→unknown`; **downgrade `pass`/`not_applicable` to `unknown` when `evidenceIds` is empty** (the builder's `superRefine` requires evidence for positive statuses).
- `findings`: flatten `sectionVI` into `{ number: String(index+1), text: finding, evidenceIds, file: '(chưa cung cấp)', hunk: '(chưa cung cấp)' }` — the docx schema requires non-empty `file`/`hunk`, so use the literal placeholder rather than an empty string. **Drop any finding whose `evidenceIds` is empty**: `WizardPl07ProposalSchema` puts no `.min(1)` on `sectionVI[].evidenceIds` but `wizardDocx.ts:163` requires it, so mapping straight through would emit `WIZARD_DOCX_PAYLOAD_INVALID` for any evidence-less finding. Do not backfill invented evidence ids. Compute `number` after the filter so the remaining findings stay contiguous.
- Add a one-line comment on each drop rule (section allowlist, evidence-less finding) naming the schema mismatch, so a future schema change does not reintroduce it silently.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AI model output → DOCX payload | model JSON becomes a document payload and a persisted Note body |
| workflow state → generation inputs | solution and pack pins decide which baseline the documents claim to describe |
| knowledge sets → evidence | resolved set ids decide which local documents the review may cite |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25.1.1-14 | Tampering | `toPl03bDocxPayload` / `toPl07DocxPayload` | mitigate | Both adapters narrow with the strict Zod proposal schemas and throw on failure; unknown fields cannot pass into the payload. Section ids are filtered through an exact allowlist matching the builder's enum, so a `VI`/`VII` mark cannot be smuggled into the document as a fabricated section. |
| T-25.1.1-15 | Repudiation | PL07 review marks and findings | mitigate | A `PASS`/`NOT_APPLICABLE` mark with no evidence is downgraded to `unknown`, and a finding with no evidence is dropped rather than given an invented citation, so the generated review can never assert an unproven claim. |
