# Phase 25.1.1 Plan 04: Hub Step 4 — Change-Pack Upload, Confirm, and Drift

**Hub step 4 now owns its whole flow: the dropzone validates the pack against the hub's CR, `Xác nhận pack` persists the entries and calls `commitChangePackAndDrift` — the coordinator method that had no production caller — and the drift matrix renders stacked inside the 296px panel. Pack identity comes from the pack's own `meta.json`; the four `UNKNOWN_*` placeholders that rejected every real pack are gone.**

- **Files modified:** 9 (1 created + 1 test created)

## Accomplishments

- `src/services/wizard/hubChangePack.ts`:
  - `validateHubChangePack(file, expectedCr)` validates with no caller identity and rejects only on `meta.json` CR ≠ hub CR.
  - `confirmHubChangePack` persists through `persistConfirmedPack` with `idempotencyKey = buildWizardIdempotencyKey({ sessionId, artifactKind: 'CHANGE_PACK_ENTRY', inputHash: manifest.packHash })`. The doc comment states why the key must not carry a revision counter.
  - `buildHubReconciliation` pins the SOLUTION Note on entity/project/thread/kind/version/hash, then narrow-`safeParse`s `exportPayload`. On failure (the real `saveHubSolution` shape) it uses `requirements: []` and `currentSystem: markdown.trim()` with empty screen/api/table lists — no throw, no fabrication — and re-parses the result as `PARTIAL_COVERAGE`.
- `validateChangePack`'s second parameter is optional. With no identity, `meta.json` supplies it and the comparison is a no-op; a supplied identity behaves exactly as before. Limits, entry policy and hashing untouched.
- `StepChangePackPanel` is now the full prop-driven state machine with explicit focus management: `validating` → status row, `invalid` → `ERROR_COPY` alert + `Chọn pack khác` (focused), `pending` → confirm strip (`Xác nhận pack` focused), `confirming` → strip loading/disabled + `Đang đối chiếu với SOLUTION.md…`, committed → `Đã nạp change-pack {cr}` + stacked matrix + `Chọn pack khác`, plus the stale alert and `Cập nhật lại`.
- `ChangePackConfirmStrip` gained `confirmButtonRef`/`replaceButtonRef` so focus can be re-homed; `DriftMatrixView` gained `headingRef`/`headingTabIndex` so a successful confirm lands focus on the matrix heading.
- `AIChatDrawer`: `hubPackDraft` + `hubPackBusyRef`, `handleHubPackSelect` (compares the live tab id after the await, uses a ref so a stale closure cannot misjudge it), `handleHubPackConfirm`, `handleHubPackReplace`. The draft resets in the existing `[activeTabId]` effect, merged with plan 03's resets — no second effect.
- `stepPanels.changePack` merged into the single `stepPanels` const. Nothing was removed from the wizard path; both coexist until plan 08.

## Deviations from Plan

- **`reconciliation.ts` renamed `UNKNOWN_BASELINE_REQUIREMENT` → `MISSING_BASELINE_REQUIREMENT`.** The plan's acceptance criterion grep `UNKNOWN_CR\|UNKNOWN_BASE` matched this unrelated error code, and it is not referenced anywhere else. The check itself is unchanged; only the message text moved off the `UNKNOWN_` prefix.
- **The legacy wizard path was also moved onto pack-owned identity.** Leaving the drawer's `expectedPackIdentity` in place would have kept `UNKNOWN_CR`/`UNKNOWN_BASE`/`UNKNOWN_HEAD`/`UNKNOWN_BRANCH` in `src/`, failing the plan's own grep, and would have left the wizard rejecting every real pack. The deps hook was removed and `wizardCoordinator.selectChangePack` now calls `validateChangePack(file)` then gates on the hub CR. `validatePack` remains an injectable dep, so `tests/ai/wizardState.test.ts` passes unchanged.
- **The `confirming` failure path returns to `pending`.** The plan says set `invalid` only for a `ChangePackValidationCode`; every other failure shows the enumerated error and returns the draft to `pending` so the user can retry the same pack without re-selecting the file.

## Issues Encountered

- `ChangePackIdentitySchema` is a `strictObject` pick, so `parse(meta)` rejected the extra `author`/`generatedAt`/`commits`/`files` keys. Fixed by parsing the four picked fields explicitly rather than the whole `meta`.
- The first draft of the confirm strip used a `querySelector` adapter to reach the primary button; replaced by passing refs through the shared component, which is one prop pair instead of a component and a `useEffect`.

The pre-existing `tests/ai/AIChatDrawer*.test.tsx` failures listed in the execution constraints were neither touched nor run.
