<objective>
Make the group identity contract real: empty groups, unlimited roster, a durable leader lock enforceable at the repository, and an attribution field that survives the backup path.

Purpose: research proved four concrete holes — `AiTeam.leadId` is required at type/Zod/backup level so an empty group cannot exist (D-05), no field stores the leader lock (D-09), `deleteLead`/`deleteEmployee`/`deleteSkill` leave references that make the app's own export fail validation (AIO-GROUP-05), and `BackupChatMessageRecordSchema` strips `targetAgentId` because it is a plain `z.object` (AIO-DATA-02, confirmed by a live probe). This plan closes the model/validator/repo half; plan 03 closes the deletion-guard and live-use half.

Output: optional `leadId` + `leaderLockedAt`, cap-free `aiTeamRepo` with transactional `assignLeader`/`lockLeader` and a `updateTeam` leader guard, `targetAgentId` in the message record schema, live-vs-historical reference validation, and the two intentional-red regressions that prove the fixes.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backup file → validate | a hand-editable JSON envelope claims team/member/version relationships |
| repo write → Dexie | a caller asks to change a leader or drop a member row |
| LLM tool args → team repo | `delegate_batch`/team tools never create teams, but the repo API is the trust boundary for any caller |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-36-07 | Tampering | `validateBackup` live refs | high | mitigate | Explicit allowlists per relation; only `leadId`/member agent/skill/version/thread scope are live; historical attribution deliberately excluded and commented |
| T-36-08 | Tampering | `assignLeader` / `lockLeader` | high | mitigate | One `rw` transaction per operation; lock write refuses a leaderless group; a second lock preserves the original timestamp |
