<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| in-memory profile → exported JSON file | A user-authored profile crosses to a portable file that may be shared; secrets must not travel. |
| imported JSON file → Dexie settings | Untrusted file content crosses into the canonical local store at `applyConfigProfile`. |
| profile import → OS keyring | The keyring must never be a write target of a profile; secrets are re-entered by the recipient. |
| profile list row → plaintext backup | `configuration_profiles` holds blank secrets and machine paths and must be excluded from backup export. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-46-01 | Information disclosure | exportProfile.ts buildProfileExportPayload | high | mitigate | Catalog-driven blanking of every secret field plus a JSON secret-value scan test; export reads only the passed-in profile, never live db/keyring. |
| T-46-02 | Tampering | importProfile.ts applyConfigProfile trust boundary | high | mitigate | validateConfigProfilePayload strictObject rejection before any write, snapshot first, key-by-key merge, zero writes on invalid input. |
| T-46-03 | Tampering | importProfile.ts key-by-key merge | high | mitigate | Skip blank secret fields so a recipient's real value survives; no keyring writes from profile; test reproduces a pre-existing secret. |
| T-46-04 | Information disclosure | exportBackup.ts UNSAFE_OR_EPHEMERAL_SETTING_KEYS | medium | mitigate | Add `configuration_profiles` to the denylist so the saved profile list is excluded from plaintext backups. |

</threat_model>
