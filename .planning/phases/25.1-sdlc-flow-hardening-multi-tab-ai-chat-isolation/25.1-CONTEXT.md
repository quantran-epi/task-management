# Phase 25.1: SDLC Flow Hardening & Multi-Tab AI Chat Isolation - Context

**Gathered:** 2026-10-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Hoàn thiện AI Chat Drawer và SDLC workflow đã có từ Phase 25. Mọi scope phải hỗ trợ nhiều tab cô lập hoàn toàn; Project có đúng một tab SDLC cố định và không đóng được. Cô lập bao gồm history, config chat, draft, attachments, request/stream/loading/tool state, retry/error và wizard state. SDLC phải bền vững qua đóng drawer/restart, phục hồi qua encrypted backup/import, hiển thị progress rõ trong drawer hẹp, cho nạp nhiều nguồn PL01/PL02 từ Note hoặc text, và hỗ trợ revision loop cho requirement/solution với impact analysis và stale propagation.

Không thay đổi endpoint/API key global, không thêm backend riêng, không tạo tab SDLC thứ hai cho cùng Project, không lưu partial/error AI response thành chat history.

</domain>

<decisions>
## Implementation Decisions

### Vòng đời tab
- **D-01:** Mọi scope tạo một chat thường mặc định khi chưa có dữ liệu. Project tạo thêm đúng một tab SDLC cố định.
- **D-02:** Đóng chat thường cuối cùng phải tạo chat thường mới ngay. Tab SDLC không có nút đóng và không thể tạo bản sao.
- **D-03:** Tiêu đề chat thường tự sinh, user được sửa, tên lưu trong thread.
- **D-04:** Mỗi scope nhớ tab active gần nhất riêng; khôi phục sau đổi scope và restart.

### Isolation và persistence
- **D-05:** Mỗi tab là execution container độc lập: history/context boundary, draft, attachments/references, streaming/loading, tool/MCP progress, AbortController, partial buffer, error/retry, wizard/export state, model, Analysis Mode, MCP/Knowledge toggles, prompt/context options và token usage.
- **D-06:** Request tab nền tiếp tục chạy khi chuyển tab. Badge/spinner gắn đúng tab; drawer và tab khác không bị khóa.
- **D-07:** Endpoint và API key là global application config, không thuộc tab. Config chat còn lại lưu cùng thread trong DB, không dùng localStorage làm nguồn canonical.
- **D-08:** Khi đóng tab đang chạy, hỏi xác nhận, abort request rồi mới xóa thread/tab. Không để request mồ côi.
- **D-09:** Đóng drawer không abort request khi app còn chạy. Nếu Tauri process thoát, lưu checkpoint; lần mở lại đánh dấu `interrupted`, cho user tiếp tục/retry stage, không giả request cũ còn chạy.
- **D-10:** Không giới hạn concurrency ở app-level; provider/rate-limit xử lý giới hạn. Một tab không khóa tab khác.

### Response và lỗi
- **D-11:** User message lưu ngay trước request. Assistant partial chỉ ở runtime buffer; chỉ commit một assistant message sau khi stream hoàn tất và toàn bộ payload bắt buộc hợp lệ.
- **D-12:** Transport timeout, abort, parser/JSON/tool schema lỗi làm toàn response invalid; không tự sửa payload và không commit phần text hữu ích kèm payload lỗi.
- **D-13:** Lỗi hiển thị bằng error card ngoài chat history, thuộc request/runtime state; diagnostics phải sanitize, không lộ secret hoặc nội dung nhạy cảm.
- **D-14:** Retry dùng lại cùng user message, tạo request ID mới; không nhân bản input, không lưu error message vào history.
- **D-15:** Lỗi một tab chỉ tác động tab đó; tab khác giữ history/loading và tiếp tục hoạt động.

### SDLC progress và intake
- **D-16:** Progress dùng timeline dọc compact 6 bước, không cuộn ngang/co chữ. Mỗi bước hiển thị completed, processing, stale, not yet hoặc error bằng indicator + text.
- **D-17:** Tách `selectedStep` khỏi `currentProcessingStep`. Click bước chỉ xem artifact/checkpoint và action hợp lệ; không tự nhảy state machine hoặc đổi bước đang xử lý.
- **D-18:** PL01 và PL02 chọn độc lập: nhập text hoặc chọn Note. Một modal search Note toàn hệ thống, mặc định filter Project hiện tại, cho chọn nhiều Note theo từng loại và preview nguồn trước khi bắt đầu.
- **D-19:** Giữ từng Note source ID/version/hash; AI tạo bản hợp nhất có citation và cảnh báo mâu thuẫn. Không sửa Note gốc.
- **D-20:** Có action rõ `Cập nhật yêu cầu` và `Cập nhật solution` tại SDLC header/step. User được brainstorm nhiều vòng đến khi chốt revision.
- **D-21:** Revision phải preview diff, nguồn, impact toàn chain và bước stale; chỉ commit sau xác nhận user, không tự ghi đè artifact.

### SDLC state machine và revision
- **D-22:** Requirement revision giữ Intake completed và làm stale theo dependency từ `SOLUTION` đến `CAB`.
- **D-23:** Solution revision làm stale `CODE_GUIDE`, `CHANGE_PACK`, `TECH_DOCS` và `CAB`; PL01/PL02 giữ completed.
- **D-24:** Artifact dùng immutable versions + active pointer. Artifact cũ không bị xóa hoặc ghi đè.
- **D-25:** Artifact stale chỉ read-only để audit/so sánh; không dùng làm baseline cho bước mới.
- **D-26:** CAB duyệt đặt revision cycle ở trạng thái completed. Change phút chót, hotfix hoặc lỗi sau go-live mở revision cycle mới trong cùng SDLC tab/project; không tạo thread/tab mới.
- **D-27:** Cùng SDLC tab hiển thị nhiều cycle thu gọn; cycle hiện tại mở rộng, cycle cũ read-only.

### Backup và restore
- **D-28:** Restart/đóng drawer phục hồi từ DB. Cài lại phục hồi qua encrypted GitHub backup hiện có hoặc local import; không thêm sync/backend riêng.
- **D-29:** Backup phải chứa thread/tab, active tab theo scope, per-tab config, workflow/checkpoint, revision/active pointers, artifact refs và history hợp lệ. Không chứa API key, passphrase, partial response hay error response.
- **D-30:** Import validate schema/liên kết trước khi ghi. Nếu thiếu Note nguồn, khôi phục checkpoint và báo nguồn cần bổ sung/thay thế; không tự chạy AI, tạo Note rỗng hoặc bỏ workflow.

### Claude's Discretion
- Chọn cấu trúc DB/migration cụ thể, miễn giữ tương thích backup và không phá dữ liệu hiện có.
- Chọn cơ chế request registry/checkpoint cụ thể, miễn stale response không ghi đè state mới và double-submit được chặn.
- Chọn primitive Ant Design cho timeline/modal/error card theo codebase hiện có, miễn đạt D-16/D-17 và accessibility.

</decisions>

## Existing Code Insights

### Reusable Assets
- `chatRepo.ts` đã có `getOrCreateSdlcThread`, `createChatTabThread`, `getProjectThreads` và xóa tab; cần tổng quát hóa scope key và bọc tab metadata/runtime persistence thay vì bỏ pattern hiện có.
- `ChatTabBar` đã có tab SDLC không đóng, Analysis indicator và badge status; nên giữ semantics, thay indicator bằng state theo tab.
- `workflowSchemas.ts` và `workflowCoordinator.ts` đã có typed step/artifact/hash/version/stale primitives; mở rộng theo hướng additive và migration-safe.
- `stalenessDetector.ts`, `artifactRepo.ts`, backup validators và test fixtures là nền cho dependency propagation, immutable revisions và restore validation.
- Ant Design `Badge`, `Tag`, `Timeline`/`Steps`, `Modal`, `Alert`, `Card` và theme tokens đã dùng trong drawer.

### Established Patterns
- Dexie là nguồn dữ liệu local; repository transaction dùng cho thread/message writes.
- Chat history lưu `ChatMessage`; wizard snapshot đã được schema-validate trước persist.
- Project SDLC hiện dùng thread scope key riêng và fallback legacy project thread; migration phải giữ legacy data an toàn.
- UI dùng Ant Design token, tiếng Việt và drawer width responsive; không thêm dependency UI.
- Backup/import có validation và data-safety gate; không ghi dữ liệu trước khi validate toàn payload.

### Integration Points
- `AIChatDrawer.tsx` cần tách state map theo `threadId`/tab ID, request registry và per-tab rendering.
- `ChatTabBar.tsx` nhận per-tab runtime status thay vì một `sdlcStatus`/shared mode.
- `chatRepo.ts`/models/Dexie schema và backup serializers cần đồng bộ tab metadata/config/checkpoint.
- `SdlcWorkflowHub.tsx` nhận `selectedStep` riêng, current processing step và revision-cycle history.
- `StepInputDocsModal.tsx` kết nối Notes search/filter/preview/multi-select.
- AI request/stream path trong `AIChatDrawer.tsx` cần commit boundary và error card ngoài persisted history.

## Specific Ideas

- User gọi rõ hành vi sửa đổi là “cập nhật, bổ sung requirement business hoặc cập nhật solution”, sau đó tiếp tục loop brainstorm cho đến khi có kết quả và hiển thị impact lên toàn bộ step sau.

- Endpoint được xác nhận là URL dịch vụ AI, vẫn global cùng API key; không nhầm với per-tab chat config.
- “Cài lại ứng dụng” được hiểu là phục hồi từ encrypted GitHub backup hiện có hoặc local backup import, không phải backend sync mới.
