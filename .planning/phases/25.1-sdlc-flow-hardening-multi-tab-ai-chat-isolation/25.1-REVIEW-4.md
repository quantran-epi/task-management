## Critical Issues

### CR-09: "Xóa toàn bộ lịch sử AI" deletes threads but keeps tab rows, leaving a store its own backup validator rejects

**File:** `src/db/repositories/chatRepo.ts:178-185`; `src/components/ai/AIChatDrawer.tsx:2714-2730, 3194`
**Issue:** `clearAllChatHistory` clears `chatMessages` and `chatThreads` only. `chatTabs` rows survive with `threadId` values that no longer exist, and `sdlc_workflow:<projectId>:<threadId>` settings survive too. Consequences with concrete evidence:

1. The app's own export cannot be restored. `validateBackup` runs its chatTabs/chatThreads block whenever `chatThreads` is a defined (here empty) array and rejects every surviving tab: `ChatTab references threadId "..." not found in chatThreads` (`src/services/backup/validateBackup.ts:374-397`). `restoreBackupPayload` throws `Backup payload must pass validation before restore` (`src/services/backup/restoreBackup.ts:256-257`), and `ImportPreviewModal` renders the backup as invalid. The user loses the ability to restore a backup exported after using this menu item.
2. The next send writes into an unbound thread. `activeThreadId` still points at the deleted thread (`AIChatDrawer.tsx:433-442`), so `messages` is permanently empty; `handleSendMessage` then falls through `db.chatThreads.get(turnTab.threadId)` → `thread` (both undefined) and creates a plain scope-level thread via `createOrGetThread` (`:1620-1640`), which no tab references. The user message and the answer are persisted where the drawer never reads them.
3. Stale SDLC state: `getSdlcCoordinator` reads `sdlc_workflow:*` from settings (`:1006-1020`), so the hub keeps rendering steps for a conversation whose history was just deleted.

**Fix:** Make the reset a single transaction that keeps the tab/thread invariant:
```ts
export async function clearAllChatHistory(db = defaultDb): Promise<void> {
  await db.transaction('rw', [db.chatMessages, db.chatThreads, db.chatTabs, db.settings], async () => {
    await db.chatMessages.clear();
    await db.chatThreads.clear();
    // Ordinary tabs must die with their threads; the SDLC tab is recreated lazily by getOrCreateSdlcTab.
    await db.chatTabs.filter((tab) => tab.type !== 'sdlc').delete();
    await db.settings.filter((row) => String(row.key).startsWith('sdlc_workflow:')).delete();
  });
}
```
and let the existing `initTabs`/`ensureTurnTab` bootstrap rebuild the first tab, then add a regression test that exports → validates the envelope after a reset.

### CR-10: Closing the last ordinary tab creates a second active tab for the scope

**File:** `src/db/repositories/chatTabRepo.ts:202-239` (replacement branch at `:210-233`)
**Issue:** When the scope's last ordinary tab is deleted, the replacement is inserted with `active: true` without clearing the sibling's active flag:
```ts
await db.chatTabs.add({ id, threadId: id, scopeKey: tab.scopeKey, type: 'chat', title, order: 0, active: true, ... });
```
If the SDLC tab is the active tab (the normal state after `setActiveTab(scopeKey, sdlcTab.id, db)` in `AIChatDrawer.tsx:636-638`, and after every intake at `:1117`), closing an inactive ordinary tab now leaves two rows with `active: true` in the same scope. Every other writer maintains one active tab (`createChatTab` `:121-123`, `getOrCreateActiveChatTab` `:170`, `setActiveTab` `:179-181`, migration v14 `src/db/index.ts:257-264`), so this branch is the sole invariant breaker. Two persisted consequences:

- `validateBackup` emits `Multiple active tabs for scope` (`src/services/backup/validateBackup.ts:398-401`), so a backup exported afterwards cannot be restored (same failure mode as CR-09).
- `activeTab = durableTabs.find((t) => t.active) ?? durableTabs[0]` (`AIChatDrawer.tsx:431`) silently resolves to the SDLC tab, so reopening the drawer never shows the user the tab they just kept.

**Fix:**
```ts
const stillActive = (await listTabsByScope(tab.scopeKey, db)).some((row) => row.active);
await db.chatTabs.add({ ..., active: !stillActive });
```
and add a repo test: active SDLC tab + one inactive ordinary tab → delete ordinary → exactly one `active` row per scope.

### CR-11: Pending clarification leaks one tab's query into another tab's request

**File:** `src/components/ai/AIChatDrawer.tsx:322-327, 1570-1586, 1853-1861`
**Issue:** `transientClarifyMessage` is drawer-global and is consumed by whichever tab sends next, not by the tab that produced the clarification:
```ts
if (transientClarifyMessage) {
  nextClarifyTurnCount = transientClarifyMessage.turnCount + 1;
  effectiveQuery = `${transientClarifyMessage.originalQuery}\n[Thông tin bổ sung]: ${trimmed}`;
}
```
Sequence: tab A triggers `clarify_intent` (grounded path stores the state), user switches to tab B and sends a normal question; tab B's transport request is built from tab A's original query plus tab B's text, while only `trimmed` is persisted as tab B's user row (`:1656-1665`). If tab A already reached count 2, tab B's send is instead rejected with the clarification-failure error (`:1572-1583`). This directly contradicts the phase's isolation contract (D-06/D-10) and silently changes what the model is asked.

**Fix:** Key clarification state by tab (`Record<tabId, {...}>` or `TabRuntime.clarify`) and read it from `turnTabId`; drop it for a tab when that tab is closed/reset. Also key the card render on the resolved owner tab rather than on `msg.content === originalQuery` (`src/components/ai/ChatMessageList.tsx:171-179`).

### WR-08: Note source picker resets the user's in-progress selection on every drawer re-render

**File:** `src/components/ai/wizard/NoteSourcePickerModal.tsx:57-73`
**Issue:** The reset effect is keyed on `initialSelectedKey`, which is the parent's *current* selection (`pl01Sources`/`pl02Sources` mapped at `StepInputDocsModal.tsx:275-279`). Every drawer re-render that changes those arrays (or any remount with a different array) re-runs the effect and calls `setSelectedIds(new Set(initialSelectedIds))`, discarding checkboxes the user just ticked before pressing Apply. The test suite already documents the symptom: "The picker resets its selection whenever the drawer re-renders, so select + apply is retried" with a 6-attempt retry loop (`tests/ai/AIChatDrawerSdlcIntake.test.tsx:89-113`).
**Fix:** Reset only on the closed→open transition, not on content change:
```ts
const wasOpen = useRef(false);
useEffect(() => {
  if (!open) { wasOpen.current = false; return; }
  if (wasOpen.current) return;           // keep the live selection while the dialog is open
  wasOpen.current = true;
  setSelectedIds(new Set(initialSelectedIds));
  ...
}, [open, projectId]);
```

### WR-09: Transient status/error writes still bind to the last tab that sent

**File:** `src/components/ai/AIChatDrawer.tsx:1451-1465, 1809-1826, 2037-2059`
**Issue:** `patchGroundedLoading` and `patchTurnError` default `ownerTabId = turnTabIdRef.current`, evaluated at call time. `turnTabIdRef` is a single ref overwritten by each send (`:1534`), while the grounded callbacks created for tab A's turn (`deps.routeScope`, `deps.retrieveFederated`, `deps.runLocalBm25`, `deps.synthesizeGroundedAnswer`, and the catch handlers at `:2037-2059`) run after tab B may have overwritten it. Two ordinary (non-analysis) tabs run concurrently → tab A's spinner text and error card land on tab B. This is the residual half of REVIEW-3 NF-02.
**Fix:** Capture the owner once per turn and pass it explicitly:
```ts
const ownerTabId = turnTabId;            // captured at send time
...
patchGroundedLoading('Đang xác định phạm vi tài liệu...', ownerTabId);
```
or bind the callbacks with `.bind(null, ownerTabId)` instead of relying on the ref default.

### WR-10: Restore recovery metadata is written but never read

**File:** `src/services/backup/validateBackup.ts:202, 402-435, 626-631`; `src/services/backup/exportBackup.ts:156`; `src/components/settings/ImportPreviewModal.tsx:60-67`
**Issue:** `validateBackupPayload` builds `recovery.missingSources`/`recovery.blockedTabs` and mutates `tab.workflowState.checkpoint` to `interrupted`, and `projectSafeChatTab` exports `workflowState`. Nothing in `src/` reads `ChatTab.workflowState` at runtime — the drawer's SDLC state lives under `settings['sdlc_workflow:<projectId>:<threadId>']` (`AIChatDrawer.tsx:1006-1020`) — and `ImportPreviewModal` uses only `validationResult.valid/envelope/counts`. So the persisted "blocked tab" is inert, and the two stores can disagree: the tab row can say `interrupted` while the settings key still says `running`, which is what the drawer actually restores.
**Fix:** Pick one store. Either have the drawer's `getSdlcCoordinator` read the checkpoint from the tab row when present, or have `replaceTables` translate `recovery.blockedTabs` into the corresponding `sdlc_workflow:*` settings rows. Also surface `validation.recovery` in the import preview so the user is told before confirming.

### WR-11: A failed `requestRegistry.begin` is treated as a successful turn

**File:** `src/components/ai/runtime/requestRegistry.ts:24-36`; `src/components/ai/AIChatDrawer.tsx:1535-1540, 1674-1682, 2453-2456`
**Issue:** `begin` returns `null` when the tab already has a current request, but the send path uses `const controller = activeReq?.controller ?? new AbortController()` and continues. The turn then runs detached, and `isCurrent(activeReq?.requestId ?? '', ...)` is permanently false, so the assistant output is dropped at `:2453` while the user row saved at `:1657` persists. The pre-guard (`hasActive || status === 'processing'`) is separated from `begin` by several awaits (`createOrGetThread`, `db.chatThreads.get`, `saveMessage`), so a second entry into the same tab within that window reaches this state. Result: a user bubble with no answer and no error.
**Fix:** Fail closed:
```ts
const activeReq = requestRegistryRef.current.begin(turnTabId, activeThread.id);
if (!activeReq) return;   // or surface a per-tab "turn already running" status
```
and add a unit test for the null branch.

### WR-12: Ordinary-tab bootstrap adopts a thread without the claim check the SDLC path uses

**File:** `src/db/repositories/chatTabRepo.ts:140-173` (adoption at `:147-156`) vs `:77-96` (`claimedThreadIds` at `:84-87`)
**Issue:** `getOrCreateActiveChatTab` adopts `db.chatThreads.where('scopeKey').equals(input.scopeKey).first()` unconditionally, while `getOrCreateSdlcTab` refuses a legacy `project:<id>` thread that is already claimed by a tab. If the bootstrap effect (`AIChatDrawer.tsx:575-584`) or a first send runs concurrently with `initTabs` (`:588-650`), the ordinary path can adopt the same legacy thread the SDLC tab just claimed. `chatTabs` has a unique index on `threadId` (`src/db/schema.ts:99`), so the second `add` raises a ConstraintError and aborts the whole transaction — the send rejects instead of creating a tab.
**Fix:** Apply the same claim check in `getOrCreateActiveChatTab`:
```ts
const claimed = new Set((await db.chatTabs.toArray()).map((tab) => tab.threadId));
const legacy = (await db.chatThreads.where('scopeKey').equals(input.scopeKey).toArray())
  .find((thread) => !claimed.has(thread.id));
```

### WR-13: Continue on a missing-source checkpoint strands a `running` checkpoint

**File:** `src/components/ai/AIChatDrawer.tsx:1038-1053, 1544-1565, 3087-3093`
**Issue:** `handleSdlcCheckpointContinue` calls `resumeCheckpoint()`, which persists `status: 'running'` (`src/services/wizard/workflowCoordinator.ts:86-101`), then sends. `handleSendMessage` hits the missing-source guard at `:1554` and returns before `setCheckpoint`/the `try…finally` that clears the checkpoint (`:2523-2528`). The durable checkpoint stays `running`, and the banner only renders for `interrupted` (`:3087`), so the Continue/Discard controls disappear until a reload flips `running → interrupted` again (`workflowCoordinator.ts:65-68`). The user is left with an error card and no way to discard the checkpoint in-session.
**Fix:** Evaluate the missing-source guard before `resumeCheckpoint`, or catch the early return and call `clearCheckpoint()`/restore `interrupted` in `handleSdlcCheckpointContinue`'s `finally`.

### WR-14: Rollback permanently loses the running timer

**File:** `src/services/backup/restoreBackup.ts:174-191, 214-224, 267-274`
**Issue:** `replaceTables` clears `activeTimers` (`:223`) for both import and rollback, but `captureSnapshot` never reads it (the 20-way `Promise.all` at `:175-177` has no `targetDb.activeTimers`), so the snapshot stored in `last_pre_import_snapshot` cannot restore it. Import → rollback destroys the in-progress timer and its segments. (The omission predates this phase — `9694731^` had the same shape — but it is still live in a reviewed file and is data loss on a documented recovery path.)
**Fix:** Add `activeTimers` to `SnapshotData`/`captureSnapshot` and to the restore loop at `:248`, then assert it in `tests/services/backup/restoreBackup.test.ts`.

### WR-15: Local SQLite persistence copies AI/knowledge secrets and trusts unvalidated rows

**File:** `src/services/localSqlitePersistence.ts:61-75, 100-106, 155-187, 235-261`
**Issue:** `EXCLUDED_SETTING_KEYS` lists only the Jira/GitHub/backup secrets. The AI and knowledge credentials written to `db.settings` on the non-Tauri path — `ninerouter_api_key`, `knowledge_server_token`, `image_api_key` (`src/services/ai/nineRouterTokenService.ts:70`, `src/services/knowledge/knowledgeConfig.tsx:83-87`) — are neither excluded here nor filtered by `isSqliteTableName`, so each write is serialized into the `tauri_sqlite_queue` setting (`:168`) and, once local SQLite is enabled, written in plaintext into the user's SQLite file (the hooks are mounted app-wide by `src/components/shell/AppShell.tsx:122`). That contradicts the deny-list in `src/services/backup/exportBackup.ts:9-33`, which treats exactly these keys as unsafe to persist. (The queue setting itself is on that export deny-list, so backups are not affected.) Separately, `hydrateDexieFromSqlite` does `JSON.parse(row.payloadJson)` and `db.table(...).put(parsed)` in a loop with no per-row guard (`:250-259`): one malformed row aborts hydration after partial writes, and an unexpected payload bypasses any schema check.
**Fix:** Reuse one exported deny-list (`UNSAFE_OR_EPHEMERAL_SETTING_KEYS`) instead of the local `EXCLUDED_SETTING_KEYS`, and wrap the hydrate loop so a bad row is skipped and reported rather than aborting the batch.

### WR-16: Tab strip exposes broken ARIA wiring

**File:** `src/components/ai/ChatTabBar.tsx:174-190, 284-315`
**Issue:** Each tab sets `aria-controls={`chat-tabpanel-${tab.id}`}` but no element in the app carries that id (no `chat-tabpanel` id exists anywhere in `src/`), so assistive tech is pointed at a nonexistent panel. The close control is a bare `<span role="button">` with no `tabIndex`, no key handler, and no `aria-disabled` state, nested inside the `role="tab"` element — a nested interactive control that keyboard users cannot reach (they can only use the undocumented Delete/Backspace path at `:136-141`).
**Fix:** Either render a real `role="tabpanel"` with the matching id, or drop `aria-controls`; replace the close span with `<button type="button" tabIndex={-1}>` (or keep it out of the tab stop order but keyboard-operable via the existing Delete handler documented in the tab's `aria-description`).
