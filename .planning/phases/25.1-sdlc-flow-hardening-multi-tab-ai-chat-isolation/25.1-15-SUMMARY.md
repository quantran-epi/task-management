The real-app Playwright spec now proves concurrency, per-tab error isolation, retry identity, revision/cycle retention, missing-source restore, and backup round-trip identity instead of tab labels plus one request — and two latent production bugs surfaced by that depth are fixed.

- **D-15 error isolation**: exactly one `[data-testid="inline-api-error-card"]` renders, on the owning tab; the sibling tab shows neither `Lỗi` nor `Đang xử lý`, and switching back restores the error card for its owner.
- **D-14 retry identity**: after a failed turn the user row exists once and no assistant row is persisted; `Thử lại` produces a new transport request and still exactly one `role === 'user'` row with the original content.
- **D-20..D-27 revision/cycles**: a seeded completed cycle plus a valid SOLUTION artifact makes `Cập nhật solution` available; the modal shows the diff and impact chain, commit opens cycle 2 and leaves cycle 1 as a read-only `Chỉ đọc` row.
- **D-30 missing sources**: the restored workflow renders the artifact-titled `role="status"` notice, the missing Note id is absent from restored rows, a send is blocked with zero transport growth, and a positive control (Note re-created under the same id) proves a real send then fires.
- **D-28/D-29 backup round-trip**: tabs match on `id`/`type`/`title`/`active`, messages match on `id`/`role`/`content`, exactly one active tab per scope survives, the exported JSON contains no api-key/passphrase/partial-buffer/streaming keys, and the restored drawer renders the renamed tab plus its history.

## Two production bugs the deeper spec found

1. **SDLC state was keyed by the wrong thread** — `getSdlcCoordinator` built `sdlc_workflow:<projectId>:<activeThreadId>`. Intake fired during the first render wrote the state under an ordinary tab's thread, so once the SDLC tab became active the hub restored nothing and showed "Chưa khởi tạo". The coordinator now resolves the durable SDLC tab's thread and rebuilds only when that id changes.
2. **Two active tabs per scope** — `getOrCreateActiveChatTab` read the tab list and inserted `active: true` outside a transaction, so the drawer bootstrap racing `createChatTab` left two actives and made the active tab order-dependent (the Send button stayed disabled because the composer belonged to a different tab). Now a single transaction that clears siblings.

A third, third-party-level fix: antd v6 `Alert` hardcodes `role="alert"` and drops a passed `role`, so `RestoredSourceNotice`'s declared `role="status"` never reached assistive tech. The alert is now wrapped in a `role="status" aria-live="polite"` element.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] antd v6 Alert drops a passed `role`, so the notice was never a status region**
- **Found during:** Task 3 (missing-source test could not find `role="status"`)
- **Issue:** `RestoredSourceNotice` passed `role="status"` to `Alert`, but antd v6 spreads `role: "alert"` after `...restProps`, and `pickAttrs` keeps only `aria`/`data` attributes anyway.
- **Fix:** Wrapped the alert in `<div role="status" aria-live="polite">`.
- **Files modified:** `src/components/ai/RestoredSourceNotice.tsx`
- **Commit:** `cbea9ef`

**2. [Rule 1 - Bug] SDLC workflow state persisted under the active ordinary tab's thread**
- **Found during:** Task 3/4 (revision and D-20 tests could not restore the hub)
- **Issue:** `getSdlcCoordinator` used `activeThreadId`, which during the first render is the bootstrapped ordinary tab, so `sdlc_workflow:<project>:<ordinaryThread>` was written and the SDLC tab restored nothing.
- **Fix:** Resolve the durable SDLC tab's thread id, build the coordinator against it, and track the id in `sdlcCoordinatorThreadRef` so a change rebuilds.
- **Files modified:** `src/components/ai/AIChatDrawer.tsx`
- **Commit:** `98b9718`

**3. [Rule 2 - Missing critical functionality] `getOrCreateActiveChatTab` could leave two active tabs in a scope**
- **Found during:** Task 4 (Send button stayed disabled after a tab switch)
- **Issue:** The "is there an active tab?" read and the `active: true` insert were not atomic, so the drawer bootstrap racing `createChatTab` produced two actives; `activeTab` resolution then depends on sort order.
- **Fix:** Perform read + sibling-clear + insert in one `rw` transaction over `chatThreads` and `chatTabs`.
- **Files modified:** `src/db/repositories/chatTabRepo.ts`
- **Commit:** `98b9718`

**4. [Rule 1 - Bug] `D-16..D-19` 320px test was order-dependent**
- **Found during:** Task 4 (`--repeat-each=2` failed one of two)
- **Issue:** The drawer is flex-sized from the previous viewport width; sampling `scrollWidth` once right after `setViewportSize` sometimes read the pre-reflow layout (~1111px). Reproduced on the pre-plan spec file (2/4 failures), so it predates this plan.
- **Fix:** Poll the scroll metrics with `expect.poll` until the layout settles, then assert. 4/4 green on repeat.
- **Files modified:** `e2e/sdlcFlowHardening.spec.ts`
- **Commit:** `860a241`

**5. [Rule 3 - Blocking issue] Restore drops the API key, breaking the positive control**
- **Found during:** Task 3
- **Issue:** The exported backup strips `ninerouter_api_key`, so after the import the positive-control send failed with "Chưa cấu hình API Key" instead of reaching the transport (this is correct product behavior and also proof the export deny-list works).
- **Fix:** Re-run `configureAiKey` after the post-import reload, before the positive control.
- **Files modified:** `e2e/sdlcFlowHardening.spec.ts`
- **Commit:** `cbea9ef`
