## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Vòng đời tab
- **D-01:** Mọi scope tạo một chat thường mặc định khi chưa có dữ liệu. Project tạo thêm đúng một tab SDLC cố định.
- **D-02:** Đóng chat thường cuối cùng phải tạo chat thường mới ngay. Tab SDLC không có nút đóng và không thể tạo bản sao.
- **D-03:** Tiêu đề chat thường tự sinh, user được sửa, tên lưu trong thread.
- **D-04:** Mỗi scope nhớ tab active gần nhất riêng; khôi phục sau đổi scope và restart.

#### Isolation và persistence
- **D-05:** Mỗi tab là execution container độc lập: history/context boundary, draft, attachments/references, streaming/loading, tool/MCP progress, AbortController, partial buffer, error/retry, wizard/export state, model, Analysis Mode, MCP/Knowledge toggles, prompt/context options và token usage.
- **D-06:** Request tab nền tiếp tục chạy khi chuyển tab. Badge/spinner gắn đúng tab; drawer và tab khác không bị khóa.
- **D-07:** Endpoint và API key là global application config, không thuộc tab. Config chat còn lại lưu cùng thread trong DB, không dùng localStorage làm nguồn canonical.
- **D-08:** Khi đóng tab đang chạy, hỏi xác nhận, abort request rồi mới xóa thread/tab. Không để request mồ côi.
- **D-09:** Đóng drawer không abort request khi app còn chạy. Nếu Tauri process thoát, lưu checkpoint; lần mở lại đánh dấu `interrupted`, cho user tiếp tục/retry stage, không giả request cũ còn chạy.
- **D-10:** Không giới hạn concurrency ở app-level; provider/rate-limit xử lý giới hạn. Một tab không khóa tab khác.

#### Response và lỗi
- **D-11:** User message lưu ngay trước request. Assistant partial chỉ ở runtime buffer; chỉ commit một assistant message sau khi stream hoàn tất và toàn bộ payload bắt buộc hợp lệ.
- **D-12:** Transport timeout, abort, parser/JSON/tool schema lỗi làm toàn response invalid; không tự sửa payload và không commit phần text hữu ích kèm payload lỗi.
- **D-13:** Lỗi hiển thị bằng error card ngoài chat history, thuộc request/runtime state; diagnostics phải sanitize, không lộ secret hoặc nội dung nhạy cảm.
- **D-14:** Retry dùng lại cùng user message, tạo request ID mới; không nhân bản input, không lưu error message vào history.
- **D-15:** Lỗi một tab chỉ tác động tab đó; tab khác giữ history/loading và tiếp tục hoạt động.

#### SDLC progress và intake
- **D-16:** Progress dùng timeline dọc compact 6 bước, không cuộn ngang/co chữ. Mỗi bước hiển thị completed, processing, stale, not yet hoặc error bằng indicator + text.
- **D-17:** Tách `selectedStep` khỏi `currentProcessingStep`. Click bước chỉ xem artifact/checkpoint và action hợp lệ; không tự nhảy state machine hoặc đổi bước đang xử lý.
- **D-18:** PL01 và PL02 chọn độc lập: nhập text hoặc chọn Note. Một modal search Note toàn hệ thống, mặc định filter Project hiện tại, cho chọn nhiều Note theo từng loại và preview nguồn trước khi bắt đầu.
- **D-19:** Giữ từng Note source ID/version/hash; AI tạo bản hợp nhất có citation và cảnh báo mâu thuẫn. Không sửa Note gốc.
- **D-20:** Có action rõ `Cập nhật yêu cầu` và `Cập nhật solution` tại SDLC header/step. User được brainstorm nhiều vòng đến khi chốt revision.
- **D-21:** Revision phải preview diff, nguồn, impact toàn chain và bước stale; chỉ commit sau xác nhận user, không tự ghi đè artifact.

#### SDLC state machine và revision
- **D-22:** Requirement revision giữ Intake completed và làm stale theo dependency từ `SOLUTION` đến `CAB`.
- **D-23:** Solution revision làm stale `CODE_GUIDE`, `CHANGE_PACK`, `TECH_DOCS` và `CAB`; PL01/PL02 giữ completed.
- **D-24:** Artifact dùng immutable versions + active pointer. Artifact cũ không bị xóa hoặc ghi đè.
- **D-25:** Artifact stale chỉ read-only để audit/so sánh; không dùng làm baseline cho bước mới.

- **D-28:** Restart/đóng drawer phục hồi từ DB. Cài lại phục hồi qua encrypted GitHub backup hiện có hoặc local import; không thêm sync/backend riêng.

- **D-32:** Refactor chỉ tách runtime theo tab ở lớp ngoài core: loading, streaming buffer, request/abort, error/retry, config và commit boundary. Các core hiện có tiếp tục xử lý retrieval, MCP/tools, provider transport, compaction và token usage.

## Summary

Phase 25 shipped a working single-thread SDLC workflow plus a project-scope tab bar, but the runtime is **not** tab-isolated: one set of streaming/abort/error/wizard state serves every tab, the tab list lives in `localStorage`, SDLC workflow state is never persisted, closing the drawer aborts every in-flight request, and abort commits a partial assistant message into history. Each contradicts a locked decision (D-05/D-06/D-07/D-09/D-11/D-12/D-15/D-28).

Work is a **refactor of an existing 2,585-line component plus additive DB/backup changes**, not greenfield. AI engine reused untouched (D-31/D-33): `runGroundedTurn` and `runAiOrchestratorLoop` stay as-is; only the state container around them changes. `runWizardStage`, `workflowCoordinator`, `artifactRepo`, `stalenessDetector` are the SDLC substrate to extend.

Two structural gaps need new model surface, not just refactoring:
1. **Revision cycles.** `SdlcWorkflowStateSchema` is single-cycle, single-version (`artifacts` holds one ref per kind). D-24..D-27 require version history + active pointer + multiple cycles.
2. **Persisted tab/checkpoint records.** `ChatThread` has no tab metadata; backup carries threads but no active-tab-per-scope and no checkpoint/interrupted flag. D-29 requires both.

**Primary recommendation:** Extract a per-tab runtime registry (`Map<tabId, TabRuntime>`) and request registry from `AIChatDrawer.tsx` into a hook/module; persist tabs + active-tab + workflow checkpoint in Dexie (new `chatTabs` table at schema v14; checkpoint inside the workflow state record already covered by backup); extend `SdlcWorkflowStateSchema` additively with `cycles[]` and per-kind `versions[]` + `activeVersion` before touching UI.

### Pattern 1: Per-tab runtime registry
**What:** One `Map<tabId, TabRuntime>` in a hook. Each entry owns its own `AbortController`, streaming buffer, status, error, retry text, wizard refs.
**When to use:** Every read/write of transient chat state. No component may read a bare `isStreaming`.
**Example (shape derived from current fields at AIChatDrawer.tsx:568-569, 242, 398):**
```ts
interface TabRuntime {
  tabId: string;
  threadId: string;
  status: 'idle' | 'streaming' | 'loading' | 'error' | 'interrupted';
  controller: AbortController | null;
  streamingText: string;
  streamingStatus: string | null;
  error: { message: string; requestId: string } | null;
  draft: string;
  attachments: File[];
  analysisMode: boolean;       // SDLC tab forced true (D-33)
  lastSubmittedText: string;   // for retry (D-14)
  wizardSnapshot: WizardSnapshot | null;
}
```
Keep the map in a `useRef` for the imperative request path; mirror only *status* into `useState` for rendering, so background tabs re-render badges without re-rendering the drawer. Do not store the map in IndexedDB.

### Pattern 2: Request registry with stale-response guard
**What:** `requestId` per send/retry; registry records `{tabId, controller, startedAt}`. Commit path asserts `registry.current.get(requestId)?.controller === controller && !controller.signal.aborted` before writing.
**When to use:** Every `saveMessage` of an assistant turn; every wizard snapshot commit.
**Why:** D-14 needs a new request ID per retry; Claude's Discretion requires stale responses not overwrite newer state and double-submit blocked. Today `lastSubmittedText` (line 569) plus a single `currentTurnAbortRef` (line 242) cannot distinguish two tabs.

### Pattern 3: Immutable artifact versions + active pointer
**What:** Artifact lives as a `Note` with `sdlcArtifact` metadata (already true in `artifactRepo.commitArtifact`); version computed per thread. Add pointer record `{kind, activeVersion, activeNoteId}` in workflow state; history via `loadCanonicalArtifactChain`.
**When to use:** Every artifact commit and baseline read. Baseline reads ONLY the active pointer Note.
**Anti-pattern:** mutating an existing Note body to "update" an artifact. D-24 forbids; `artifactRepo` already creates new Notes — keep it, add the pointer.

### Pattern 4: Revision cycle record
**What:** `cycles: RevisionCycle[]` in workflow state; each has `cycleId`, `startedAt`, `closedAt?`, `status`, per-step artifact refs. Current cycle = `closedAt` undefined.
**When to use:** CAB approval closes a cycle (D-26); "Cập nhật yêu cầu"/"Cập nhật solution" start revision inside current cycle (D-20/D-22/D-23); post-approval change opens new cycle in same thread.
**Persistence:** workflow state must be written to Dexie via `saveState` (currently not wired — gap G1).

### Pattern 5: Checkpoint / interrupted
**What:** Before process exit, write `{tabId, requestId, step, status:'running', startedAt}` into workflow/tab state. On mount, any `status:'running'` record is rewritten to `interrupted` and surfaced as resumable/retryable.
**When to use:** `pagehide` + Tauri `onCloseRequested` (existing hooks: `src/hooks/useLocalSqlitePersistence.ts`, `src/services/localSqlitePersistence.ts` queue flush). D-09 does **not** allow aborting on drawer close.

### Pattern 6: Vertical timeline with selected/current split
**What:** `SdlcWorkflowHub` renders a vertical `Timeline` (or stacked list with left rail). `selectedStep` is local UI state; `currentProcessingStep` comes from workflow state. Click sets `selectedStep` only.
**When to use:** Always. D-16 forbids horizontal scroll (current: `overflowX:'auto'`, `whiteSpace:'nowrap'` at SdlcWorkflowHub.tsx:182-185); D-17 forbids click-driven transitions (current `onNavigateStep` → `coordinator.navigateToStep` mutates `currentStep`).

### Anti-Patterns to Avoid
- **localStorage as tab/analysis-mode source of truth.** Current: lines 437, 486, 497, 524, 550 (tabs), 983-1002 (analysis modes). D-07 violation. Width (174-192) may stay — pure presentation.
- **Single shared streaming bubble.** `ChatMessageList` temp streaming message is one shared object; two tabs streaming would swap text. Render streaming bubble from active tab's registry entry only.
- **Committing on abort.** Lines 1943-1970 save `cleanPartial + ' [Đã dừng]'`. D-11/D-12 forbid.
- **Aborting on drawer close.** Lines 1041-1056 abort both controllers when `open` becomes false. D-09 forbids.
- **Legacy SDLC thread fallback.** `getOrCreateSdlcThread` returns `project:${projectId}` thread if present (chatRepo.ts:203-206), silently merging default chat and SDLC identities.
- **`navigateToStep` from UI click.** Replace with `selectStep` (local) + explicit allowed actions.

## Common Pitfalls

### Pitfall 1: Shared AbortController kills the wrong tab
**What goes wrong:** Keeping `abortControllerRef`/`currentTurnAbortRef` in the component and reusing across tabs means switching tabs or sending in tab B aborts tab A.
**Why:** single `currentTurnAbortRef` (line 242) + scope-change effect aborts it (lines 1059-1068).
**How to avoid:** controller lives in runtime registry keyed by tabId; only owning tab aborts it.
**Warning signs:** test sends in tab A, switches to tab B, asserts tab A still streaming.

### Pitfall 2: `useLiveQuery` keyed wrong after tab split
**What goes wrong:** `thread` query falls back to `scopeKey` for non-project scopes (lines 408-413). Once all scopes get tabs, fallback returns the *first* thread, possibly not the active tab's.
**How to avoid:** resolve `activeTab.threadId` for every scope; scopeKey fallback only as migration path.
**Warning signs:** two chat tabs in a task scope show same history.

### Pitfall 3: Migration ordering breaks existing SDLC users
**What goes wrong:** misclassifying the legacy `project:<id>` thread as SDLC loses default chat history or yields empty SDLC tab.
**How to avoid:** `getOrCreateSdlcThread` already prefers `project:<id>:sdlc`; migration promotes `project:<id>` to first *chat* tab. Never delete the legacy thread.
**Warning signs:** user reports chat history gone; SDLC tab shows chat messages.

### Pitfall 4: Abort path re-introduced during refactor
**What goes wrong:** moving the ~900-line `handleSendMessage` (1084-1983), the catch block's abort-commit is easy to copy.
**How to avoid:** one `commitValidatedTurn(...)` on success only; abort/error paths call `discardBuffer(...)`.
**Warning signs:** grep for `[Đã dừng]` must return zero hits after the phase.

### Pitfall 5: Workflow state lost on drawer close
**What goes wrong:** `wizardCoordinatorRef.current?.dispose()` runs on close (line 913); workflow state only in React state.
**How to avoid:** `saveState` on every emit (coordinator already supports) + `loadState` on mount; `dispose` must not clear persisted state.
**Warning signs:** close drawer, reopen, hub shows step 1.

### Pitfall 6: Backup schema bump breaks old backups
**What goes wrong:** `exportBackup` writes `CURRENT_SCHEMA_VERSION = 10`; required tab fields at a higher version make old backups fail validation.
**How to avoid:** new fields optional in Zod, backfill on import (existing schemaVersion-1 backfill pattern in `validateBackup.ts`), keep old payloads valid.
**Warning signs:** `tests/backup/*.test.ts` fixtures with `schemaVersion: 10` fail.

### Pitfall 7: Prompt leakage across tabs
**What goes wrong:** SDLC prompt appended into a shared system prompt means normal tabs inherit `[SDLC DEVELOPER WORKFLOW ACTIVE]`.
**How to avoid:** prompt assembled inside SDLC wrapper and passed as argument to `runAiOrchestratorLoop`; never mutate module-level prompt.
**Warning signs:** unit test asserts normal-tab system prompt contains no SDLC marker.

### Pitfall 8: Stale artifacts used as baseline
**What goes wrong:** `loadCanonicalArtifactChain` returns newest notes; stale version could be read as current after a revision.
**How to avoid:** baseline reads go through active pointer only; stale versions readable but read-only (D-25).
**Warning signs:** revision test asserts new step consumes new version.

### Pitfall 9: Double-submit during retry
**What goes wrong:** D-14 retry reuses the same user message; double-click sends twice.
**How to avoid:** registry rejects a second active request for same tabId.
**Warning signs:** test fires two retries, asserts one request.
