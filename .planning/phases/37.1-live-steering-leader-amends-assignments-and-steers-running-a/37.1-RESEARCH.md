## Summary

Phase 37 shipped a ledger-driven, scheduler-bounded batch runner. Every seam 37.1 needs already exists; nothing needs a new dependency, a new table, or a schema version bump.

Three facts dominate the design:

1. **The lead's `ChatTurnRuntime` is occupied for the entire batch.** `delegate_batch` is executed inside the lead's own tool loop (`makeExecuteToolFn` → `runBatch`, `teamRunCoordinator.ts:726-730`), and `runBatch` awaits `Promise.allSettled(started)` plus every agent deferred (`:1583-1588`). So while a batch runs, `registry.get(lead.id).start()` would throw `TURN_IN_PROGRESS` (`chatTurnRuntime.ts:216`). A mid-batch leader re-plan therefore needs its **own** lead runtime (a "steer turn"), not a call into the busy one. This is the single most consequential finding in this research.
2. **`beforeToolRound` cannot mutate the message list today.** It is `(round, signal) => Promise<void>` (`aiOrchestratorLoop.ts:96`) and fires only when `loopCount > 1` (`:224`). Draining an inbox requires the loop to append messages, so the hook's contract must change (return messages to append) and the round-1 skip must go.
3. **`liveBubbles` is currently the only per-agent Stop control.** `AgentStatusRow` renders only on persisted `report` rows (`ChatMessageBubble.tsx:1204-1222`), and a queued/running agent has no report row yet. Deleting `liveBubbles` (D-19) without re-homing Stop into the D-22 popover silently removes per-agent stop.

**Primary recommendation:** implement steering as a coordinator-owned pipeline — persist the steer row immediately, route by `@mention` into a persisted per-attempt inbox (`steerMessageIds` on the assignment row) plus a derived leader queue, drain into the agent's loop through a return-value `beforeToolRound` hook fired on every round, and run the leader's mid-batch re-plan on the **shared serialized lead runtime** (`runLeadTurnSerialized`) whose only mutation tools are `deliver_steer` and `amend_assignments`. No new Dexie version. **(Superseded by D-24: the original recommendation was a second, dedicated lead runtime; the user chose event-driven `delegate_batch` instead, which frees the single runtime.)**

### Pattern 1: Route inside `send()`, not beside it

**What:** Keep one entry point. `send()` decides idle-turn vs steer from the phase it already owns.
**When to use:** Always — D-01 forbids a second submit path, and `TeamWorkspace` already funnels every dispatch through `runTurn`.

```ts
// teamRunCoordinator.ts — current shape at :1240-1281
async function send(text: string): Promise<SendOutcome> {
  if (disposed) return 'blocked';                       // D-12
  if (BUSY_PHASES.has(phase)) return steer(text);        // NEW: was `return 'busy'`
  // … unchanged idle path …
}

type SendOutcome = 'started' | 'steered' | 'refused' | 'blocked';
```

`'steered'` means: the user row is persisted and the message is in an inbox. `'refused'` means: the mentioned agent is terminal (criterion 4) — the leader must say so. `'blocked'` keeps the D-12 behaviour (draft restored).

### Anti-Patterns to Avoid

- **Starting a second lead turn on the existing runtime.** `chatTurnRuntime.start()` throws `TURN_IN_PROGRESS` (`:216`) and the lead is parked inside `delegate_batch`. Use a dedicated runtime.
- **Calling `scheduler.cancel(handle)` to cancel a queued assignment.** No handle exists before admission (`scheduler.ts:32-37`); abort the assignment's own `AbortController`.
- **Writing `runStatus` with `db.aiTeamAssignments.update()`.** D-09/37-D-09: `transitionAssignment` is the only writer.
- **Letting the steer turn advertise `delegate_batch`.** It would open a second concurrent batch and overwrite `openBatchId` (see Pitfall 2).
- **Wrapping steer text in `wrapUntrusted`.** Steer text is the *user's own instruction*, not retrieved data; wrapping it would tell the agent to ignore it.
- **Filtering the whole `liveBubbles` block without re-homing Stop.** See Pitfall 8.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cancelling a queued assignment | A new cancel path / scheduler handle | `assignmentControllers.get(id)?.abort()` + `finalizeAttempt(...,'queued','stopped',…)` | Already proven by `stopAgent` and `abortAll`; a second path re-opens the "two report rows" race |

## Common Pitfalls

### Pitfall 1: The lead's runtime is busy for the whole batch
**What goes wrong:** the steer path calls `registry.get(lead.id).start(...)` and throws `TURN_IN_PROGRESS`, surfacing as a generic error and losing the message.
**Why it happens:** `delegate_batch` executes inside the lead's own tool loop (`makeExecuteToolFn` → `runBatch`, `:726-730`) and `runBatch` awaits the whole batch (`:1583-1588`).
**How to avoid:** chain every lead turn through `runLeadTurnSerialized` (D-24) so the dispatch, steer and synthesis turns never overlap on one runtime. A second dedicated runtime is NOT the answer — D-24 rejected it.
**Warning signs:** `TURN_IN_PROGRESS` in logs; a steer row that stays "chờ leader đọc" forever.

### Pitfall 2: A second batch opened by the steer turn
**What goes wrong:** the steer turn advertises `delegate_batch` (it uses `leadTools()`), the leader calls it, `runBatch` opens a second batch and overwrites `openBatchId`, and the first batch is never closed (`closeBatch` is keyed by id, but `abortAll`/`dispose` only close `openBatchId`).
**Why it happens:** `leadTools()` (`:694-706`) unconditionally includes `TEAM_TOOL_DEFINITIONS`; `runBatch` has no "a batch is already live" guard.
**How to avoid:** (a) give the steer turn its own tool list = reads + `amend_assignments` only; **and** (b) add a guard at the top of `runBatch`: `if (openBatchId !== null) return ALREADY_RUNNING_REFUSAL;`. Both — the prompt can be ignored, the guard cannot.
**Warning signs:** two `aiTeamBatches` rows with `endedAt === undefined`; `abortAll` leaving a batch open.

### Pitfall 3: Two lead turns corrupt the usage baseline
**What goes wrong:** `startLeadTurn` does `usageTotals.delete(lead.id)` (`:1195`) before starting. A concurrent steer turn on the same key resets the delta baseline, so `handleUsage` computes a negative/zero delta and member usage under-reports.
**Why it happens:** `usageTotals` is keyed by `agentId` only (`:441`).
**How to avoid:** give the steer turn a distinct accounting key (e.g. `lead.id + ':steer'`) and route its `onUsage` through `handleUsage(accountingKey, usage)`; the member/budget maps stay keyed by the real `agentId`.
**Warning signs:** `memberUsed` stops growing during steers; Phase 38's numbers will be wrong.

### Pitfall 4: Cancel transitions the row but the dispatch still starts the turn
**What goes wrong:** `transitionAssignment(queued→stopped)` succeeds; the dispatch task is still parked in `scheduler.acquire`; when a slot frees it calls `startEmployeeTurn`, which runs `transitionAssignment(queued→running)` (returns `null`, ignored), the agent burns tokens, and its report row is deleted by the settled-check in `saveMessage`.
**Why it happens:** `dispatchAssignment` only checks `disposed` after `acquire` (`:1315`).
**How to avoid:** abort the assignment's controller **before** (or atomically with) the transition — exactly what `stopAgent`/`abortAll` do. Add the same `disposed`-style re-read after `acquire`: `if ((await getAssignment(assignmentId, db))?.runStatus !== 'queued') throw new DOMException('Aborted','AbortError');`
**Warning signs:** a cancelled agent's model appears in the debug prompt log; token usage rises for a cancelled row.

### Pitfall 5: Rewritten assignment is invisible to `runBatch`'s completion wait
**What goes wrong:** the replacement row is dispatched outside `runBatch`'s `started` array. `Promise.allSettled(started)` can resolve first; `Promise.all(agentDeferreds.values())` only sees deferreds that already exist, so a replacement still parked in `scheduler.acquire` is not awaited. The lead synthesizes before the rewritten task runs, and `collectBatchReports`/`results` may report a stale status.
**Why it happens:** `runBatch`'s completion is promise-based, not ledger-based — even though 37-D-08 says the scheduler reads the ledger as truth.
**How to avoid:** after the deferred wait, loop on the ledger: `while ((await listBatchAssignments(batch.id, db)).some(r => r.runStatus === 'queued' || r.runStatus === 'running')) await sleep(25);` with an abort/dispose check. Cheap, and it also covers `retryAssignment`-style late appends.
**Warning signs:** the synthesis names the old task; `getRunningCount() > 0` when `lead-synthesizing` starts.

### Pitfall 6: A skipped/rewritten attempt looks like an interrupted turn forever
**What goes wrong:** `listInterruptedAssignments` (`teamTranscriptRepo.ts:288-310`) flags any `instruction` row whose `targetAgentId` has no later `report`. The retired row's instruction (old task) has none, so the workspace shows "Lượt trước bị gián đoạn" on every mount.
**Why it happens:** the inference is transcript-only by design.
**How to avoid:** route the retirement through `finalizeAttempt` (which inserts a sanitized report row) — this is why the `to: 'skipped'` widening is the recommended path rather than a bare `transitionAssignment`.
**Warning signs:** the interrupted banner appears after a clean amend.

### Pitfall 7: The steer gets compacted away before the model sees it
**What goes wrong:** the hook runs at `:224`, in-loop compaction at `:234`. A steer appended by the hook can be summarized into the compaction output in the same round.
**Why it happens:** ordering in the loop body.
**How to avoid:** move the hook call **after** the compaction block, so the injected message is always in the payload for that round. Note this in the plan — it is a one-line move but changes the D-21 test's expectations about what precedes what.
**Warning signs:** an agent acts on a steer one round late or not at all under a large context.

### Pitfall 8: Removing `liveBubbles` deletes the only per-agent Stop
**What goes wrong:** D-19 removes `liveBubbles`; `AgentStatusRow` only renders for persisted `report` rows (`ChatMessageBubble.tsx:1204-1222`), and `WR-01` explicitly suppresses it for `instruction` rows. A queued/running agent therefore has **no** Stop button anywhere.
**Why it happens:** the live bubble was the only carrier of `agentStatus` for non-terminal agents.
**How to avoid:** re-home Stop into the D-22 indicator popover (per-agent row: name, phase text, Stop) and/or the `TeamSidebar` (which already receives `snapshot` and maps `statusByAgent`, `TeamSidebar.tsx:51`). D-23's hover rule then applies to the popover row and to `AgentStatusRow` on settled rows.
**Warning signs:** a batch that can only be stopped globally.

### Pitfall 9: Steer rows leak into every agent's prompt
**What goes wrong:** `listRecentTurns` is thread-wide (`teamTranscriptRepo.ts:240-246`) and feeds every agent's `history`. A steer addressed to agent A therefore appears in agent B's next prompt, violating D-17.
**Why it happens:** `buildEmployeeTurnRequest` filters `assignmentHistory` by agent but appends `recentTurns` unfiltered (`teamPrompts.ts:130`).
**How to avoid:** filter `messageKind === 'steer'` out of `recentTurns` in `buildEmployeeTurnRequest` unless `targetAgentId === employee.id` (or the row has no target and the employee is the lead). Add a `teamPrompts` test.
**Warning signs:** agent B answers a question only agent A was asked.

### Pitfall 10: The steer turn leaves an active turn / writes after dispose
**What goes wrong:** criterion 5 fails — a steer turn started just before `dispose()` keeps writing a `plan` row after the team is deleted.
**Why it happens:** `dispose()` only clears `registry` (`:2029`) and aborts `assignmentControllers`; a steer runtime outside those collections is invisible to it.
**How to avoid:** own the steer runtime in the coordinator, abort it in `dispose()`/`abortAll()`, check `disposed` after every await (the established pattern, `:1257`, `:1378`, `:1431`), and finish any registered turn in `finally`.
**Warning signs:** `getActiveTurns()` non-empty after teardown; a `chatMessages` row with `createdAt >= deletedAt`.

### Pitfall 11: `FORBIDDEN_BACKUP_KEYS` rejects the new field name
**What goes wrong:** a field named e.g. `steerError`, `steerPrompt`, `steerDiagnostic`, `steerPartial` fails the recursive key gate (`backupSchemas.ts:194-219`) and the app's own export becomes unrestorable.
**Why it happens:** the regex bans `(^|_)(api_key|…|prompt|partial|raw.*response|stack|diagnostic|error)(_|$)` case-insensitively.
**How to avoid:** `steerMessageIds` (verified against the regex: no banned token), `steerDeliveredAt` if needed. Never `steerError` — use `steerRefusalReason` if a reason is ever needed.
**Warning signs:** `validateBackupPayload(exportBackupPayload(db)).valid === false` in `officeBackup.test.ts`.

### Drain hook (coordinator side)

```ts
// teamRunCoordinator.ts — replaces beforeToolRoundFor (:960-968)
function beforeToolRoundFor(agentId: string, attempt?: AttemptRef) {
  return async (round: number, signal: AbortSignal): Promise<ChatCompletionMessage[] | void> => {
    await gateFor(agentId).wait(signal);
    await teamGate.wait(signal);
    signal.throwIfAborted();
    return drainSteerInbox(agentId, attempt);   // returns [] when nothing is pending
  };
}

async function drainSteerInbox(
  agentId: string,
  attempt?: AttemptRef
): Promise<ChatCompletionMessage[]> {
  if (!attempt) return [];
  const row = await getAssignment(attempt.assignmentId, db);
  const pending = row?.steerMessageIds ?? [];
  if (pending.length === 0) return [];
  const messages = await db.chatMessages.bulkGet(pending);
  // clear FIRST so a second drain cannot re-inject the same text
  await db.aiTeamAssignments.update(attempt.assignmentId, { steerMessageIds: [] });
  return messages
    .filter((m): m is NonNullable<typeof m> => Boolean(m))
    .map((m) => ({ role: 'user' as const, content: `[Chỉ đạo từ người dùng] ${m.content}` }));
}
```

Note the `db.aiTeamAssignments.update` here is a **non-status** field write, so it does not violate D-09 (the same exemption 37 already uses for `reportMessageId` and `instructionMessageId`, `:798-800`, `:1072-1074`).

```ts
    if (!assignment || !['queued', 'running'].includes(assignment.runStatus)) {

    }

      });
    }
    // queued: nothing to inject yet — the row is drained at round 1 of its turn
  }
  void runLeadSteerTurn();         // D-04/D-16: the leader reads and re-plans
  return 'steered';
}
```
