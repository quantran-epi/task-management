## Critical Issues

### CR-01: A steer sent before the batch opens is delivered but its badge stays "chưa giao" forever

**File:** `src/components/ai/office/TeamWorkspace.tsx:373-417`, `src/services/ai/office/teamRunCoordinator.ts:1442` and `:1693-1705`
**Issue:** The workspace derives delivery state from assignments found by the **steer row's**
`batchId`:

```ts
// TeamWorkspace.tsx:373-386
for (const row of messages) {
  if (row.messageKind === 'steer' && row.batchId !== undefined) ids.add(row.batchId);
}
const steerAssignments = useLiveQuery(... where('batchId').anyOf(steerBatchIds) ...)
```

but `steer()` stamps `batchId` only when a batch is already open (`teamRunCoordinator.ts:1442`:
`...(openBatchId !== null ? { batchId: openBatchId } : {})`). A steer sent during `awaiting-plan`
(or `lead-thinking`) is therefore persisted with **no** `batchId`, while `deliverSteer` accepts it
later, once the plan is approved and the batch is open (`:1693-1705` only requires
`assignment.batchId === openBatchId`).

That is the headline flow: the plan card is on screen, the user types
`@[An](agent:<id>) làm thêm X`, the plan is approved, the leader's steer turn calls `deliver_steer`
and gets `{delivered: true}`. The steer row still has no `batchId`, so
`steerAssignments` never contains the assignment, `deliveredSteerIds` never contains the id, and
`assignmentByAgent` is empty — the terminal-attempt escape hatch at `:412-413` cannot fire either.
`steerStates` therefore sets `'held'` and the bubble renders **"chưa giao" permanently**, including
after relaunch (the query is identical). This is the same D-03/D-14 violation CR-04 was raised for,
narrowed to steers persisted before the batch row exists.

Secondary case in the same derivation: a steer whose target agent has no assignment in the queried
batches at all (`:412` → `undefined`) also never clears its badge.
**Fix:** make the delivery write stamp the batch onto the steer row, which is the one place the
batch is known:

```ts
// deliverSteer, inside the same rw transaction as the array append
await db.chatMessages.update(steerMessageId, { batchId: assignment.batchId });
```

and defensively treat "no assignment found for the target in any batch of this thread" as delivered
rather than held:

```ts
const assignment = assignmentByAgent.get(row.targetAgentId);
if (assignment !== undefined && TERMINAL.has(assignment.runStatus)) continue;
if (assignment === undefined && !pending.has(row.id)) continue; // nothing to deliver to
```

Add a `TeamWorkspace`-level test: steer during `awaiting-plan`, approve, deliver, assert no
`steer-badge-<id>`.

## Warnings

### WR-01: The steer turn injects every pending steer twice

**File:** `src/services/ai/office/teamRunCoordinator.ts:1577-1581`, `:1610`, `:1643-1649`
**Issue:** CR-01's fix moved the `pendingSteerMessageIds` delete to *after* `start()` resolves. But
`loadPendingSteers()` still puts the same rows into the system prompt as
`[CHỈ ĐẠO CHỜ XỬ LÝ]` (`teamPrompts.ts:223-234`), and `beforeToolRound` fires at round 1
(`aiOrchestratorLoop.ts:259-263`), where `drainLeaderSteerQueue()` still sees the ids (not yet
deleted) and appends them again as `[Chỉ đạo từ người dùng] …` user messages. Before the fix the
delete happened before the prompt was built, so round 1 found an empty set. The leader now receives
the same instruction twice in one turn — duplicate tokens and a real risk of double-applying an
amend.
**Fix:** exclude the ids already rendered in the system prompt from this turn's drain, e.g. record
them as injected for the lead before `start()`:
```ts
for (const steer of pendingSteers) leaderInjectedThisTurn.add(steer.id);
```
and have `drainLeaderSteerQueue()` skip ids in that set for the duration of the turn, or simply
delete the ids from `pendingSteerMessageIds` before building the prompt and re-add them if the turn
fails (the CR-01 guarantee is about *not losing* them, not about the exact delete point).

### WR-02: The steer-turn rollback clobbers the running lead turn's turn registration

**File:** `src/services/ai/office/teamRunCoordinator.ts:1632`, `:1652-1662`
**Issue:** On the `TURN_IN_PROGRESS` path the rollback restores the accounting key, live-use claim
and status, but:
- `registerAgentTurn(lead.id, …)` at `:1632` already overwrote the running turn's
  `aiTurnManager` entry (same id `team:<teamId>:agent:<leadId>`), and the rollback calls
  `aiTurnManager.finishTurn(agentTurnId(lead.id))` with the default `'complete'`, which purges that
  entry after 800 ms. `ActiveAiTurnIndicator` loses the lead for the rest of the real turn.
- `updateAgent(lead.id, { status: priorLeadStatus })` restores only `status`; the steer turn already
  reset `streamingText: ''`, `steps: []` and `startedAt` (`:1626-1631`), so the running turn's live
  steps are wiped.

The path is currently unreachable — every lead turn now goes through `runLeadTurnSerialized`, so a
steer turn cannot start while the lead runtime is live — which makes this untested dead defensive
code that would corrupt the indicator the moment a lead turn is started outside the chain.
**Fix:** capture and restore the full prior state, and do not touch the turn manager on rollback:
```ts
const prior = agents.get(lead.id);
...
} else if (!started) {
  if (priorAccountingKey !== undefined) usageBaselineKey.set(lead.id, priorAccountingKey);
  if (!alreadyLive) releaseLiveUse(lead.id);
  if (prior) agents.set(lead.id, prior); else agents.delete(lead.id);
  // no finishTurn: this turn never registered a turn of its own
}
```
and move `registerAgentTurn` after `start()` has been accepted, or drop the rollback entirely if the
serialization makes it dead.

### WR-03: `amend_assignments` refuses a `cancel` for undrained steers, with a rewrite-only message and the wrong code

**File:** `src/services/ai/office/teamRunCoordinator.ts:1788-1795`
**Issue:** The CR-03 guard runs for **every** operation, so `{op: 'cancel'}` on a queued row that
holds a delivered steer is refused with "Hãy để nhân viên nhận chỉ đạo trước khi **sửa việc**" and
`code: 'NOT_QUEUED'`. Two problems: the copy describes a rewrite the leader did not ask for, and the
code tells the model the row is not queued when it is — the exact self-correction trap WR-08 fixed
for the argument-shape failures. The model's natural retry is to re-send the same cancel against
another id.
**Fix:** scope the guard to `operation.op === 'rewrite_task'` (a cancel cannot lose a steer that was
never injected — the row is terminal and the badge derivation already suppresses it), and use a code
that names the real condition (add e.g. `STEER_PENDING` to `TeamToolRefusalCode`) for the rewrite
case.

### WR-04: A rewrite can lose the `queued → skipped` race and start two turns for one agent

**File:** `src/services/ai/office/teamRunCoordinator.ts:1848-1873`
**Issue:** Pre-validation proves the row is `queued`, but the apply loop then `await`s
`createAssignment` (`:1848`) before aborting the retired controller and finalizing. During that
await a parked `dispatchAssignment` can acquire a free scheduler slot and call
`startEmployeeTurn`, which transitions the row `queued → running` (`:1239-1245`). The abort at
`:1869` cannot stop a turn that already started (the controller only rejects `scheduler.acquire`),
and `finalizeAttempt(row.id, 'queued', 'skipped', …)` then loses the `from` guard and returns
`null`. The replacement is dispatched anyway, hits `TURN_IN_PROGRESS` on the shared per-agent
runtime, and errors — while the leader has already been told `{applied: [{op:'rewrite_task',
replacementId}]}`.
**Fix:** abort the retired controller **before** `createAssignment`, and re-read the row's status
right before the finalize:
```ts
assignmentControllers.get(row.id)?.abort();
const live = await getAssignment(row.id, db);
if (live?.runStatus !== 'queued') return /* NOT_QUEUED, whole list refused before any mutation */;
```
(do the re-read for the whole list before the apply loop so the all-or-nothing contract still holds).

### WR-05: The bounded settle poll closes the batch while rows are still live

**File:** `src/services/ai/office/teamRunCoordinator.ts:2306-2313`, `:2319-2368`
**Issue:** WR-09's deadline `break` falls through to the synthesis path: `openBatchId` is cleared
(`:2367`), the batch is closed `abortedBy: 'none'`, and the results are built from
`agents.get(...)` — so a still-`running` agent is reported to the synthesis as
`[Chưa hoàn tất — running/none]`. Worse, with `openBatchId === null` a subsequent `send()` opens a
**second** batch for the same team, overwriting `assignmentIdsByAgent`; the first batch's agent then
finishes with its settle suppressed by the WR-04 identity guard, leaving a phantom `running` entry
in `agents` (and a permanent "đang làm việc" line) until `abortAll`.
**Fix:** on deadline expiry, mark the stuck rows rather than pretending the batch settled — abort
their controllers, finalize them `stopped`/`tool-limit` (or a new `budget-pause`-style reason), and
only then synthesize. At minimum keep `openBatchId` set until no row is `queued`/`running`.

## Info

### IN-01: The `steerMessageIds` doc comments describe the old, cleared semantics
**File:** `src/types/aiOffice.ts:220`, `src/validation/backupSchemas.ts:770`
Both still say "steer message ids **not yet drained** into this attempt's prompt". The field is now
the durable delivered marker and is never cleared; a future reader following the comment would
re-derive "undelivered" from it — the exact CR-04 bug. Update both to "delivered to this attempt
(never cleared; D-14/D-25)".

### IN-02: `injectedSteerIdsByAttempt` is never pruned per attempt
**File:** `src/services/ai/office/teamRunCoordinator.ts:561`, `:1495-1504`
One `Set` per attempt id, removed only by `dispose()`. Bounded by the session's steer count, so not
a leak in practice, but a long-lived coordinator keeps every attempt's set forever. Delete the entry
when the attempt finalizes (in `finalizeAttempt`'s unlink block).

### IN-03: `drainSteerInbox`'s `agentId` parameter is unused
**File:** `src/services/ai/office/teamRunCoordinator.ts:1487`, `:2912-2913`
Renamed to `_agentId` but the public seam still requires it. Either drop it from the seam or use it
to assert `row.agentId === agentId` (which would also catch a mismatched assignment id).

### IN-04: A failed turn reports the "could not save changes" copy
**File:** `src/components/ai/office/TeamWorkspace.tsx:486-491`
`ACTION_ERROR_COPY` ("Không lưu được thay đổi…") describes a failed repo write, not a failed turn.
Add a `TURN_FAILED_COPY` alongside `RETRY_ERROR_COPY`.

### IN-05: `steerStates` treats only three statuses as terminal
**File:** `src/components/ai/office/TeamWorkspace.tsx:98`, `:413`
`TERMINAL` is `done|stopped|error`. A `skipped` (rewritten), `blocked` or `needs-input` latest
attempt keeps a badge. Currently unreachable because CR-03 refuses a rewrite while steers exist, but
the set should match `AiTeamAssignmentRunStatus`'s terminal members.

### IN-06: After relaunch an unread steer renders "chưa giao", not "chờ leader đọc"
**File:** `src/components/ai/office/TeamWorkspace.tsx:402`, `:414`
`pendingSteerMessageIds` is live-session only, so a steer the leader never read falls back to
`'held'` on a fresh coordinator — the badge claims the leader read it. Either derive "unread" from
the transcript (no lead turn after the steer row) or accept and document the ceiling.
