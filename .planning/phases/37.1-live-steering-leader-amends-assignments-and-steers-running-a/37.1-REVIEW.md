# Phase 37.1: Code Review Report

**Reviewed:** 2026-11-12T05:20:12Z
**Depth:** standard
**Files Reviewed:** 27
**Status:** issues_found

## Summary

The phase's structural work is sound: `delegate_batch` is now event-driven with a batch-scoped
`AbortController` (D-24), `beforeToolRound` fires on round 1 after compaction (D-09), the
`steer`/`leader-amend` contract is declared in both backup schemas, and the UI drops streaming
bubbles for one inline indicator line (D-19..D-23).

The defects cluster in one place: **the steer lifecycle is not durable and not atomic**. The
pending set is cleared before the leader turn is known to have started, the delivered set is
erased by the drain that consumes it, and both delivery writes are non-transactional
read-modify-write. The result is that a steer can be silently lost (never reaching the leader,
or never reaching the agent) while the UI and the tool results both claim success. The
`amend_assignments` executor has a second cluster: a partial application that reports total
refusal, and a rewrite that discards the old attempt's delivered steers.

Six blockers below. The D-24/D-09/D-17/D-19..D-23 decisions check out.

## Critical Issues

### CR-01: A steer sent while the leader is parked is marked read and then silently dropped

**File:** `src/services/ai/office/teamRunCoordinator.ts:1543-1596` (specifically `:1559` and `:1589-1593`)
**Issue:** `runLeadSteerTurn` removes every pending steer id from `pendingSteerMessageIds`
(line 1559) **before** it calls `registry.get(lead.id).start(request)`. `start()` throws
`TURN_IN_PROGRESS` whenever the lead runtime is already running (`chatTurnRuntime.ts:222`), and
that throw is swallowed by the bare `catch {}` at line 1591.

Two phases in `BUSY_PHASES` guarantee the lead runtime is running when a steer arrives:
`awaiting-plan` (lead parked inside `delegate_batch`'s plan promise) and
`awaiting-mutation-approval` (lead parked inside `onMutationCheck`). In both, `steer()` persists
the row, `runLeadSteerTurn` clears the id from the pending set, `start()` throws, and the error
is discarded. The id is gone from `pendingSteerMessageIds`, so the running lead turn's
`drainLeaderSteerQueue()` at its next round boundary returns `[]` — the leader never sees the
text, the "chờ leader đọc" badge clears, and `steer()` still returned `'steered'`.

This is exactly the D-01/D-02/D-16 promise the phase exists to deliver: "a submit while a turn
is live is a STEER … the leader always reads it".
**Fix:** clear the pending set only after the turn actually started, and leave the ids for the
running turn's drain on `TURN_IN_PROGRESS`:
```ts
let started = false;
try {
  await registry.get(lead.id).start(request);
  started = true;
} catch {
  /* TURN_IN_PROGRESS: the running lead turn's beforeToolRound will drain these instead */
}
if (disposed) return;
if (started) {
  for (const steer of pendingSteers) pendingSteerMessageIds.delete(steer.id);
  notify();
}
```
(Move the `for (const steer of pendingSteers) pendingSteerMessageIds.delete(steer.id)` block from
line 1559 to after `start` resolves.) Add a regression test: send during `awaiting-plan`, then
assert the lead's next round-boundary injection contains the steer text.

### CR-02: `amend_assignments` applies part of the list, then reports a total refusal

**File:** `src/services/ai/office/teamRunCoordinator.ts:1676-1770` (roster check at `:1724-1731`)
**Issue:** The pre-validation loops (`:1676-1696`) check batch membership and `queued` status for
**all** operations before any mutation, which is what the doc comment promises ("the WHOLE list
is refused when any row is not queued, so the leader's report always matches the ledger"). But
the roster check for a `rewrite_task` op lives **inside the apply loop** at `:1724`. A list such
as `[cancel A, rewrite_task B]` where B's agent was de-rostered mid-batch:
1. cancels A through `finalizeAttempt` (row `stopped`, `stopReason: 'leader-amend'`, a report
   bubble inserted, agent settled),
2. then returns `{refused: true, code: 'AGENT_NOT_IN_ROSTER'}`.

The leader reports "nothing was cancelled" while the ledger and the transcript show A cancelled.
That is the T-37.1-24 invariant broken in the opposite direction.
**Fix:** hoist the roster check into the pre-validation loop:
```ts
for (const operation of operations) {
  const row = byId.get(operation.assignmentId)!;
  if (row.runStatus !== 'queued') return /* NOT_QUEUED */;
  if (operation.op === 'rewrite_task' &&
      !roster.employees.some((c) => c.id === row.agentId)) {
    return JSON.stringify({ refused: true, code: 'AGENT_NOT_IN_ROSTER', message: 'Nhân viên không còn trong nhóm.' });
  }
}
```
Then the apply loop cannot return early.

### CR-03: Rewriting a queued assignment silently discards steers already delivered to it

**File:** `src/services/ai/office/teamRunCoordinator.ts:1733-1746`
**Issue:** `deliverSteer` writes `steerMessageIds` onto the **queued** assignment row (D-28
explicitly supports this: "a `queued` agent has no turn yet, but its round-1 drain reads this
field"). A later `rewrite_task` creates a replacement row via `createAssignment` and never copies
`steerMessageIds`; the old row is finalized as `skipped`. The replacement's round-1 drain reads
`[]`, so the steer is never injected, yet `deliver_steer` already returned
`{delivered: true}` and the badge is suppressed (the old row still lists the id, so
`deliveredSteerIds` in `TeamWorkspace` still contains it). The user's instruction is lost with
no signal to anyone.

The replacement also does not carry `dependsOn` (`:1733-1745`), same class of omission.
**Fix:** carry the delivery state forward, or refuse the rewrite while steers are undrained:
```ts
const pendingSteers = row.steerMessageIds ?? [];
if (pendingSteers.length > 0) {
  return JSON.stringify({
    refused: true,
    code: 'NOT_QUEUED',
    message: 'Việc này đang có chỉ đạo chưa đọc. Hãy để nhân viên nhận chỉ đạo trước khi sửa việc.',
  });
}
```
Add `...(row.dependsOn !== undefined ? { dependsOn: row.dependsOn } : {})` to the
`createAssignment` input either way.

### CR-04: The "delivered" state is erased by the drain, so every consumed steer renders "chưa giao"

**File:** `src/components/ai/office/TeamWorkspace.tsx:388-404`, `src/services/ai/office/teamRunCoordinator.ts:1475`
**Issue:** `drainSteerInbox` clears the ledger field wholesale
(`await db.aiTeamAssignments.update(attempt.assignmentId, { steerMessageIds: [] })`). The
workspace derives "delivered" from exactly that field:
```ts
for (const row of steerAssignments) for (const id of row.steerMessageIds ?? []) ids.add(id);
```
Once the agent has consumed a steer (the normal, successful path), the id is no longer in any
`steerMessageIds`, `pendingSteerMessageIds` is also empty, so `steerStates.set(row.id, 'held')`
→ the bubble renders the **"chưa giao"** badge forever. Same after any relaunch: the pending set
is live-session only, so every historical steer row renders "chưa giao".

Second case in the same block: `steerStates` maps **every** `messageKind === 'steer'` row,
including the `@`-less ones (`targetAgentId === undefined`). Per D-28 an unaddressed steer needs
no delivery at all, yet it also gets a permanent "chưa giao" badge.

This contradicts D-03 (badge walks pending → held → gone) and D-14 (undelivered is derived, and
must mean *not yet reached the agent*).
**Fix:** give "delivered" a durable marker that survives the drain — e.g. keep the ids on the
assignment and add a `drainedSteerMessageIds` (or record `deliveredAt` per id), or move the
delivered state onto the steer row (`deliveredToAssignmentId`). Minimum viable fix without a
schema change: only render the badge for rows with a `targetAgentId`, and treat "absent from
pending **and** absent from every `steerMessageIds` **and** the assignment is terminal" as
delivered:
```ts
if (row.targetAgentId === undefined) continue;           // unaddressed: no delivery concept
const assignment = assignmentByAgent.get(row.targetAgentId);
const consumed = assignment !== undefined && TERMINAL.has(assignment.runStatus);
if (deliveredSteerIds.has(row.id) || consumed) continue;
```

### CR-05: `deliverSteer` and `drainSteerInbox` are non-transactional read-modify-write on `steerMessageIds`

**File:** `src/services/ai/office/teamRunCoordinator.ts:1624-1630` and `:1467-1475`
**Issue:** Both paths read the array, await, then write the whole array back:
- `deliverSteer`: `getAssignment` → (await) → `update({ steerMessageIds: [...(assignment.steerMessageIds ?? []), id] })`
- `drainSteerInbox`: `getAssignment` → `bulkGet` (await) → `update({ steerMessageIds: [] })`

They run in different async contexts (the leader's tool loop vs. the agent's round boundary) and
can interleave: drain reads `[X]`, deliver reads `[X]`, deliver writes `[X, Y]`, drain writes
`[]` → **Y is lost after `deliver_steer` reported `{delivered: true}`**. The same lost-update
applies to two `deliver_steer` calls that overlap with a drain.

The project rule for this table is explicit: "Writes: wrap multi-table changes in Dexie
transactions" and `transitionAssignment` exists precisely to make status writes race-safe.
**Fix:** do the read-modify-write inside one `rw` transaction (or a `modify` callback):
```ts
await db.transaction('rw', [db.aiTeamAssignments], async () => {
  const live = await db.aiTeamAssignments.get(assignment.id);
  const current = live?.steerMessageIds ?? [];
  if (current.includes(steerMessageId)) return;
  await db.aiTeamAssignments.update(assignment.id, { steerMessageIds: [...current, steerMessageId] });
});
```
and for the drain, remove only the ids it actually injected rather than blanket-clearing.

### CR-06: The steer caption always shows the raw target UUID in production

**File:** `src/components/ai/ChatMessageBubble.tsx:1166-1182`, `src/components/ai/ChatMessageList.tsx:175`
**Issue:** The caption is `'Chỉ đạo → ' + (agent?.name ?? msg.targetAgentId)`. `agent` is
resolved by `ChatMessageList` as `msg.agentId ? agentDirectory?.get(msg.agentId) : undefined` —
and a steer row is deliberately written **without** `agentId` (D-15: "never `agentId`/`agentName`,
which would render an agent bubble"). So in production `agent` is always `undefined` for a steer
row and the label is always `Chỉ đạo → <uuid>`. The component test only passes because it hands
`agent={agent}` in directly (`ChatMessageListAttribution.test.tsx:276`), which the real list never
does.

This violates the project's own IN-08d rule ("never a raw UUID in UI copy") on the phase's
headline surface.
**Fix:** resolve the target from `targetAgentId` in the list:
```ts
const agent = msg.agentId
  ? agentDirectory?.get(msg.agentId)
  : msg.targetAgentId
    ? agentDirectory?.get(msg.targetAgentId)
    : undefined;
```
and add a `ChatMessageList`-level test (not a direct `ChatMessageBubble` render) asserting the
name, not the id.

## Warnings

### WR-01: `retryAssignment` bypasses the lead-turn chain and can lose its synthesis

**File:** `src/services/ai/office/teamRunCoordinator.ts:2462`
**Issue:** Every other lead turn goes through `runLeadTurnSerialized` (`:1814`, `:2251`, `:1547`).
The retry path calls `startLeadTurn(...)` directly. A steer turn does not change the phase, so
the phase can be `ready` while a steer turn is still running; a retry clicked in that window
hits `TURN_IN_PROGRESS` inside `startLeadTurn` → the error escapes `retryAssignment`, the new
attempt's report is already saved and the source report already superseded, but no synthesis runs
and `lastSynthesisMessageId` stays null so the previous synthesis is never superseded. The user
sees `RETRY_ERROR_COPY` on a retry that half-happened.
**Fix:** `await runLeadTurnSerialized(() => startLeadTurn(SYNTHESIS_INSTRUCTION, reports));`

### WR-02: The steer lead turn is invisible and its tokens are never accounted

**File:** `src/services/ai/office/teamRunCoordinator.ts:1543-1596`
**Issue:** `runLeadSteerTurn` deliberately skips everything `startLeadTurn` does around a turn:
no `leadTurnSeq`/`usageBaselineKey` reset, no `usageTotals.delete`, no `claimLiveUse`, no
`updateAgent(lead, 'running')`, no `registerAgentTurn`.
- Usage: `handleUsage` computes `delta = total - usageTotals.get(key)`. The steer turn reuses the
  **dispatch turn's** key (still holding that turn's cumulative total), and its own cumulative
  total restarts near 0, so `delta <= 0` and the whole steer turn returns early at `:1026`. D-13
  says the leader's read of a steer is billed to the leader; it is billed to nobody.
- Visibility: `getState().agents` keeps the lead at `done`, so `TeamActivityIndicator` shows no
  lead activity for the entire steer turn — the user gets no feedback that the leader is reading.
**Fix:** give the steer turn its own accounting key and a live state:
```ts
leadTurnSeq += 1;
const key = `${lead.id}:${leadTurnSeq}`;
usageBaselineKey.set(lead.id, key);
usageTotals.delete(key);
updateAgent(lead.id, { status: 'running', streamingText: '', steps: [] });
try { await registry.get(lead.id).start(request); } finally { /* settle like startLeadTurn */ }
```

### WR-03: `steer()` returns `'blocked'` after the row is already persisted, duplicating the text

**File:** `src/services/ai/office/teamRunCoordinator.ts:1439-1441`
**Issue:** The comment at `:1429` states the invariant — "The persist already happened;
`'blocked'` would duplicate the text in the composer" — and then the code returns `'blocked'`
twelve lines later after the `getAssignment` await. `TeamWorkspace.runTurn` restores the draft on
`'blocked'`, so the user's text is now both a `steer` row in the transcript and back in the
composer; resending writes a second row. D-12's "keep the text" rule is about the *nothing was
written* case.
**Fix:** return `'steered'` (the row exists and the leader will read it) — or, if the intent is
to stop the leader turn, `return 'steered'` without calling `runLeadSteerTurn`.

### WR-04: A rewritten assignment's old parked task can stomp the replacement's live state

**File:** `src/services/ai/office/teamRunCoordinator.ts:1733-1768`, `:1858-1884`
**Issue:** `rewrite_task` never aborts the old assignment's controller. The old
`dispatchAssignment` stays parked in `scheduler.acquire`; when a slot frees it re-reads the ledger
(`:1860`), sees `skipped`, throws `AbortError`, and its catch runs
`settleAgent(employee.id, 'stopped')` (`:1884`) — **after** the replacement has already been
queued (`:1748`) or started (`:1212` sets `running`). `settleAgent` overwrites `queued`/`running`
with `stopped` and `incomplete: true`, and resolves `agentDeferreds.get(employee.id)` — which is
now the **replacement's** deferred, releasing `onBatchSettled`'s `Promise.all` early. If the
stomp lands after the replacement's `updateAgent(running)` and before its turn completes, the
completion's `settleAgent(done)` is blocked by the terminal guard (`:636`), so `reports` never
gets the content and the synthesis reports the agent as unfinished.
**Fix:** make `settleAgent` identity-aware — ignore a settle whose attempt is no longer the
agent's current one:
```ts
const current = assignmentIdsByAgent.get(agentId);
if (attemptId !== undefined && current !== undefined && current !== attemptId) return;
```
and/or abort the old controller in the rewrite path before creating the replacement.

### WR-05: `undeliveredSteerCountByAgent` is dead state with misleading semantics

**File:** `src/services/ai/office/teamRunCoordinator.ts:121`, `:1631-1634`, `:1476`, `:2752`
**Issue:** The field is added to the public `TeamRunSnapshot`, incremented per delivery, and
deleted per drain — but no consumer reads it (`TeamWorkspace` only repeats it in `EMPTY_SNAPSHOT`,
and the only test asserts it is `{}`). It is also not a count: `drainSteerInbox` does
`delete(agentId)`, so two undrained steers collapse to 0 on the first drain. A public, tested,
never-read field invites a future consumer to trust a wrong number.
**Fix:** either remove it from the snapshot until a surface needs it, or make it a real set of
undrained ids and derive the count.

### WR-06: Hover-gated actions are invisible but still focusable and clickable

**File:** `src/components/ai/office/AgentAttributionRow.tsx:141-174`
**Issue:** `actionsVisible` only drives `opacity: 0`. The Stop/retry buttons stay in the tab order
and remain clickable while invisible, so a keyboard user can land on an unlabeled-by-position
control with no visual indication, and a stray click in the empty gap triggers a stop. D-23 asked
for hover-gating, not for hiding interactive controls from sighted keyboard users.
**Fix:** keep opacity for the transition but also gate interaction:
```tsx
<div style={{ ...(actionsVisible ? {} : { pointerEvents: 'none' }) }} aria-hidden={!actionsVisible}>
```
plus `tabIndex={actionsVisible ? 0 : -1}` on the buttons, or reveal on `:focus-within` via CSS
instead of state.

### WR-07: `deliverSteer` does not verify the steer row belongs to this team's thread

**File:** `src/services/ai/office/teamRunCoordinator.ts:1605-1611`
**Issue:** `db.chatMessages.get(steerMessageId)` is a global lookup; the only checks are
`messageKind === 'steer'` and a defined `targetAgentId`. Every other team tool enforces the
cross-team read guard (`getTeamTurn` checks `row.threadId !== threadId`, T-34-07). A
model-supplied id from another thread/team would be injected into this team's agent prompt as
long as the target agent happens to have an assignment in the open batch.
**Fix:** `if (message.threadId !== options.threadId) return refusal;` before the ledger checks.

### WR-08: The amend validator returns the wrong refusal codes

**File:** `src/services/ai/office/teamTools.ts:396-437`
**Issue:** An invalid `op`, a missing `assignmentId`, and a missing `task` all return
`code: 'NOT_QUEUED'` — which tells the model "this assignment is not queued, use a different
one" when the real problem is a malformed argument. An empty operations list returns
`EMPTY_BATCH`, which is the `delegate_batch` code. The model self-corrects on the code, so a
wrong code produces a wrong retry (e.g. re-sending the same malformed op against a different id).
`INVALID_ARGUMENT` already exists in `TeamToolRefusalCode` for exactly this.
**Fix:** use `refuse('INVALID_ARGUMENT', ...)` for all four argument-shape failures.

### WR-09: The settle ledger poll is unbounded and a rewrite can leave it spinning

**File:** `src/services/ai/office/teamRunCoordinator.ts:2181-2185`, `:1751-1768`
**Issue:** `while (!disposed && !batchController?.signal.aborted)` polls every 25 ms and only
exits when no row is `queued`/`running`. The rewrite path guards the dispatch with
`if (controller)` (`:1751`): if the batch controller is gone, the replacement row is created and
never dispatched, so it stays `queued` forever, the poll never exits, `onBatchSettled`'s `finally`
never runs, and `aiTurnManager.finishTurn(teamTurnId)` never fires — the team turn hangs with no
indicator and every later submit is routed as a steer.
**Fix:** treat a missing controller as a hard failure for the rewrite (refuse the op before
mutating), and bound the poll (`const deadline = Date.now() + 120_000`) so a stuck row cannot hang
the team turn forever.

### WR-10: `runTurn` forwards a raw error message into the UI

**File:** `src/components/ai/office/TeamWorkspace.tsx:473-480`
**Issue:** `setSendError({ code: 'TURN_FAILED', message: err.message })`. This is the same channel
the file elsewhere protects with fixed copy (`ACTION_ERROR_COPY`, `RETRY_ERROR_COPY`,
`LEADER_LOCK_FAILED_COPY`) precisely because repo/coordinator messages can embed ids (IN-05).
`retryAssignment` throws messages containing assignment ids
(`retryAssignment: source attempt ${source.id} has no report to supersede`).
**Fix:** `setSendError({ code: 'TURN_FAILED', message: ACTION_ERROR_COPY })`.

## Info

### IN-01: A `skipped` report renders an empty status row
**File:** `src/components/ai/office/AgentAttributionRow.tsx:94-120`
The badge switch has no `skipped` case → `default: return null`, but the component still renders
its wrapper because `status !== 'done'`. An amended (rewritten) attempt's bubble therefore shows
an empty `agent-status-<id>` row. Add `case 'skipped': return <Tag>Đã thay đổi</Tag>;` or return
`null` for it.

### IN-02: `pushStep` only dedupes against the immediately preceding label
**File:** `src/services/ai/office/teamRunCoordinator.ts:622-630`
`đang viết → đang gọi tool X → đang viết` appends a duplicate "đang viết". Harmless at the 6-step
cap, but the popover reads as a log of two writes when there was one. Dedupe against the whole
list, or key steps by `status`.

### IN-03: `deliverSteer` refusals omit `code`
**File:** `src/services/ai/office/teamRunCoordinator.ts:1606-1623`
Both refusals return `{ refused: true, message }`, while every other refusal carries a
`TeamToolRefusalCode`. The model cannot branch on them.

### IN-04: `amendAssignments` fabricates an empty agent id for its validator context
**File:** `src/services/ai/office/teamRunCoordinator.ts:1661-1665`
`toolContext(roster.lead?.id ?? '')` builds a context with `agentId: ''`. The validator ignores
it today; the next handler added to that path would silently read a bogus caller. Pass the lead
id only when it exists, or give the validator a context-free signature.

### IN-05: `handleSubmit` records the retry text before the whitespace check
**File:** `src/components/ai/office/TeamWorkspace.tsx:489-497`
`lastUserTextRef.current = text` runs before `if (!text.trim()) return`, so a whitespace-only
submit replaces the last real request and the widget's retry button would resend whitespace.
Move the assignment after the guard.

### IN-06: Steer content enters the leader's SYSTEM prompt unwrapped
**File:** `src/services/ai/office/teamPrompts.ts:223-234`
`[CHỈ ĐẠO CHỜ XỬ LÝ]` interpolates `steer.content` raw, while `[HIỆN TRẠNG LÔ ĐANG CHẠY]`
(`:207-220`) wraps `row.task` with `wrapUntrusted`. The steer is user-authored (not retrieved
data) so this is defensible, but it is the one place user text is promoted into the system
message. Either wrap it as `wrapUntrusted('CHỈ ĐẠO', steer.content)` for consistency, or add a
comment stating why user text is trusted here.
