# Phase 37.1 Plan 04: Live steer routing and the leader gate Summary

A submit during a running batch is now persisted as a `steer` row and answered by a serialized leader re-plan turn; a mentioned agent receives it exactly once, and only after the leader calls `deliver_steer`.

## What Was Built

**Task 1 — `send()` routes into `steer()` (commit `9a0aa82f`)**

- `TeamRunCoordinator.send` returns `'started' | 'steered' | 'refused' | 'blocked'`. `BUSY_PHASES` is kept and exported but is now an internal route discriminator: `if (BUSY_PHASES.has(phase)) return steer(text);`. No `return 'busy'` remains anywhere in `src/`.
- `steer()` persists the row unconditionally as `role: 'user'`, `messageKind: 'steer'`, with `targetAgentId` when mentioned and `batchId` when a batch is open — never `agentId`/`agentName`, so it renders as a user bubble (D-15). It re-checks `disposed` immediately after the persist and returns `'steered'` (not `'blocked'`) because the row already exists. It adds the id to `pendingSteerMessageIds`, notifies, and opens `runLeadSteerTurn`.
- A mentioned agent whose assignment is missing or not `queued`/`running` yields `'refused'` (D-11) with the row left pending and the leader turn still opened. A live assignment gets **nothing written** — the leader decides (D-28). `steer()` contains no `steerMessageIds` write.
- `TeamRunSnapshot` gained `pendingSteerMessageIds: string[]` and `undeliveredSteerCountByAgent: Record<string, number>`, both populated in `getState`.

**Task 1b — `deliver_steer`, the leader-only gate (commit `9a0aa82f`)**

- `teamTools.ts` gained the `deliver_steer` definition (one required `steerMessageId`), `export const LEAD_ONLY_TEAM_TOOLS: ReadonlySet<string>` (`delegate_batch`, `deliver_steer`) — one declaration, one home — and a validator that refuses a non-string id with the new `INVALID_ARGUMENT` code.
- `EMPLOYEE_TEAM_TOOLS` is now `TEAM_TOOL_DEFINITIONS.filter((tool) => !LEAD_ONLY_TEAM_TOOLS.has(...))`, so adding a lead tool can never leak it into the employee payload.
- `makeExecuteToolFn` has a `deliver_steer` branch before the generic team-tool branch, mirroring `delegate_batch`: an employee gets `EMPLOYEE_DELIVER_STEER_REFUSAL` and writes nothing.
- `deliverSteer(steerMessageId)` refuses unless the row is `messageKind: 'steer'` with a `targetAgentId`, the target's assignment exists, `assignment.batchId === openBatchId`, and `runStatus` is `queued` or `running`. It is idempotent, writes for **both** `queued` and `running` (a queued agent's round-1 drain reads the field), increments the undelivered count, removes the id from the pending set, and notifies.

**Task 2 — drain into the loop and run the leader's steer turn (commit `9a0aa82f`)**

- `beforeToolRoundFor(agentId, attempt?)` now returns `Promise<ChatCompletionMessage[] | void>`: gates first, then `drainLeaderSteerQueue()` for the lead or `drainSteerInbox(agentId, attempt)` for an employee. Call sites pass `attempt` for employees and nothing for the lead.
- `drainSteerInbox` reads the assignment's `steerMessageIds`, bulk-gets the rows, clears the field **before** returning (a second drain injects nothing), deletes the undelivered count, and maps each row to `{ role: 'user', content: STEER_PREFIX + content }`. Not wrapped in `wrapUntrusted` — steer text is the user's own instruction (T-37.1-16).
- `drainLeaderSteerQueue` takes and clears the pending set, then maps the rows the same way, so the leader reads every message even one that arrived mid-turn.
- `STEER_PREFIX = '[Chỉ đạo từ người dùng] '` is a single module constant; the literal appears exactly once in the file.
- `leadSteerTools()` is `getToolsForTurn(true, mcpTools, LEAD_TOOL_ALLOWLIST)` plus only the `deliver_steer` definition — no `delegate_batch`, no `AI_DATABASE_TOOLS` mutations (T-37.1-13).
- `runLeadSteerTurn(text)` runs through `runLeadTurnSerialized`, loads `recentTurns`, `linkedItems`, `loadPendingSteers()` and the live ledger, builds the prompt with `pendingSteers` and `ledger`, and starts the lead runtime with `messageKind: 'plan'`, `persistUserMessage: false`. It never calls `setPhase`, never registers an agent turn, never settles the lead, and swallows a start failure so a steer turn can never break the batch (T-37.1-17).
- `send()`'s idle path now calls `startLeadTurn` through `runLeadTurnSerialized`, so a steer arriving during `lead-thinking` queues behind the dispatch turn instead of hitting `TURN_IN_PROGRESS`.

**Task 3 — live ledger, conduct rules, D-17 filter (commits `9a0aa82f`, `e953661a`)**

- `BuildLeadTurnRequestInput` gained `ledger` and `pendingSteers`. `[HIỆN TRẠNG LÔ ĐANG CHẠY]` renders `assignmentId · agentName · runStatus` with `· có thể huỷ hoặc sửa` only for `queued` and `· chỉ có thể gửi chỉ đạo` otherwise, wraps each `task` in `wrapUntrusted('VIỆC ĐANG GIAO', …)` (T-37.1-15), and closes with the queued/running rule line. `[CHỈ ĐẠO CHỜ XỬ LÝ]` lists each steer's id, target (or "cả nhóm") and text — without it `deliver_steer` would have no callable id.
- Conduct rules 7-11 added: read the ledger and report honestly; ask when ambiguous or large; warn and hold on a conflict; **you are the gate for every `@agent` steer — the agent does not receive it until you call `deliver_steer`**; report an already-finished agent plainly and never re-run on your own.
- `buildEmployeeTurnRequest` filters `recentTurns` into `visibleTurns` with `row.messageKind !== 'steer' || row.targetAgentId === employee.id` (T-37.1-14).

**Task 4 — teardown wins over an in-flight steer (commit `eb8a7775`)**

- Both drains check `disposed` **before** the clearing write (a check after the update could not prevent it) and return `[]` without clearing, leaving the ledger honest for the post-relaunch undelivered read (D-14).
- `runLeadSteerTurn` re-checks `disposed` after `loadPendingSteers()`/the ledger read and after `registry.get(lead.id).start(request)`.
- `dispose()` clears `pendingSteerMessageIds` and `undeliveredSteerCountByAgent` so no stale badge survives into a new coordinator for the same team id.
- A `drainSteerInbox(agentId, assignmentId)` seam was added to the coordinator interface (same rationale as the exported `finalizeAttempt`) so the disposed gate is provable without a provider.
