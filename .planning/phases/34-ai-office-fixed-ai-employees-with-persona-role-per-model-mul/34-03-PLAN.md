  <action>
Add `beforeToolRound?: (round: number, signal?: AbortSignal) => Promise<void>` to `AiOrchestratorLoopOptions` and destructure it in `runAiOrchestratorLoop`. The signal is optional on the loop option (the loop's own `signal` is optional) but required on `ChatTurnRequest`'s hook — plan 34-03 Task 1's forwarding closure always supplies one, so the runtime path is never signal-less.

Insert immediately after `loopCount++;` at the top of the `while (loopCount < maxLoops)` body: when `loopCount > 1` and `beforeToolRound` is defined, await `beforeToolRound(loopCount, signal)` and then call `signal?.throwIfAborted()`.

Passing `signal` into the call is what makes the abort reach a parked gate. A gate's `wait(signal)` registers its own abort listener; without the argument the gate would park forever and the `throwIfAborted()` after the await would never be reached, because the await itself never settles. The trailing `throwIfAborted()` stays as the belt-and-braces check for a hook that resolves normally after an abort.

The position matters: the loop head is reached only after the previous iteration appended every tool result to `currentMessages` and emitted `onStatusChange('Đang tổng hợp thông tin...')`. Parking there means the in-flight tool completed, the message list is intact, and resuming continues exactly where it stopped — which is what D-21 requires and what a wrapper around `executeToolFn` cannot give (a wrapper parks before the result is appended and only fires on rounds that have tool calls).

`signal?.throwIfAborted()` after the await is mandatory: a bare `await` with no abort path leaves a parked turn hung forever when the user hits Stop (Pitfall 8). The loop's existing `catch` already rethrows `AbortError`, and `chatTurnRuntime` maps that to `phase: 'aborted'`.

Then extend `tests/services/ai/aiOrchestratorLoop.test.ts` with a `describe` block asserting the six behaviors. Use a controllable promise for the park and `AbortController` for the abort case.
