# Phase 19.1: Production Neo4j Integration & Live Retrieval Validation - Context

**Gathered:** 2026-10-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 19.1 deploys the existing optional knowledge stack to a real Kubernetes environment inside the SHB internal network and proves the process `60000006` pilot through TaskMate's production UI against persistent Neo4j storage. It owns production-ready Kubernetes packaging, server-side 9router query planning, live publish/rebuild/retrieve validation, Neo4j restart durability, and metadata-only acceptance evidence.

This phase closes integration gaps that mock and in-memory tests cannot prove. It does not broaden the pilot corpus, add graph editing, perform full disaster recovery, or replace Phase 20's 30–50 question benchmark and aggregate quality calibration.

</domain>

<decisions>
## Implementation Decisions

### Deployment target
- **D-01:** Production target is a remote Kubernetes cluster inside the SHB internal network. TaskMate reaches the knowledge service through an internal URL backed by a `NodePort` service.
- **D-02:** TaskMate must never connect directly to Neo4j or receive Neo4j credentials. Only `knowledge-server` is exposed to TaskMate; Neo4j remains cluster-internal behind `ClusterIP` and Kubernetes network controls.
- **D-03:** Run `knowledge-server` as a Kubernetes `Deployment`. Run Neo4j separately as a `StatefulSet` with a `PersistentVolumeClaim`. Do not place both containers in one Pod or one shared Deployment because their lifecycle, scaling, and persistence requirements differ.
- **D-04:** Package deployment as two easy-to-apply YAML files: one Neo4j manifest containing its `StatefulSet`, internal service, and persistent storage declarations; one knowledge-server manifest containing its `Deployment`, `NodePort` service, ConfigMap references, and Secret references. Document apply order: Neo4j first, then knowledge-server.
- **D-05:** Committed manifests must not contain tokens or passwords, including Base64-encoded secret values. Operator creates or updates the Kubernetes Secret with documented `kubectl create secret generic ...` commands before applying manifests.

### Live pilot flow
- **D-06:** TaskMate UI is the primary acceptance path. API scripts may support setup and diagnostics but cannot replace UI end-to-end proof.
- **D-07:** Acceptance starts by importing the canonical process `60000006` Markdown through the real TaskMate UI. Do not seed or inject IndexedDB records for the acceptance run.
- **D-08:** User creates the document set, runs the real preview and DLP checks, and publishes through the existing guarded UI. No bypass of client-side DLP or publish confirmation is allowed.
- **D-09:** Graph rebuild remains a deliberate manual action after publication. UI must show the real rebuild stage, poll until the graph reaches `Active`, and display Neo4j-backed node, fact, conflict, and quarantine counts before retrieval validation begins.
- **D-10:** Live UI proof requires a grounded answer, at least one valid graph path, and an interactive citation that opens the correct document and exact source range in `QuickPreviewDrawer`.

### Planner runtime
- **D-11:** Use the internal 9router endpoint for natural-language query planning. Preserve the provider-neutral `QueryPlanner` interface and implement 9router behind an adapter rather than coupling retrieval contracts to one provider.
- **D-12:** Query planning is one structured LLM transformation from user question plus bounded ontology context to a strict logical plan. It is not an autonomous agent and must never emit or execute raw Cypher.
- **D-13:** Store `PLANNER_ENDPOINT` and `PLANNER_MODEL` in a Kubernetes ConfigMap. Store `PLANNER_API_KEY` in a Kubernetes Secret. TaskMate must never receive, send, persist, or log the planner credential.
- **D-14:** When planner mode is enabled, knowledge-server startup fails closed on missing or incomplete endpoint/model/key configuration. Operator-facing errors name missing variable categories but never reveal secret values.
- **D-15:** Validate every planner result locally with the existing strict logical-plan and ontology constraints: resolved URNs, allow-listed relation types, valid directions, bounded traversal entries, and maximum three hops. Model output is untrusted until validation passes.
- **D-16:** Allow exactly one bounded schema-repair call after an invalid planner response. Repair input contains only the prior structured output and bounded validation issues. After the second invalid response, stop; do not loop.
- **D-17:** Planner failure degrades safely. Pure identifiers continue through the deterministic fast path; surviving full-text and vector evidence remains usable; graph modality reports planner unavailable. Never guess a graph plan, relation, direction, seed, or Cypher query.

### Acceptance boundary
- **D-18:** Require five representative live smoke cases. Together they cover pure identifier lookup, natural-language planner use, flow/path retrieval, three-hop impact retrieval, and no-evidence or degraded behavior. Each case declares expected source, path, or outcome. Aggregate accuracy scoring remains Phase 20.
- **D-19:** Restart both the `knowledge-server` and Neo4j Pods after successful live queries, then rerun retrieval without rebuilding. Active snapshot identity, graph/retrieval metadata, real counts, quarantines, full-text index, and vector index must survive.
- **D-20:** Phase 17 review warnings `WR-01` and `WR-02` are production blockers for this phase: Neo4j status counts cannot remain hardcoded to zero, and quarantine records cannot remain in a process-memory-only map.
- **D-21:** Failure gate makes the knowledge daemon unreachable from TaskMate. TaskMate must automatically use scoped local BM25, while Docs CRUD, navigation, autosave, and local search remain available. New queries return to server retrieval after connectivity recovers.
- **D-22:** Automatic local fallback remains restricted to disabled/absent daemon and allowed transport/network/timeout failures. Authentication, configuration, invalid-response, and manual-abort errors remain visible and are not silently converted to local results.
- **D-23:** Persist acceptance evidence as metadata-only JSON plus a human UAT checklist. JSON may contain case IDs, pass/fail, snapshot IDs, counts, modality statuses, reason codes, and timings. It must not contain Markdown excerpts, queries containing sensitive data, credentials, raw provider payloads, or sensitive screenshots.

### Claude's Discretion
- Exact Kubernetes resource names, labels, namespace name, probes, resource requests/limits, storage request size, and NodePort value, provided the topology and secret boundaries above hold.
- Exact 9router model selected through `PLANNER_MODEL`, timeout value, and OpenAI-compatible request adapter details, provided planning remains schema-bound, bounded to one repair, and safely degraded.
- Exact five smoke-question wording and metadata-only JSON schema, provided all D-18 categories and live UI interactions are covered.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `readKnowledgeServerOptions` in `knowledge-server/src/main.ts` already provides strict environment parsing and fail-closed startup validation; extend it for planner endpoint/model/key instead of creating a second config system.
- `QueryPlanner`, `QueryPlannerContext`, and `QueryPlanResult` in `knowledge-server/src/retrieval/contracts.ts` provide the provider-neutral planner boundary required by D-11.
- `buildQueryExecutionPlan` in `knowledge-server/src/retrieval/queryPlanning.ts` already separates deterministic identifier handling from LLM planning and enforces the closed ontology plan shape.
- `Neo4jRepository` already owns graph persistence, retrieval generation, active snapshot leases, full-text/vector indexes, and shutdown; production fixes should stay in this adapter.
- Existing Document Set, publish, rebuild-status, grounded-answer, graph-path, citation, and local-BM25 UI flows provide the end-to-end acceptance surface; avoid a separate production-only UI.

### Established Patterns
- TaskMate remains local-first and treats the knowledge daemon as optional. Remote deployment must not become an application startup dependency.
- Protocol boundaries use strict Zod validation and bounded, content-free diagnostics. 9router output and acceptance evidence must follow the same pattern.
- Graph and retrieval data are immutable candidate projections activated atomically from canonical Markdown snapshots.
- Secrets stay server-side and out of client storage, payloads, logs, manifests, and evidence artifacts.
- Only targeted tests and five live smoke cases belong here; broad benchmark evaluation remains Phase 20.

### Integration Points
- Replace the placeholder planner in `startKnowledgeServer` with a configured 9router adapter while preserving `RetrievalService` constructor contracts.
- Extend Neo4j snapshot writes/reads to persist status counts and quarantine records, then verify them after Pod restarts.
- Add Kubernetes manifests and concise operator deployment instructions without introducing a new deployment framework or Helm dependency.
- Drive acceptance through existing TaskMate UI: import pilot docs, create set, DLP preview, publish, manual rebuild, status polling, AI Chat query, graph path, and citation preview.
- Add a bounded metadata-only smoke runner for repeatable API checks and pair it with a UI UAT checklist.

</code_context>

<specifics>
## Specific Ideas

- Recommended deployment order:
  1. Create Kubernetes Secret with Neo4j password, knowledge-server token, and `PLANNER_API_KEY`.
  2. Apply the Neo4j manifest and wait for its readiness probe and PVC binding.
  3. Apply the knowledge-server manifest and verify its authenticated health endpoint through NodePort.
  4. Configure TaskMate with the internal knowledge-server URL and token.
- Representative exact identifier case: `MAIN1.FCL_CYCLE_COUNTER` must use the deterministic fast path and return an exact cited chunk.
- Representative impact case: a question about changing `MAIN1.FCL_CYCLE_COUNTER` must produce a snapshot-local path up to three hops with per-hop citations.
- Representative flow case: ask how process `60000006` runs and inspect the ordered graph path.
- Restart proof must query before and after both Pods restart using the same active snapshot without a new rebuild.
- Acceptance artifacts must be safe to commit or archive: identifiers and content-free metrics only, never raw banking-document excerpts or secret-bearing environment dumps.

</specifics>

<deferred>
## Deferred Ideas

- Full Neo4j disaster-recovery backup and restore into a new Kubernetes cluster — future operations phase.
- Broad 30–50 question benchmark, aggregate accuracy threshold, planner/retrieval calibration, and quality scoring — Phase 20.
- Exposing Neo4j Bolt/HTTP externally for administrative clients — not required for TaskMate and intentionally excluded from this topology.
- Supporting multiple planner providers simultaneously — defer until a second real provider is required; Phase 19.1 keeps the interface provider-neutral but ships one 9router adapter.

</deferred>
