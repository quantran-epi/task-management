## Deployment Target

| Decision | Options considered | Selected |
|----------|--------------------|----------|
| Runtime location | Local Docker; local native; remote server; Neo4j Aura | Remote Kubernetes server inside SHB network |
| Exposed component | Knowledge-server only; both services; API gateway | TaskMate reaches knowledge-server through NodePort; Neo4j stays internal |
| Workload topology | Separate Deployment/StatefulSet; same Pod; separate Deployments | Knowledge-server Deployment + Neo4j StatefulSet/PVC |
| Packaging | Combined resources; component manifests | Two easy-to-apply YAML files, one per component |
| Secret provisioning | `kubectl create secret`; CSI secret manager; committed Secret YAML | Operator-created Kubernetes Secret |

**User's choice:** Remote SHB Kubernetes, separate production-safe workloads, NodePort API access, two simple manifests, operator-created secrets.
**Notes:** User initially suggested two containers in one Deployment for convenience. Discussion clarified why Neo4j requires stateful lifecycle and persistent storage. Convenience requirement retained through one manifest per component rather than one Pod.

## Live Pilot Flow

| Decision | Options considered | Selected |
|----------|--------------------|----------|
| Primary acceptance path | UI end-to-end; API script; equal gates | UI end-to-end |
| Pilot data setup | UI import; automatic seed; pre-existing set; both | Import through TaskMate UI |
| Rebuild behavior | Manual and wait; automatic after publish; script-driven | Manual rebuild and poll to `Active` |
| UI proof | Answer/path/citation; answer/citation; evidence only | Grounded answer + graph path + exact citation |

**User's choice:** Exercise the complete user flow through TaskMate UI.
**Notes:** API tooling remains allowed for setup and diagnostics but cannot substitute for import, DLP preview, publish, rebuild status, answer rendering, graph path, or citation navigation.

## Planner Runtime

| Decision | Options considered | Selected |
|----------|--------------------|----------|
| Provider | Internal 9router; Claude API; local model; multiple adapters | Internal 9router |
| Credential location | Kubernetes Secret; TaskMate key; unauthenticated endpoint | Kubernetes Secret |
| Failure behavior | Safe degradation; fail whole request; heuristic plan; backup model | Safe degradation |
| Endpoint/model config | ConfigMap; image hardcode; TaskMate settings | Kubernetes ConfigMap |
| Invalid output | One repair; no repair; two repairs | One repair |

**User's choice:** 9router server-side adapter with ConfigMap/Secret separation and bounded safe failure behavior.
**Notes:** Query planner was explained as the translation from natural-language questions to validated logical plans, not an autonomous agent or raw Cypher generator. Provider-neutral `QueryPlanner` boundary remains intact.

## Acceptance Boundary

| Decision | Options considered | Selected |
|----------|--------------------|----------|
| Smoke set size | 5 representative; 3 minimal; 10 extended | 5 representative cases |
| Durability gate | Restart both Pods; server only; node reschedule; full DR | Restart both knowledge-server and Neo4j Pods |
| Failure gate | Daemon unreachable; Neo4j unavailable; both | Daemon unreachable |
| Evidence format | JSON + UAT; UAT only; JSON only; screenshots | Metadata-only JSON + UAT checklist |

**User's choice:** Five live cases, restart durability without rebuild, local fallback when daemon is unreachable, and safe repeatable evidence.
**Notes:** Phase 20 retains broad benchmark scoring and calibration. Full cluster disaster recovery is deferred.
