## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** Production target is a remote Kubernetes cluster inside the SHB internal network. TaskMate reaches the knowledge service through an internal URL backed by a `NodePort` service.
- **D-02:** TaskMate must never connect directly to Neo4j or receive Neo4j credentials. Only `knowledge-server` is exposed to TaskMate; Neo4j remains cluster-internal behind `ClusterIP` and Kubernetes network controls.
- **D-03:** Run `knowledge-server` as a Kubernetes `Deployment`. Run Neo4j separately as a `StatefulSet` with a `PersistentVolumeClaim`. Do not place both containers in one Pod or one shared Deployment because their lifecycle, scaling, and persistence requirements differ.
- **D-04:** Package deployment as two easy-to-apply YAML files: one Neo4j manifest containing its `StatefulSet`, internal service, and persistent storage declarations; one knowledge-server manifest containing its `Deployment`, `NodePort` service, ConfigMap references, and Secret references. Document apply order: Neo4j first, then knowledge-server.
- **D-05:** Committed manifests must not contain tokens or passwords, including Base64-encoded secret values. Operator creates or updates the Kubernetes Secret with documented `kubectl create secret generic ...` commands before applying manifests.
- **D-06:** TaskMate UI is the primary acceptance path. API scripts may support setup and diagnostics but cannot replace UI end-to-end proof.
- **D-07:** Acceptance starts by importing the canonical process `60000006` Markdown through the real TaskMate UI. Do not seed or inject IndexedDB records for the acceptance run.
- **D-08:** User creates the document set, runs the real preview and DLP checks, and publishes through the existing guarded UI. No bypass of client-side DLP or publish confirmation is allowed.
- **D-09:** Graph rebuild remains a deliberate manual action after publication. UI must show the real rebuild stage, poll until the graph reaches `Active`, and display Neo4j-backed node, fact, conflict, and quarantine counts before retrieval validation begins.
- **D-10:** Live UI proof requires a grounded answer, at least one valid graph path, and an interactive citation that opens the correct document and exact source range in `QuickPreviewDrawer`.
- **D-11:** Use the internal 9router endpoint for natural-language query planning. Preserve the provider-neutral `QueryPlanner` interface and implement 9router behind an adapter rather than coupling retrieval contracts to one provider.
- **D-12:** Query planning is one structured LLM transformation from user question plus bounded ontology context to a strict logical plan. It is not an autonomous agent and must never emit or execute raw Cypher.
- **D-13:** Store `PLANNER_ENDPOINT` and `PLANNER_MODEL` in a Kubernetes ConfigMap. Store `PLANNER_API_KEY` in a Kubernetes Secret. TaskMate must never receive, send, persist, or log the planner credential.
- **D-14:** When planner mode is enabled, knowledge-server startup fails closed on missing or incomplete endpoint/model/key configuration. Operator-facing errors name missing variable categories but never reveal secret values.
- **D-15:** Validate every planner result locally with the existing strict logical-plan and ontology constraints: resolved URNs, allow-listed relation types, valid directions, bounded traversal entries, and maximum three hops. Model output is untrusted until validation passes.
- **D-16:** Allow exactly one bounded schema-repair call after an invalid planner response. Repair input contains only the prior structured output and bounded validation issues. After the second invalid response, stop; do not loop.
- **D-17:** Planner failure degrades safely. Pure identifiers continue through the deterministic fast path; surviving full-text and vector evidence remains usable; graph modality reports planner unavailable. Never guess a graph plan, relation, direction, seed, or Cypher query.
- **D-18:** Require five representative live smoke cases. Together they cover pure identifier lookup, natural-language planner use, flow/path retrieval, three-hop impact retrieval, and no-evidence or degraded behavior. Each case declares expected source, path, or outcome. Aggregate accuracy scoring remains Phase 20.
- **D-19:** Restart both the `knowledge-server` and Neo4j Pods after successful live queries, then rerun retrieval without rebuilding. Active snapshot identity, graph/retrieval metadata, real counts, quarantines, full-text index, and vector index must survive.
- **D-20:** Phase 17 review warnings `WR-01` and `WR-02` are production blockers for this phase: Neo4j status counts cannot remain hardcoded to zero, and quarantine records cannot remain in a process-memory-only map.
- **D-21:** Failure gate makes the knowledge daemon unreachable from TaskMate. TaskMate must automatically use scoped local BM25, while Docs CRUD, navigation, autosave, and local search remain available. New queries return to server retrieval after connectivity recovers.
- **D-22:** Automatic local fallback remains restricted to disabled/absent daemon and allowed transport/network/timeout failures. Authentication, configuration, invalid-response, and manual-abort errors remain visible and are not silently converted to local results.
- **D-23:** Persist acceptance evidence as metadata-only JSON plus a human UAT checklist. JSON may contain case IDs, pass/fail, snapshot IDs, counts, modality statuses, reason codes, and timings. It must not contain Markdown excerpts, queries containing sensitive data, credentials, raw provider payloads, or sensitive screenshots.

## Summary

Phase 19.1 moves the existing optional knowledge stack from local in-memory/test mocks to a real Kubernetes environment in the SHB internal network. It proves the process `60000006` pilot through TaskMate's production UI against persistent Neo4j storage. It resolves two known production blockers from Phase 17 (`WR-01` hardcoded status counts and `WR-02` memory-only quarantine records), wires an OpenAI-compatible 9router `QueryPlanner` adapter with strict schema validation and bounded one-shot repair, establishes a 2-manifest Kubernetes deployment topology (Neo4j StatefulSet and knowledge-server Deployment), and executes 5 metadata-only live smoke tests plus Pod restart durability checks.

**Primary recommendation:** Package deployment strictly as two manifests (`k8s/neo4j.yaml` and `k8s/knowledge-server.yaml`) with external secret provisioning; persist counts and quarantines on Neo4j `GraphSnapshot` nodes; wire `NineRouterQueryPlanner` behind `QueryPlanner` contract in `knowledge-server/src/main.ts` using native fetch; prove end-to-end retrieval and Pod restart persistence via UI UAT and metadata-only smoke JSON.

### Pattern 1: NineRouterQueryPlanner Adapter (D-11..D-17)
**What:** Implements `QueryPlanner` interface in `knowledge-server/src/retrieval/nineRouterQueryPlanner.ts` using native fetch.
**When to use:** Injected into `RetrievalService` in `startKnowledgeServer` when `PLANNER_REMOTE_ENABLED=true`.
**Rules:**
- Maps user query + resolved candidate entities + ontology schema into strict system prompt.
- Sends OpenAI-compatible chat completion payload with `response_format: { type: 'json_object' }`.
- Validates returned JSON with `LogicalQueryPlanSchema` and semantic check (`validatePlanSemantics`).
- If invalid, executes exactly ONE bounded repair request providing validation error strings and prior output.
- If repair fails, stops and returns `{ type: 'unsupported', reason: 'PLANNER_SCHEMA_FAILURE' }` allowing `buildQueryExecutionPlan` to drop to deterministic fallback without throwing or looping.
- Fails closed on startup if endpoint/model/key are missing when enabled.

### Pattern 2: Persistent Counts & Quarantines in Neo4j (D-20, WR-01, WR-02)
**What:** Durably store status metrics and quarantine items directly in Neo4j.
**When to use:** During `writeCandidate` and `getActiveGraph` / `getQuarantines`.
**Implementation details:**
- In `CYPHER_QUERIES.INSERT_GRAPH_SNAPSHOT`, store candidate summary metrics:
  `s.nodeCount = $nodeCount, s.relationCount = $relationCount, s.factCount = $factCount, s.conflictCount = $conflictCount, s.quarantineCount = $quarantineCount, s.approvedFactCount = $approvedFactCount`.
- In `CYPHER_QUERIES.GET_ACTIVE_GRAPH`, retrieve these properties and convert them with safe Neo4j integer parsing (`toNumber()`).
- In `writeCandidate`, persist quarantine records into Neo4j:
  Store as linked `Quarantine` nodes `(:Quarantine {graphSnapshotId: $graphSnapshotId, rawIdentifier: ...})` or serialize `candidate.quarantines` to JSON string on `GraphSnapshot.quarantinesJson`.
  *Recommended:* Storing `s.quarantinesJson = $quarantinesJson` on `GraphSnapshot` node is atomic, requires zero schema migration or extra joins, and survives server restarts perfectly!

## Common Pitfalls

### Pitfall 1: Leaking Secrets in ConfigMaps or Logs
**What goes wrong:** Sensitive credentials like `PLANNER_API_KEY` or `NEO4J_PASSWORD` get committed into git manifests or printed in container stdout.
**Why it happens:** Convenience during local testing or default error stringification.
**How to avoid:** Put all credentials in `kubectl create secret` commands. Ensure `readKnowledgeServerOptions` and startup banners only log hostnames and models, never secret values (redact strings).

### Pitfall 2: LLM Emitting Unbounded Graph Traversal or Raw Cypher
**What goes wrong:** Prompt injection or model hallucination produces Cypher injection or explosive multi-hop queries that hang Neo4j.
**Why it happens:** Relying on LLM text-to-Cypher.
**How to avoid:** Enforce D-12: The planner transforms to `LogicalQueryPlan` only (typed enums, max 3 hops, max 5 traversal steps). Traversal execution uses static parameterized Cypher templates in `graphTraversal.ts`.

### Pitfall 3: Indefinite Repair Loop on Malformed Planner JSON
**What goes wrong:** When model returns bad JSON or invalid relations, server repeatedly asks for repairs until request times out.
**Why it happens:** Loose loop condition in retry handler.
**How to avoid:** Strictly clamp to exactly 1 repair attempt (D-16). If the second attempt fails schema or semantic check, return degraded outcome immediately.

### Pitfall 4: Loss of State on Neo4j Pod Restart
**What goes wrong:** Rebuilding graph creates data in container ephemeral layer; Pod restart wipes indexes or nodes.
**Why it happens:** Misconfigured PVC mount path (`/data` not mounted to PVC).
**How to avoid:** StatefulSet volume mount must mount PVC to `/data` in Neo4j container. Validate persistence in smoke test step D-19 by restarting Pod and querying without rebuilding.

### Pitfall 5: Broken Local BM25 Fallback on Non-Whitelisted Errors
**What goes wrong:** An auth failure (401) or invalid configuration (400) is swallowed and converted to local BM25 results, masking infrastructure errors.
**Why it happens:** Overly broad catch block in fallback handler.
**How to avoid:** Respect D-22 and existing `isFallbackAllowed` logic: only trigger BM25 fallback on `NETWORK_ERROR` (connection refused / unreachable) and `TIMEOUT`. 401, 403, 400, and invalid response must surface to user as error alerts.

## Acceptance & Smoke Validation Plan (D-18, D-19, D-23)

### Five Representative Live Smoke Cases (D-18)
1. **Case 1: Pure Technical Identifier Fast-Path**
   - Query: `MAIN1.FCL_CYCLE_COUNTER` (or `` `MAIN1.FCL_CYCLE_COUNTER` ``)
   - Expected Mode: Fast-path execution (`fastPath: true`), no planner call needed.
   - Expected Outcome: Exact match chunk citation pointing to `02-data-objects.md` with line-level range.

2. **Case 2: Natural Language Query with 9router Planner**
   - Query: "Chu kỳ Switch cycle nào xử lý tính lãi và phí quá hạn trong container 60000006?"
   - Expected Mode: 9router planner invoked, emits valid `LogicalQueryPlan` with `queryIntent: 'LOOKUP'`.
   - Expected Outcome: Grounded answer citing `04-cycles.md` and related cycle step facts.

3. **Case 3: Process Flow Traversal Path**
   - Query: "Quy trình thực thi của container 60000006 diễn ra theo các bước nào từ Scheduler đến PL/SQL?"
   - Expected Mode: Traversal along `PRECEDES` / `CALLS` relations up to 3 hops.
   - Expected Outcome: Interactive `GraphPathCard` displaying ordered execution steps citing `03-call-chain.md`.

4. **Case 4: Multi-Hop Impact Retrieval**
   - Query: "Nếu thay đổi cấu trúc bảng MAIN1.FCL_CYCLE_COUNTER thì những package và quy trình nào bị ảnh hưởng?"

   - Expected Outcome: Graph path showing affected procedures (`fcl_prc_cycle_counter_pkg`, container 60000006) with evidence classifications.

5. **Case 5: Unreferenced / No-Evidence Safe Degradation**
   - Query: "Thủ tục xử lý chuyển tiền quốc tế SWIFT MT103 trong container 60000006 hoạt động ra sao?"
   - Expected Mode: Evaluated against snapshot; zero graph seeds found.
   - Expected Outcome: `NO_EVIDENCE` semantic outcome, explicit missing evidence warning, zero hallucinations.
