## Behavior Changes

### D-11, D-12 — QueryPlanner Implementation
`NineRouterQueryPlanner` implements `QueryPlanner` and sends query plus context to `${endpoint}/v1/chat/completions` via native `fetch`. It strictly prohibits raw Cypher generation: the system prompt constrains output to JSON logical plans, and responses are parsed through strict `LogicalQueryPlanSchema`.

### D-13, D-14 — Fail-Closed Startup & Configuration
`readKnowledgeServerOptions` checks `PLANNER_REMOTE_ENABLED`. When `'true'`, it asserts presence and validity of:
- `PLANNER_ENDPOINT` (valid URL, no credentials, no query/hash)
- `PLANNER_MODEL`
- `PLANNER_API_KEY`
- `PLANNER_REMOTE_ALLOWED_HOSTS` (endpoint hostname must be explicitly listed)
Errors fail closed without exposing secrets or token values.

### D-15, D-16 — Strict Validation & Bounded 1-Shot Repair
LLM outputs are validated against:
1. `LogicalQueryPlanSchema` (Zod strict parsing)
2. Server-resolved candidate allowlists (`seedUrns` must be in `context.resolvedCandidates`)
3. Closed ontology relations and hop bounds (`RETRIEVAL_ONTOLOGY_REGISTRY`, 1..3 hops)
On validation error, exactly one repair completion is dispatched containing previous output and error issues. If repair fails, it gracefully returns `{ type: 'unsupported', reason: 'PLANNER_SCHEMA_FAILURE' }` without throwing.

### D-17 — Server Bootstrap Wiring
`startKnowledgeServer` in `knowledge-server/src/main.ts` instantiates `NineRouterQueryPlanner` when `remotePlanner.enabled` is true and injects it into `RetrievalService`. If disabled, it falls back to the baseline unsupported planner so deterministic fast-paths and lexical/vector modalities remain active.
