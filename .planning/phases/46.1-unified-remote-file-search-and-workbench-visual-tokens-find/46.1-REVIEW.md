# Phase 46.1: Code Review Report

## Summary

Reviewed the unified remote file search and workbench visual-token changes across services, shell, Find dialog, and remote explorer. Shell-injection defenses (`escapeShellArg`, `--end-of-options`) are applied consistently to all string argv in `gitRemoteService`; I verified the `git log`, `git grep`, and `git diff -z` output shapes in a scratch repo and found the log/numstat/name-status parsers correct. No critical issues. The substantive defects are two user-visible Find regressions (Regex cannot use ERE constructs; the Words checkbox is a no-op in default literal mode), plus a stale-result race when Find is closed or reseeded, an empty-pattern dead end in Files/Folders mode, and an un-normalized numeric argument at a shell boundary. Remaining items are hardening/dead-code notes.

## Critical Issues

None.

## Warnings

### WR-01: Regex mode cannot use ERE constructs because `git grep` runs BRE without `-E`

**File:** `src/services/gitRemoteService.ts:402-405`, `src/workbench/search/find/FindInRemoteFiles.tsx:353`
**Issue:** `flags = ['-z', '-n', '-I', '--no-color']` and `-F` is added only for literal mode. When the Regex checkbox is on, `literal` is false and the pattern reaches `git grep` as a basic regex. Verified in a scratch repo: `git grep -e '(cat|dog)'` matches nothing, while `git grep -E -e '(cat|dog)'` matches both lines. The UI advertises `.*`, so users will reasonably enter `foo|bar`, `(a|b)`, `+`, `?`, `{n}` — none of which work as expected under BRE. Meanwhile client-side `matchRanges` (`parsing.ts:35-55`) uses a JavaScript regex, so the preview highlighting dialect disagrees with the server dialect even on matching text. Fix: add `-E` when not literal.
**Fix:**
```ts
const flags = ['-z', '-n', '-I', '--no-color'];
if (options.literal) flags.push('-F');
else flags.push('-E'); // align remote ERE with the JS regex used for highlighting
```

### WR-02: "Words" checkbox is a no-op in literal (default) mode

**File:** `src/workbench/search/find/query.ts:16-27`, `src/workbench/search/find/FindInRemoteFiles.tsx:352`
**Issue:** `buildGrepOptions` wraps `\\b` boundaries only when `query.words && query.regex`. In the default literal mode it passes the bare pattern with `literal: true` and no whole-word flag. Verified: `git grep -F -e 'cat'` matches inside `concatenate`, so a user checking "Word" still gets substring hits. The highlighter (`parsing.ts:39-42`) *does* apply `\\b` in every mode, so result rows show matches with no highlight — a visible inconsistency. Fix: carry `words` through `GrepRemoteRefOptions` and pass git's `-w` flag; drop the manual `\\b` wrapping in regex mode to avoid double boundaries.
**Fix:**
```ts
// query.ts — stop hand-writing \b, pass the flag
return { pattern: query.pattern, caseSensitive: query.matchCase,
  literal: !query.regex, words: query.words, limit: FIND_MATCH_LIMIT, /* path ... */ };

// gitRemoteService.ts
if (options.words) flags.push('-w');
```

### WR-03: Stale in-flight search can leak into a reopened/reseeded Find dialog; no Stop path exists

**File:** `src/workbench/search/find/FindInRemoteFiles.tsx:291`, `src/workbench/search/find/session.ts:163-171`
**Issue:** Returning `null` when `open` is false does not tear down a search already dispatched. The debounce effect (`FindInRemoteFiles.tsx:125-132`) clears only the *pending* timer on cleanup; a call that already reached `session.search` keeps running on the remote and its `onChange` writes into component state via a stable `setState`. Because the component instance is not unmounted, reopening Find on a different seed creates a new `FindSession` (`useMemo` keyed on `seedKey`) with its own `seq`, but the old session's late response still commits results from the old config/repo/branch into the new dialog. `FindSession.cancel()` is the designed fix but is never called in production (only in tests), so `FIND_STATUS_COPY.partial` ("Stopped — showing partial results") is unreachable and there is no Stop control. Fix: cancel the session when the dialog closes or the seed changes, and optionally expose a Stop button bound to `session.cancel()`.
**Fix:**
```ts
useEffect(() => {
  if (!open) session.cancel();
}, [open, session]);
// seedKey change already yields a new session via useMemo; cancel the old one in the
// useMemo cleanup (return a teardown there) to drop in-flight work from the previous target.
```

### WR-04: Files/Folders modes with an empty pattern fetch nothing and render an unexplained empty list

**File:** `src/workbench/search/find/FindInRemoteFiles.tsx:136-175`
**Issue:** The Files/Folders effect runs whenever `mode !== 'content'`, including an empty `pattern`. `searchRemoteTree` returns `[]` immediately for an empty needle (`gitRemoteTreeService.ts:205-206`), so switching to Files or Folders before typing always yields an empty results panel with no instruction. There is no empty-state message in the Files/Folders branch (the `find-empty` block at line 421 is gated on `state.status === 'done'`, which never changes in these modes). Fix: gate the effect on a non-empty needle and render a prompt when these modes are active with no query.
**Fix:**
```ts
if (!open || mode === 'content' || !remoteQuery.pattern) { setTreeRows([]); return; }
// and in the results panel: if (mode !== 'content' && !remoteQuery.pattern) show "Type to search files/folders".
```

### WR-05: `getRecentCommits` interpolates `limit` into the shell string without the normalization used elsewhere

**File:** `src/services/gitRemoteService.ts:173-188`
**Issue:** `runGitCommand` joins argv with spaces into a shell command. Every string argv in this file goes through `escapeShellArg`, but `String(limit)` is inserted raw. `limit` is typed `number` and the sole in-repo caller (`teamTools.ts:1532`) clamps it with `Math.floor(Number(...))`, so there is no reachable injection today — but `grepRemoteRef` (line 401) defensively normalizes its numeric `limit` at the service boundary while this function does not. If a future caller passes an unvalidated value, `limit = "1; touch /tmp/pwned #"` becomes part of the shell string. Harden at the boundary for consistency with the module's own convention, not at the caller.
**Fix:**
```ts
const safeLimit = Math.min(Math.max(1, Math.floor(Number(limit)) || 20), 100);
const output = await runGitCommand(config, repoPath, [
  'log', '-n', escapeShellArg(String(safeLimit)),
  "--format='%x1e%H%x00%h%x00%an%x00%ad%x00%s'", '--date=iso',
  '--end-of-options', escapeShellArg(branch),
], secret, callId);
```

## Info

### IN-01: `AntdThemeAdapter` hardcodes `data-theme="light"` against a dark-token contract

**File:** `src/workbench/AntdThemeAdapter.tsx:52`
**Issue:** `workbench-tokens.css` defines a complete dark palette keyed on `@media (prefers-color-scheme: dark)` and `:root[data-theme="dark"]`, but the wrapper pins `data-theme="light"` and the Antd `ConfigProvider` tokens are all light values. Dark palettes are therefore dead for the workbench even under an OS dark preference. Acceptable if dark mode is deliberately deferred; otherwise derive the attribute and Antd tokens from the resolved theme.
**Fix:** Replace the literal with the resolved theme value and select matching Antd `colorBgBase`/`colorText` tokens from the same palette.

### IN-02: Unscoped global `overflow: hidden !important` leaks to the default shell

**File:** `src/styles/workbench-tokens.css:287-295`
**Issue:** `html, body, #root { overflow: hidden !important }` is global. This CSS is imported from `WorkbenchLayout`, but `main.tsx` boots the default `App` unless the IntelliJ shell is chosen, so the default shell's root is also forced non-scrollable with no override (`!important`). Scope the viewport lock to the workbench.
**Fix:** Remove the global rule and rely on `.workbench-root` (line 297-306), which already sets `overflow: hidden` and `100%` dimensions.

### IN-03: `parseNameStatusZ` mislabels a copied file as `modified`, and `cancelRemoteCall` is a dead alias

**File:** `src/services/gitRemoteService.ts:291-298`, `src/services/sshService.ts:281-287`
**Issue:** The status mapping has no `C` case, so a copy record (`C100\0old\0new\0`) is reported as `modified`. Not reachable from `getDiffSummary` today (`-M` detects renames, not copies), but the parser is exported and reusable. Separately, `cancelRemoteCall` merely delegates to `cancelToolCall` and has no production caller — it documents a seam that WR-03 should actually wire.
**Fix:** Add `letter === 'C' ? 'added'` to the status mapping, and either wire `cancelRemoteCall` into the Find cancel path (WR-03) or delete the alias so one cancel function remains.
