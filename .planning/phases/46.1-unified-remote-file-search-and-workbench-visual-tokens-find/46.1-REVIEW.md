## Warnings

### WR-06: Regex + Words highlighting disagrees with git `-w` for alternation (WR-02 follow-up)

**File:** `src/workbench/search/find/parsing.ts:39-42`
**Issue:** WR-02 moved whole-word semantics to git's `-w` on the server and removed the hand-written `\b` from `buildGrepOptions`, but `matchRanges` still wraps the *entire* pattern in `\b`:

```ts
if (options.words) {
  const boundary = String.fromCharCode(92) + 'b';
  source = boundary + source + boundary; // "\b" + source + "\b"
}
```

For an ERE alternation (now enabled by WR-01's `-E`) this yields `\bfoo|bar\b`, which parses as `(\bfoo)|(bar\b)` — the boundaries bind to the first and last alternatives only. Verified empirically: `git grep -E -w 'foo|bar'` matches only whole-word occurrences (line `foo bar`, not `foobar`), while the JS highlighter marks `foo` and `bar` inside `foobar` and `xbar`. Result rows are still returned by git, so the preview shows highlights that do not correspond to what matched — the exact "highlight disagrees with remote matching" defect WR-02 set out to remove, now only for the regex+words+alternation combination. Literal+words is fine (`\bcat\b` on `concatenate` → no match, agreeing with `-F -w`).

**Fix:** group the pattern so the boundaries apply to every alternative, matching git `-w`:

```ts
if (options.words) {
  const boundary = String.fromCharCode(92) + 'b';
  source = `${boundary}(?:${source})${boundary}`;
}
```

(The non-capturing group is harmless in literal mode, where `source` is already escaped.)
