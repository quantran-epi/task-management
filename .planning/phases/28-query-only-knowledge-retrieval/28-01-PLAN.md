<objective>
Make `POST /api/v1/retrieve` a query-only federated endpoint: the client sends `{query, limit?, setIds?}` and the server resolves every published set from `SnapshotStore`, searches each set with whatever modality is actually available, and returns evidence carrying set/snapshot attribution.

Purpose: today a fresh device cannot retrieve anything, because the wire schema requires `setTierAssignments`/`comparisonMode`/`budgets`, and a published set without an active graph build has no searchable index at all. This plan removes both blockers on the server and proves the path end-to-end with a tracer before expanding.

Output: thin wire schema, internal resolved request, server-authoritative published-set discovery, a server-local snapshot-lexical retrieval modality, population of the per-set coverage ledger, and route registration that no longer depends on Neo4j being enabled.

Per D-01, D-02, D-03, D-05, D-07, D-09.
</objective>

<assumption_delta_decision>
**noun:** the retrieval scope identity — from caller-supplied `setTierAssignments` to a server-resolved scope (`{query, limit?}` default: all published sets; optional explicit `setIds` restriction).

**decision:** `promote`.

The resolved scope becomes primary. `setTierAssignments` demotes from the wire contract to a field of the internal resolved request (`ResolvedFederatedRetrievalRequest`), produced only by `resolveQueryOnlyScope`. Rationale: D-05/D-07 keep explicit restriction as an optional caller input, never the wire default; leaving `setTierAssignments` required on the wire would contradict the generalized intent and re-block a fresh device. `comparisonMode` likewise becomes an internal field fixed to `'single'` for query-only resolution — no client ever sends it.

`getSetReadiness` is consumed, not merely declared: `main.ts` derives it from the router's two authoritative sources (a retrieval generation is present → `GRAPH_READY`; only an active published snapshot → `PUBLISHED_ONLY`; neither → `FAILED`), and the resolver uses it to seed each enumerated set's `publishedSnapshotId` — `null` for `FAILED`, the enumerated snapshot id otherwise. A `PUBLISHED_ONLY` set is still assigned and searched via snapshot-lexical (D-02), so readiness never removes a published set from the fleet; it only governs whether its published snapshot may be named.

Resolution rules: when `wire.setIds` is present, exact-match each requested ID against the enumerated published set IDs; a miss becomes coverage state `UNAVAILABLE` with both snapshot fields `null`; never append a non-requested set.
