## User Constraints (from CONTEXT.md)

### Locked Decisions
**D-01 — One complete widget, not two runtimes:** `AiChatWidget` owns the lifecycle of a chat turn: persistence, orchestrator invocation, streaming/status, tool execution feedback, mutation approval, abort/retry/error handling, and completed-message persistence. `AIChatDrawer` and SDLC surfaces do not retain their own duplicate chat loops.
**D-02 — Shared renderer with host extension points:** Header-by-scope, toolbox, transcript, composer, and message renderer are common. Hosts retain only outer chrome (for example, drawer open/close controls or the SDLC stepper/editor) and supply scope/context, prompt template, grounding, quick prompts, and typed business callbacks. Surface differences are context and density/layout, not a forked renderer/runtime.
**D-03 — Contextual header and responsive controls:** Header identifies the active scope (ordinary chat/tab or SDLC step/CR). Keep model selection/refresh, Analysis Mode, Auto-approve, MCP controls, and clear context available; collapse controls into compact/overflow presentation at narrow widths. Empty-state quick prompts are supplied per context: general suggestions in Drawer and step-specific suggestions in SDLC.
**D-04 — Consistent tool feedback:** Show concise stage/status and tool badges; make tool details/results expandable instead of dumping every result into the transcript by default. Do not expose raw reasoning as transcript content.
**D-05 — Clear is thread-scoped:** After confirmation, clear only conversation history for the currently active thread. Do not clear SDLC workflow state, drafts, artifacts, other steps, or other threads.
**D-06 — Durable artifact event cards:** Provide one generic event-card mechanism in the widget for structured results from any host. Persist a separate card per artifact version, distinguish draft from saved/approved, display type/title/version/status and host-provided CTA, and have the host handle CTA actions. Opening a historical card targets that exact version, read-only when it is no longer active or the CR is closed. Keep long artifact bodies in their editor/preview rather than duplicating them in chat.
**D-07 — Layered prompt architecture:** Compose each turn from shared policy, step-specific contract, grounded context/evidence, the artifact output contract when applicable, and the user's turn. A step template cannot weaken shared evidence/safety rules.
**D-08 — Evidence and uncertainty:** Do not invent facts. Surface missing evidence and source conflicts; do not silently choose between conflicting internal sources. External best-practice suggestions may be offered only when clearly labeled as unconfirmed/assumptions, separate from facts. Artifact formats are strict only for artifact-generation turns; ordinary chat is not forced into a document template.
**D-09 — Language:** Formal SDLC artifacts default to professional Vietnamese and preserve technical identifiers, names, paths, API/table/code tokens. Ordinary chat follows the user's language.
**D-10 — INTAKE:** Review PL01/PL02 against supplied evidence, show coverage/gaps/conflicts, and group missing-information questions into one concise checklist. Do not claim intake is complete without evidence.
**D-11 — SOLUTION:** Generate a complete implementation blueprint with standard sections for context/scope, architecture/data flow, data/API, security, failure/rollback, tests/acceptance, assumptions, and open questions. Mark irrelevant sections N/A; leave unsupported details explicitly unresolved.
**D-12 — CODE_GUIDE / Step 3:** This is a coding handoff plus Change Pack contract. Communicate approved scope/acceptance and test/migration/rollback expectations, the CR-specific command, and pack expectations. Do not claim code is implemented and do not retain a separate checklist status. The validated Change Pack is the evidence used by Step 4. `Step3CodeGuideView.tsx` currently displays `node scripts/change-pack.mjs --cr <CR>`; the script is not implemented in the TaskMate repository, so planning must treat it as an external target-repository command and verify its contract rather than imply TaskMate can execute it.
**D-13 — CHANGE_PACK:** Interpret the pack in an evidence-linked matrix (path/hunk/entry as available), covering outside-solution, not-implemented, implemented-differently, and incomplete-coverage findings; include impact/risk and next action. Missing pack coverage must remain visible. Do not auto-approve the implementation.
**D-14 — TECH_DOCS / PL03B and PL07:** PL03B describes the actual implemented system truthfully from Change Pack evidence only; it does not contain the SOLUTION comparison or drift matrix. Drift details and comparison remain in TaskMate. PL07 is generated as a blank reviewer checklist/questions; the AI does not infer or pre-mark PASS/FAIL/NOT VERIFIED. The user's PL03B-only-actual decision supersedes the older Phase 25 Roadmap requirement for PL03 to include approved design + actual implementation + drift matrix + DB changes/rollback; update that roadmap contract before planning.
**D-15 — CAB:** The GoLive-facing portion is a concise technical-change list supported by implementation evidence in PL03B/Change Pack only; exclude planned-but-unimplemented SOLUTION items and disclose evidence gaps. In addition, produce a structured CR summary for viewing/storing inside TaskMate only (scope/goal, actual changes, key decisions, risks/rollback, open gaps, and links to supporting artifacts/evidence); do not mix this longer summary into the GoLive text.
**D-16 — Explicit artifact intent:** Ordinary Q&A does not modify artifact state. A dedicated action or a clear natural-language request to create/revise an artifact may generate/update a draft. A clear SOLUTION edit request updates the editor draft immediately and creates a Draft event; it does not replace the prior approved version.
**D-17 — Draft before commit:** PL03B, PL07, and CAB generation produce drafts for review. No artifact is automatically saved/approved/committed after generation; the user performs the existing explicit approval/save action.
**D-18 — Complete artifact on update:** Each create/update returns the complete artifact, not a partial patch, so the editor/preview has one unambiguous current draft.
**D-19 — Immediate staged loading:** Show a visible assistant placeholder/status immediately when a turn starts, then update through preparation, streaming, tool execution, and synthesis. Show progress/tool events, not raw reasoning.
**D-20 — Actionable prerequisite guards:** Disable the unavailable action/input/dropzone and show inline which artifact is missing, which step supplies it, and a direct navigation action where useful. A tooltip may supplement but must not be the only explanation.
**D-21 — Safe inline failures and retry:** Show a sanitized inline error with an actionable next step and Retry. Preserve current draft and approved artifacts; do not persist partial/error output. Retry must not duplicate the user message, consistent with Phase 25.1 atomic-turn/retry identity rules.
**D-22 — Distinct approval wait:** Mutation confirmation uses an explicit “waiting for your approval” state with the change details and approve/reject actions; it is not represented as an active spinner. Continue the turn only after the decision, preserving the existing per-thread/tab Auto-approve behavior and Analysis Mode read-only guard.
**D-23 — Preserve prior SDLC/AI contracts:** Keep isolated step threads (`sdlc:${projectId}:${crId}:${stepId}`), scoped context, durable workflow state, explicit user-triggered analysis (never trigger on component remount), previous approved artifact versions, and Phase 25.2 mutation/approval behavior. Continue using the existing `runAiOrchestratorLoop`; this phase consolidates its consumer rather than introducing a second engine.
**D-24 — Research round-trip is deferred:** The proposal to probe gaps, decide whether external research is needed, generate a self-contained Claude Code brief, paste/import its result as untrusted evidence, then re-synthesize is useful but is a separate capability. Phase 25.3 INTAKE remains evidence review + gap/conflict checklist. Reuse the existing proposal in a future phase; do not implement its gate/import/staleness workflow here.

### Pattern 1: Shared component ownership with typed host adapters
**What:** The widget owns one mounted execution lifecycle and renderer; each host passes a discriminated surface/scope contract, complete messages/config, prompt composer/context, quick prompts and typed callbacks (for example `onArtifactDraft`, `onArtifactOpen`, `onClearThread`, `onMutationApproval`). Keep only drawer shell or step editor/stepper around it. **When to use:** Both surfaces need the same conversation lifecycle and controls, but domain context and resulting artifacts differ. [CITED: React “Sharing State Between Components”; D-01/D-02]

**Example:**
```tsx
<AiChatWidget
  scope={{ kind: 'sdlc', threadKey: `sdlc:${projectId}:${crId}:${stepId}` }}
  context={stepContext}
  prompts={promptLayers}
  quickPrompts={stepQuickPrompts}
  onArtifactDraft={(event) => setCurrentDraft(event.completeMarkdown)}
  onArtifactOpen={(ref) => openArtifactVersion(ref.kind, ref.version)}
/>
```
Source: [React shared-state guidance](https://react.dev/learn/sharing-state-between-components); exact API is a proposed example. [ASSUMED]

### Pattern 2: Restore-before-action coordinator with stable guard codes
**What:** Every action path ensures `getState()` or awaits `restore()` before examining required artifacts; restoration Zod-parses persisted value and respects late-read race guard. For missing prerequisite, return/throw stable reason code and have UI show inline named missing artifact + supplying step + direct navigation (not raw exception). Do not cause mount-triggered AI analysis: restoring local workflow state is distinct from running model calls. **When to use:** Coordinator actions or views may be invoked before async restore finishes/recreated. [VERIFIED: `workflowCoordinator.ts`; CONTEXT D-19/D-20/D-23]

**Example:**
```ts
const ensureState = async () => coordinator.getState() ?? await coordinator.restore();
const state = await ensureState();
if (!state?.artifacts.solution) throw new Error('SOLUTION_REQUIRED_FOR_CHANGE_PACK');
```
Source: `src/services/wizard/workflowCoordinator.ts` (staging, lines inspected); stable user-facing copy/navigation mapping is proposed. [VERIFIED: codebase]

### Pattern 3: Explicit artifact-intent prompt composition
**What:** Build policy/contract/context/output segments as separate typed values; choose output contract only for explicit artifact-generation or clear revise request. Q&A prompt uses shared evidence policy and step-specific instructions without forcing full-document output. Return complete artifact object; host updates draft and emits durable version-specific event; approval/save remains a separate user action. [CITED: D-07/D-08/D-16/D-18]

```ts
const messages = composeSdlcTurn({
  policy: SHARED_EVIDENCE_POLICY,
  step: stepContract[stepId],
  grounding: buildLocalGrounding(context, selectedPackEvidence),
  output: intent === 'artifact' ? artifactContract[kind] : undefined,
  userTurn,
});
```
Source: `25.3-CONTEXT.md` D-07..D-18; proposal only. [ASSUMED]

### Pattern 4: Mutation approval, error and retry stay per thread
**What:** Connect to orchestrator `onMutationCheck`; represent approval as an explicit waiting state, suspend processing indicator, resume only on decision; preserve Analysis Mode guard/Auto-approve semantics. Retry references the same persisted user-message identity; incomplete/aborted/error response stays runtime-only and never commits. Keep request state owned by each widget instance/thread, not a module singleton. [VERIFIED: orchestrator API; CITED: Phase 25.1/25.2 contexts; React effect cleanup guidance]

## Common Pitfalls

### Pitfall 1: Satisfying conflicting Roadmap and D-14 simultaneously
**What goes wrong:** PL03B contains an approved-design comparison/drift matrix despite D-14; plans claim both incompatible outcomes. **Why:** Legacy Phase 25 success criterion 6 requires combined PL03 + drift, while 25.3 D-14 supersedes it. **How to avoid:** Update Phase 25/25.3 Roadmap contract before phase planning and scope success checks to actual-only PL03B, separate TaskMate drift, blank PL07. **Warning signs:** PL03B templates/prompts include “approved design/drift,” tests assert drift sections in PL03B. [VERIFIED: roadmap read; CITED: D-14]

### Pitfall 2: Approving both tech docs as side effect of Generate
**What goes wrong:** New drafts become immutable approved/versioned artifacts immediately, removing review and overwriting safe previous versions. **Why:** Existing Step5 handler calls `onCommitTechDoc` for both docs directly after constructing output. **How to avoid:** Separate AI draft callbacks/editor state from coordinator `commitTechDoc`; add explicit, independent confirmation/save actions and retain prior approved versions on failure. **Warning signs:** generation handler calls commit/save/export or marks approved. [VERIFIED: staging `Step5TechDocsView.tsx`; CITED: D-16/D-17]

### Pitfall 3: Treating `restore()` as the prerequisite solution by itself
**What goes wrong:** UI actions still throw `WORKFLOW_NOT_INITIALIZED` if invoked before restore, or step actions wrongly proceed with a persisted incomplete/stale state. **Why:** Several coordinator actions rely on `currentStateOrThrow`; only particular commits check their next artifact prerequisites; no global async ensure path is present. **How to avoid:** await restore at lifecycle/handler boundaries, make action APIs ensure restore or require initialized state explicitly, validate the correct artifact/coverage/staleness before every transition and map each code to an inline explanation/navigation target. Use lock/generation token where concurrent action/restore can race. [VERIFIED: coordinator source; race guard already present]

### Pitfall 4: Shared widget extraction becomes a common paint layer with duplicated behavior
**What goes wrong:** `AiChatWidget` only renders visuals, while Drawer and SDLC retain separate persistence, AbortControllers, prompt composition, approval, retry and streaming logic. **Why:** Existing code entwines per-host logic; a hook-only extraction may create independent state instances. **How to avoid:** define ownership boundaries and tests that exercise the same lifecycle behavior through both hosts. Hosts provide typed adapters and chrome only. [VERIFIED: drawer/StepChat source; CITED: React custom hooks docs/D-01]

### Pitfall 5: Ordinary conversation accidentally becomes an artifact request
**What goes wrong:** Q&A mutates SOLUTION/PL03B/PL07/CAB state or responses are all forced into formal artifact JSON. **Why:** Per-step prompt always mandates artifact output or parsing triggers based on model language alone. **How to avoid:** distinguish explicit action/natural clear intent, pass output schema only on artifact turn, and route ordinary Q&A without commit callbacks. SOLUTION edits update draft only. [CITED: D-08/D-16]

### Pitfall 6: Missing/partial Change Pack falsely claims system truth
**What goes wrong:** PL03B lists planned changes as implemented, incomplete coverage is suppressed, or “no drift” is asserted on unobserved files. **Why:** Solution is treated as implementation evidence; the ZIP’s metadata/diff is taken as a complete repo snapshot. **How to avoid:** feed PL03B only included Change Pack evidence; explicitly surface deferred/binary/unreadable coverage and unsupported screen/API/table claims; keep drift matrix in TaskMate. A claim of no drift requires `canClaimNoDrift`. [VERIFIED: reconciler; CITED: D-13/D-14]

### Pitfall 7: CAB text reuses unsupported defaults
**What goes wrong:** CAB assures risks controlled, says rollback tested, implies all changes deployed or checklist passed, despite no supporting evidence. **Why:** Existing Step6 creates synthetic defaults (`risks: [controlled]`, `rollback.verified: true`, `unresolvedDrift: []`, placeholder artifact IDs/hashes). **How to avoid:** derive GoLive list strictly from evidence-backed actual implementation; disclose open evidence and unknown rollback; keep TaskMate-only structured CR summary separate. Draft output then approval. [VERIFIED: staging `Step6CabView.tsx`; CITED: D-15/D-17]

### Pitfall 8: Retry, abort, clear or delayed callbacks cross thread boundaries
**What goes wrong:** duplicate user input, partial assistant persistence, late response committed into another tab/thread, clear wipes workflow/artifacts. **Why:** Runtime extraction centralizes/merges unrelated identities or omits request-currentness guard. **How to avoid:** preserve thread-specific run registries and current request IDs, same user message on retry, abort ownership, atomic completed response commit; clear only current `threadId`. Apply stale response/current-tab gate and do not persist progress/errors. [CITED: Phase 25.1 D-05..15 and D-32; VERIFIED: existing separate thread identities]
