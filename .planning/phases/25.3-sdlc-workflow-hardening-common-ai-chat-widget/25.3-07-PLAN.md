<objective>
Extract the duplicated chat-turn lifecycle out of `AIChatDrawer` and `StepChatPanel` into one framework-free runtime plus a thin React hook, so the widget in plan 25.3-08 has a single behaviour source.

Purpose: D-01 and D-23. Two copies of this logic exist today and they have already diverged — `StepChatPanel` persists assistant error text (forbidden by D-21) and has no request-currentness guard, while `AIChatDrawer` has both. A framework-free runtime keeps the state machine testable without React and prevents a hook-only extraction from silently creating two independent runtimes.
Output: `chatTurnTools.ts`, `chatTurnRuntime.ts`, `useChatTurn.ts`, and runtime tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AI provider → runtime | Streamed text, tool calls, and errors are untrusted |
| Runtime → IndexedDB | Only validated complete turns may be persisted |
| Tool call → data mutation | A model-requested mutation needs authorization |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25.3-21 | Elevation | `onMutationCheck` | mitigate | Fixed order: Analysis Mode read-only cancel, then Auto-approve, then explicit approval wait; asserted by Task 2 Tests 3-5 |
| T-25.3-22 | Tampering | Completed-turn persistence | mitigate | Current-request check plus non-empty stripped content; no write on abort/error (Tests 6, 7, 10) |
| T-25.3-23 | Information disclosure | Error surfaces | mitigate | Sanitized `{ code, message }` with no provider payload, key, or stack (Test 7) |
| T-25.3-24 | Repudiation | Retry identity | mitigate | Retry reuses the same user message id so history cannot be double-counted (Test 8) |
| T-25.3-25 | Tampering | Concurrent turns | mitigate | Single in-flight claim per runtime instance, `TURN_IN_PROGRESS` rejection (Test 9) |
</threat_model>
