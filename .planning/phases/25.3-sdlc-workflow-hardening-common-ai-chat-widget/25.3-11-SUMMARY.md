# Phase 25.3 Plan 11: Two-Host Lifecycle Parity Summary

One `describe.each` matrix drives `AIChatDrawer` and `StepChatPanel` through nine identical lifecycle assertions, and it caught four real divergences that two separate per-host suites would have blessed.

## What Was Built

**`tests/ai/AIChatWidgetParity.test.tsx` (370 lines, 18 cases = 9 x 2 hosts)** — a `HostHarness` object per host (`mount`, `prepare`, `ready`, `clearThread`, `toolbox`) absorbs only chrome differences (Drawer = non-compact toolbox, own tab seeding; Step panel = compact overflow menu, `getStepThread` seeding). Every assertion then runs unmodified through both.

| # | Assertion (identical for both hosts) |
|---|--------------------------------------|
| 1 | staged `role="status"` indicator paints before the injected loop resolves |
| 2 | one collapsed badge per tool call; expanding reveals args **and** result |
| 3 | approval card with `Chấp thuận`/`Từ chối`, no staged loader, no Stop control |
| 4 | reject resumes the turn, writes no assistant row, no task row |
| 5 | sanitized error + `Thử lại`; api key and provider text never reach the DOM |
| 6 | clear removes the active thread only; a sibling thread keeps its rows |
| 7 | header shows the host-provided scope label; exactly one widget mounted |
| 8 | `onReasoningChunk` output never appears in the transcript |
| 9 | model select, Analysis Mode, Auto-approve and MCP controls are all reachable |

The orchestrator module itself is mocked (`runAiOrchestratorLoop` is replaced, `dispatchAiToolCall` stubbed), so every test reaches production code up to the network boundary and a host that re-grew its own loop would never run the script.

## Divergences the suite found (and fixed)

1. **Tool badges never rendered in the Drawer.** `tabTypes` had no `toolEvents`, and `activeToolEvents` synthesized a single `phase: 'call'` entry from `toolProgress`, so arguments and results were unreachable. Fixed: runtime emits `args` on `call` and a stable `name` on `result` (`onToolResult` previously reported the call **id** as the tool name); `TabRuntime.toolEvents` carries the real sequence; the widget merges call/result into one badge by id.
2. **The Drawer rendered a spinner during approval wait.** `awaiting-approval` was both in `ACTIVE_STAGES` and mapped to a staged stage, so the D-22 card coexisted with a loader and a `Dừng` button. Fixed: `ACTIVE_STAGES` excludes it, `stagedStageFor` returns `null`, and the composer's `isStreaming` follows the same set.
3. **The Drawer's clear never cleared.** `handleClearContext` appended a context-boundary marker instead of deleting rows, so the transcript survived "clear". Fixed: `clearThreadMessages` on the active thread (D-05), with a confirmation step, and `handleDeleteCurrentThread` now delegates to the same path so there is one clear contract.
4. **The SDLC host cleared without asking.** `StepChatPanel.handleClearThread` deleted immediately. Fixed: same `Modal.confirm` copy as the Drawer.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] Tool event carried no arguments and the result event carried the wrong name**
- **Found during:** Task 1 (assertion 2)
- **Issue:** `ChatTurnToolEvent` had no `args`, and `onToolResult` reported `name: callId`, so a badge could not show what the tool was asked or which tool produced a result.
- **Fix:** added serialized `args` on `call`; the runtime keeps an id→name map so `result` names the tool.
- **Files:** `chatTurnRuntime.ts`, `AiChatWidget.tsx`
- **Commit:** `740b90ef`

**2. [Rule 1 - Bug] Approval wait rendered as an active turn**
- **Found during:** Task 1 (assertion 3)
- **Issue:** `awaiting-approval` was in `ACTIVE_STAGES` and had its own staged stage, contradicting D-22 ("not represented as an active spinner").
- **Fix:** removed it from both; the approval card is now the only wait affordance, and `Stop` is not offered mid-approval.
- **Files:** `AiChatWidget.tsx`
- **Commit:** `740b90ef`

**3. [Rule 1 - Bug] Drawer "clear" appended a boundary marker instead of clearing**
- **Found during:** Task 1 (assertion 6)
- **Issue:** `handleClearContext` called `clearThreadContext`, which writes a `isContextBoundary` row; the thread's messages survived.
- **Fix:** `clearThreadMessages` on the active thread, behind a confirmation; `handleDeleteCurrentThread` reuses the same path.
- **Files:** `AIChatDrawer.tsx`
- **Commit:** `740b90ef`

**4. [Rule 4 - Architectural alignment, no new architecture] Test-only substitution in `AIChatDrawer.test.tsx`**
- **Found during:** Task 2 verification
- **Issue:** the old test asserted `clearThreadContext` was called, which is exactly the behaviour assertion 6 pins as wrong.
- **Fix:** renamed to "clearing context confirms, then removes only the active thread messages (D-05)" and re-pointed at `clearThreadMessages`. Same safety property, corrected target.
- **Files:** `tests/ai/AIChatDrawer.test.tsx`
- **Commit:** task 2 commit

**5. [Rule 3 - Blocking issue] `sdlcPromptIsolation.test.ts` imported the removed re-export**
- **Found during:** Task 2
- **Issue:** the only remaining `getToolsForTurn` consumer of the component path was a test.
- **Fix:** import moved to `src/services/ai/chatTurnTools`.
- **Files:** `tests/ai/sdlcPromptIsolation.test.ts`
- **Commit:** `740b90ef`

No authentication gates. No new dependencies.
