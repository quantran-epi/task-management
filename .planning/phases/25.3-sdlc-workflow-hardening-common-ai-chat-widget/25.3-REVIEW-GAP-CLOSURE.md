# Phase 25.3: Gap-Closure Code Review Report

**Reviewed:** 2026-11-02
**Depth:** standard
**Files Reviewed:** 21
**Status:** issues_found

## Summary

Reviewed the 25.3-13..18 gap-closure surface: SDLC workflow coordinator persistence, CR switching, artifact event cards, chat turn runtime/provider streaming, SOLUTION extraction, splitter accessibility, and Step 2 editor. Truncation handling, maxTokens removal, finish_reason propagation, SQL-free markdown rendering, and the layered prompt composer are sound.

Two blockers remain. (1) Switching CRs leaves the coordinator's in-memory state from the previous CR, and every coordinator write/load/delete resolves the key from `activeCrRef` at call time, so state can be read from one CR and written to another. (2) Draft artifact cards are always rendered locked, so the "open editor" path cannot edit a chat-produced SOLUTION draft.

Fifteen warnings cover lost drafts during approval, invisible prelude loading, clear-thread orphaning an in-flight reply, stale view state across CR switches, retry state leaks, swallowed submit errors, SSE full-body duplication, tool-call index collapse, missing timeout fallback, stale capability cache, parser truncation from a sample fence, Step 2 sync races, splitter listener leaks, post-persist `onCompleted` throw turning success into error, and test coverage gaps.

## Critical Issues

### CR-01: CR switch reuses previous CR's coordinator state and writes it to the new CR key

**File:** `src/services/wizard/workflowCoordinator.ts:73-94`, `src/views/ProjectSdlcView.tsx:189-193`, `src/views/ProjectSdlcView.tsx:259-293`

**Issue:** The coordinator is created once per project (`useMemo([projectId, db])`) and holds a module-level `currentState`. `selectCr` only changes `activeCrId`; it never resets the coordinator. `ensureState()` returns `currentState` immediately when set (`workflowCoordinator.ts:87`) and `restore()` returns `undefined` early without clearing `currentState` (`:78`). Meanwhile `saveState`/`loadState`/`deleteState` resolve the storage key from `activeCrRef.current` at call time (`ProjectSdlcView.tsx:266-289`).

Failure scenario: CR-A state is loaded into memory. User switches to CR-B. `restore()` loads nothing (or is cancelled), but the stale CR-A `currentState` survives. The next step action (`navigateToStep`, `commitSolution`, `setCheckpoint`, etc.) calls `ensureState()`, receives CR-A's versions/artifacts, emits it, and `saveState` writes it under `sdlc_workflow:${projectId}:${CR-B}`. CR-B now displays and persists CR-A's workflow, and CR-B's real state is overwritten on the next emit. A concurrent restore for CR-A can also complete after the switch and call `onStateChange` with CR-A state, which the cancelled effect no longer guards because `restore()` writes `currentState` itself.

**Fix:** Make the coordinator CR-scoped. Reset `currentState`/`restoreInFlight` when the CR changes, and key persistence by the CR the coordinator was created for rather than by mutable ref:

```ts
// ProjectSdlcView: rebuild the coordinator per CR, or add coordinator.resetMemory() on selectCr
const coordinator = useMemo(
  () => createSdlcWorkflowCoordinator({
    projectId,
    // capture the CR this coordinator belongs to
    saveState: (state) => db.settings.put({
      key: workflowStorageKey(projectId, coordinatorCrId), value: JSON.stringify(state),
    }),
    loadState: async () => { /* same fixed coordinatorCrId */ },
    deleteState: async () => db.settings.delete(workflowStorageKey(projectId, coordinatorCrId)),
    ...
  }),
  [projectId, db, coordinatorCrId]
);
```

and in the coordinator, clear `currentState` and `restoreInFlight` at the start of `restore()` for the new identity (or expose `reset()` that does). Add a test: load CR-A state, switch to CR-B, invoke `navigateToStep`, assert no row is written under CR-B and `workflowState` is CR-B's (undefined) state.

### CR-02: Draft artifact cards are always read-only and cannot open an editable draft

**File:** `src/views/ProjectSdlcView.tsx:113`, `src/views/ProjectSdlcView.tsx:183`, `src/views/ProjectSdlcView.tsx:672-675`, `src/components/ai/artifacts/ArtifactEventCard.tsx:56-66`

**Issue:** `readOnly: event.version !== active || crStatus !== 'active'`. A chat-produced draft is stamped with `version = (activeVersions.SOLUTION ?? artifact.version ?? 0) + 1` (`ProjectSdlcView.tsx:381`), while `active` is the committed `activeVersions.SOLUTION`. The draft version is therefore never equal to `active`, so every draft card is `readOnly: true`. The CTA button is disabled (`ArtifactEventCard.tsx:65`) and `onArtifactOpen` always passes `readOnly === true` (`AiChatWidget.tsx` onOpen). The `onArtifactCta` handler re-derives `readOnly` as `status !== 'approved' ? true : false` (`ProjectSdlcView.tsx:674`), so even if the CTA were enabled it would set `readOnlySolution = true`.

Result: D-16/D-07's "draft goes to the editor for review" path is unreachable from the card. The user sees a disabled "Mở trình soạn thảo" and cannot edit or approve the extracted SOLUTION from the card.

**Fix:** Distinguish "historical/closed" from "draft of the current active version". A draft belonging to the current active CR should be editable; only approved versions older than `active`, or CRs that are no longer active, should be read-only:

```ts
readOnly: (event.status === 'approved' && event.version !== active) || crStatus !== 'active',
```

and for the CTA, open the live editor for a draft:

```tsx
onArtifactCta={(eventId) => {
  const event = stepMessages.find((m) => m.id === eventId)?.artifactEvent;
  const isDraftCurrent = event?.status === 'draft' && activeCrRef.current === activeCrId;
  handleArtifactOpen(eventId, !isDraftCurrent);
}}
```

Add a test asserting a draft card's CTA is enabled and opens Step 2 with `readOnly=false`.

## Warnings

### WR-01: Prelude loading is invisible after a completed/failed turn

**File:** `src/components/sdlc/chat/StepChatPanel.tsx:305-310`

**Issue:** The loading status is only painted when `turn.status === 'idle'`: `preludePending && turn.status === 'idle' ? 'preparing' : turn.status`. After any completed, error, or aborted turn the runtime status remains `complete`/`error`/`aborted`, so a new send's config/key/tool discovery prelude shows no spinner. The composer looks dead for the duration of `Promise.all([getNineRouterConfig, getNineRouterApiKey, toolsForTurn])`, exactly the gap D-19/SC5 intended to close.

**Fix:**

```ts
status: preludePending && !['preparing', 'tool', 'streaming', 'synthesizing'].includes(turn.status)
  ? 'preparing'
  : turn.status,
```

Add a test that submits after a completed turn and asserts the preparing indicator appears before `turn.start` resolves.

### WR-02: Draft is discarded while an approval is pending

**File:** `src/components/ai/AiChatWidget.tsx:109-114`, `src/components/ai/AiChatWidget.tsx:254`, `src/components/ai/AiChatWidget.tsx:277`, `src/components/ai/AiChatWidget.tsx:361`, `src/components/sdlc/chat/StepChatPanel.tsx:144-232`

**Issue:** `ACTIVE_STAGES` excludes `awaiting-approval`, so `isTurnActive` is false. `ChatInputBar` is enabled (`isStreaming={isTurnActive}`), and if the thread is empty, `showQuickPrompts` is also true. `submit` clears `setDraft('')` before awaiting, and `turn.start()` rejects with `TURN_IN_PROGRESS` (the runtime is parked on approval); the `catch {}` swallows it. The user's typed text is lost with no feedback, and a quick prompt is discarded the same way.

**Fix:** Treat `awaiting-approval` as input-locking while a turn is parked:

```ts
const isTurnActive = ACTIVE_STAGES.has(turn.status) || turn.status === 'awaiting-approval';
// but keep the spinner hidden for awaiting-approval:
const showSpinner = ACTIVE_STAGES.has(turn.status);
```

Or in `StepChatPanel.submit`, re-check the runtime status and restore the text on `TURN_IN_PROGRESS` instead of clearing it first.

### WR-03: Clearing the thread does not stop an in-flight turn, so its reply is orphaned

**File:** `src/components/sdlc/chat/StepChatPanel.tsx:244-263`

**Issue:** `handleClearThread` only calls `clearThreadMessages(threadId, db)`. If a turn is streaming (or a prelude is staged), the runtime keeps running and later persists its assistant message into the just-cleared thread. The user sees an empty conversation that silently regains a stale reply, and the prelude token is not released. The clear contract ("xóa toàn bộ nội dung trao đổi") is violated.

**Fix:** Abort and reset before deleting:

```ts
onOk: async () => {
  preludeTokenRef.current = 0;
  setPreludePending(false);
  turn.abort();
  await clearThreadMessages(threadId, db);
  ...
}
```

(the callback must then depend on `turn.abort`). Add a test: start a turn, clear mid-stream, assert the runtime is aborted and no assistant row is written afterwards.

### WR-04: Switching CR leaves stale viewed version, read-only mode, and drafts

**File:** `src/views/ProjectSdlcView.tsx:189-193`

**Issue:** `selectCr` only resets the analysis timer. It does not clear `viewedVersion`, `readOnlySolution`, `incomingSolutionDraft`, `draftPl03b`, or `draftPl07`. `handleArtifactOpen` pins the editor to the previous CR's historical body; after a CR switch the Step 2/5/6 views still show the old CR's pinned content and remain read-only (`handleArtifactOpen` set `readOnlySolution=true`). The Step 2 editor can also show the previous CR's draft until the load effect overwrites `incomingSolutionDraft`.

**Fix:**

```ts
const selectCr = useCallback((crId: string) => {
  if (activeCrRef.current !== crId) {
    clearAnalysisTimer();
    setViewedVersion(undefined);
    setReadOnlySolution(false);
    setIncomingSolutionDraft(undefined);
    setDraftPl03b(undefined);
    setDraftPl07(undefined);
  }
  activeCrRef.current = crId;
  setActiveCrId(crId);
}, [clearAnalysisTimer]);
```

### WR-05: Async draft/artifact writes resolve the CR at completion, so they can land on the wrong CR or duplicate a version

**File:** `src/views/ProjectSdlcView.tsx:127-158`, `src/views/ProjectSdlcView.tsx:363-389`, `src/views/ProjectSdlcView.tsx:410-422`, `src/views/ProjectSdlcView.tsx:425-437`

**Issue:** `saveDraft` and `appendArtifactEvent` read `activeCrRef.current` when they execute, after `await` boundaries (hashing, `getStepThread`, Dexie puts). `handleSolutionExtracted` also computes `version` from the render-scope `activeVersions`/`workflowState`, which can belong to the CR that was active when the turn started. If the user switches CR while a chat turn completes, the extracted draft and its event are written under the new CR; `handleCommitSolution` deletes `draftSettingKey(..., activeCrRef.current)` after the commit await, so the draft of whichever CR is selected at completion is deleted. `handleResetWorkflow` has the same delete-after-await pattern.

**Fix:** Capture `const crId = activeCrRef.current` (and the CR's version) at the start of each handler and thread it through; abort the write if the captured CR no longer matches when it resumes:

```ts
const handleSolutionExtracted = useCallback(async (draftMarkdown: string) => {
  const crId = activeCrRef.current;
  if (!crId) return;
  await db.settings.put({ key: draftSettingKey(projectId, crId), value: draftMarkdown });
  if (activeCrRef.current !== crId) return; // stale turn: skip card for a CR the user left
  await appendArtifactEvent(crId, ...);
}, ...);
```

Give `appendArtifactEvent` an explicit `crId` parameter instead of reading the ref.

### WR-06: Retry does not reset streaming text or pending approval

**File:** `src/components/ai/runtime/useChatTurn.ts:91-118`

**Issue:** `start` clears `streamingText` and `pendingApproval`, but `retry: runtime.retry` is passed through without those resets. A retry after a failed/aborted turn can render the previous turn's streaming text or stale approval card until the new turn's first delta/publish arrives.

**Fix:** Wrap retry like `start`:

```ts
const retry = useCallback(async () => {
  setStreamingText('');
  setPendingApproval(null);
  return runtime.retry();
}, [runtime]);
```

### WR-07: `submit` swallows every error, including composition failures

**File:** `src/components/sdlc/chat/StepChatPanel.tsx:220-221`

**Issue:** The bare `catch {}` assumes the only failure is `TURN_IN_PROGRESS`, but it also hides `composeSdlcTurn` throws (`ARTIFACT_CONTRACT_REQUIRED`), `getStepThread`/config failures, and any runtime throw. The draft was already cleared, so the user loses the prompt and gets no message.

**Fix:** Surface non-`TURN_IN_PROGRESS` failures and restore the draft:

```ts
} catch (err) {
  const code = (err as { code?: string } | null)?.code;
  if (code !== 'TURN_IN_PROGRESS') {
    setDraft(rawText);
    setError({ code: code ?? 'TURN_FAILED', message: 'Không thể bắt đầu lượt trả lời. Vui lòng thử lại.' });
  }
}
```

### WR-08: SSE fallback parser accumulates the buffered partial line, duplicating body content

**File:** `src/services/ai/nineRouterClient.ts:273-277`, `src/services/ai/nineRouterClient.ts:383-391`

**Issue:** On each network chunk: `lineBuffer += decoded`; then `fullRawBody += lineBuffer`; then split and `lineBuffer = lines.pop()`. The trailing partial line is added to `fullRawBody` again on the next chunk. If the stream yields no parsed events (`yieldedAny === false`) the fallback does `JSON.parse(fullRawBody)` (`:385`), which now contains interleaved/duplicated fragments and can fail or mis-parse. This path is used by providers that return a single JSON body instead of SSE.

**Fix:** Accumulate only complete lines, or snapshot the decoded chunk separately:

```ts
lineBuffer += decoder.decode(value, { stream: true });
const lines = lineBuffer.split(/\r?\n/);
lineBuffer = lines.pop() ?? '';
for (const line of lines) fullRawBody += line + '\n';
```

then flush `lineBuffer` into `fullRawBody` after the loop.

### WR-09: Parallel tool calls collapse when the provider omits `index`

**File:** `src/services/ai/nineRouterClient.ts:341`

**Issue:** `const idx = tc.index ?? 0;` merges every tool-call delta without an explicit `index` into slot 0. Providers that stream `tool_calls` without `index` (or emit multiple top-level calls in one delta without indices) collapse into one truncated tool call, so the orchestrator executes the wrong arguments or only the last call.

**Fix:** Fall back to a monotonic slot when the provider omits `index` and the delta carries a new `id`/`function.name`:

```ts
const idx = tc.index ?? (tc.id ? (toolCallIndexById.get(tc.id) ?? nextToolIndex++) : currentToolIndex);
```

Add a test feeding two id-bearing deltas with no `index`.

### WR-10: `completeJson` loses its 90s timeout when `AbortSignal.any` is unavailable

**File:** `src/services/ai/nineRouterClient.ts:523-526`

**Issue:** `combinedSignal` falls back to `req.signal` when `AbortSignal.any` is missing. In runtimes without `AbortSignal.any` (older Safari/WebViews, some Tauri webviews), a hung provider request never times out, blocking the turn indefinitely.

**Fix:** Use a manual controller that mirrors both signals, or fall back to `timeoutSignal` when `req.signal` is absent:

```ts
const controller = new AbortController();
const cancel = () => controller.abort();
req.signal?.addEventListener('abort', cancel, { once: true });
timeoutSignal.addEventListener('abort', cancel, { once: true });
const combinedSignal = controller.signal;
```

### WR-11: Capability probe caches failures for 24h, disabling structured output after a transient outage

**File:** `src/services/ai/nineRouterClient.ts:677-739`

**Issue:** `probeStructuredOutputCapability` stores failed probes with `expiresAt: now + 24h` (`:736`). A single network hiccup, 429, or provider restart disables structured/tool output for the rest of the day with no retry. The failure is indistinguishable from "provider lacks capability".

**Fix:** Cache only positive results; cache negative results for a short backoff (e.g. 60s) or not at all, and distinguish transport errors from capability rejection.

### WR-12: SOLUTION extractor can truncate the document at a `# SOLUTION` line inside an earlier sample fence

**File:** `src/utils/sdlcSolutionParser.ts:14-31`, `src/utils/sdlcSolutionParser.ts:44`

**Issue:** `if (!heading && /^#\s+SOLUTION\b/i.test(line)) heading = { start: offset, fence }` captures the first `# SOLUTION` anywhere, including inside an earlier fenced sample. `heading.fence` is then set, and when that fence closes `end = offset` (`:26`), so `clean.slice(heading.start, end)` returns only the sample up to its closing fence. Later real sections are dropped.

Example:
```markdown
Ví dụ cũ:
```markdown
# SOLUTION — sample
```
# SOLUTION — CR-2026-18
## Kiến trúc
...
```

The `return clean.slice(heading.start, end)` path prefers the sample. No test covers a `# SOLUTION` line before the real heading.

**Fix:** Ignore headings inside a fence when choosing the anchor (`if (!heading && !fence && ...)`), and/or prefer the last heading that is outside a fence or whose fence closes last. Add a regression test for the sample-then-real-heading case.

### WR-13: Step 2 editor can show stale content and overwrite unsaved edits

**File:** `src/components/sdlc/steps/Step2SolutionView.tsx:83-105`, `src/components/sdlc/steps/Step2SolutionView.tsx:121-163`, `src/components/sdlc/steps/Step2SolutionView.tsx:158`

**Issue:** Three related defects:
1. The parent-sync effect only assigns when `parentContent` is truthy (`if (parentContent && ...)`). If the parent's solution/initial content becomes empty (reset, CR with no solution), the editor keeps the previous CR's content.
2. The `incomingDraft` effect (`:101-105`) unconditionally replaces the editor body whenever the prop changes, so an async chat completion can clobber text the user typed after the turn started. It also omits `onDraftChange`/`content` from deps, reading stale closures.
3. `handleApproveAndSave` bypasses `getStepThread` and manually queries/creates `db.chatThreads` (`:135-146`), racing the panel's own `getStepThread`; two concurrent creations for the same `&scopeKey` can throw or produce a duplicate thread. Its `catch (err: any)` (`:158`) renders raw `err.message`, leaking internal error strings to the UI.

**Fix:** Sync empty content (`if (parentContent !== undefined && parentContent !== content)`), only accept `incomingDraft` when the editor is not dirty or when a draft version token changes, and call `getStepThread(projectId, crId, 'SOLUTION', db)`. Replace the `any` catch with a guard-code check and a fixed Vietnamese message.

### WR-14: Splitter window listeners leak if the component unmounts mid-drag

**File:** `src/components/common/ResizeSplitter.tsx:59-75`

**Issue:** `pointermove`/`pointerup`/`pointercancel` listeners are added on `pointerdown` and removed only in `handlePointerUp`. If the splitter unmounts (step switch, drawer close, layout change) while dragging, the listeners stay attached to `window`, keep calling `onResize` on a stale component, and retain the closure's `onResize`/width state. The handlers also do not filter `upEvent.pointerId`, so a second pointer's release can end a drag it did not start.

**Fix:** Track cleanup in a ref and run it on unmount:

```ts
const dragCleanupRef = useRef<(() => void) | null>(null);
useEffect(() => () => dragCleanupRef.current?.(), []);
// in pointerdown: dragCleanupRef.current = () => { window.removeEventListener(...); };
// in pointerup: if (upEvent.pointerId !== e.pointerId) return;
```

### WR-15: `onCompleted` throwing after persistence flips a saved turn to error

**File:** `src/components/ai/runtime/chatTurnRuntime.ts:358-384`

**Issue:** The assistant message is saved, `publish('complete')` fires, then `deps.onCompleted?.(...)` runs inside the same `try`. If `onCompleted` throws (host handoff, draft write), the `catch` publishes `error` and returns `{ phase: 'error' }`. The UI shows a failure even though the message is persisted; `StepChatPanel` skips `extractSolutionDraft` and the SDLC editor never receives the artifact.

**Fix:** Invoke the completion callback outside the persistence `try`, or wrap it so a host callback failure cannot reclassify a persisted turn:

```ts
publish('complete');
try { deps.onCompleted?.({ content: clean, tokenUsage }); } catch { /* host callback only */ }
return { phase: 'complete', ... };
```
