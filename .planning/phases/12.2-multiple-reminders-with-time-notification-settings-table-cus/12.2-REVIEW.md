## Critical Issues

### CR-01: Omission of `stale` tasks in startup desktop notification body causes misleading zero-count notifications

**File:** `src/hooks/useDesktopNotification.ts:93-100`  
**Issue:** `useDesktopNotification` checks `notifications.activeCount === 0` to decide whether to dispatch a startup summary notification. `activeCount` includes `stale` tasks. However, lines 93-97 only extract `overdue`, `overload`, and `reminders` (which only sums `reminder` and `due-soon`). If a user has only stale tasks in progress or review, `activeCount > 0` is true and a desktop notification is dispatched stating `"Bạn có 0 việc quá hạn, 0 ngày quá tải, và 0 việc cần xử lý."`. This displays misleading zero counts despite triggering an active notification.  
**Fix:**
Include `stale` in the summary counts so all active notification categories contributing to `activeCount` are accurately reflected:

```typescript
    const overdue = notifications.categoryCounts.overdue;
    const overload = notifications.categoryCounts.overload;
    const stale = notifications.categoryCounts.stale;
    const reminders =
      notifications.categoryCounts.reminder + notifications.categoryCounts['due-soon'];
    const totalPending = reminders + stale;

    const summaryText = `Bạn có ${overdue} việc quá hạn, ${overload} ngày quá tải, và ${totalPending} việc cần xử lý.`;
```

## Warnings

### WR-01: Rigid exact-minute comparison in live reminder ticker drops alerts under browser throttling

**File:** `src/hooks/useDesktopNotification.ts:142-148`  
**Issue:** `checkLiveReminders` uses strict string equality: `if (item.date === currentMinuteTarget)` where `currentMinuteTarget` is `${currentClock} ${currentDate}`. Modern browsers (Chrome, Firefox, Safari) aggressively throttle inactive background tab timers to 1 minute or longer. If the 30-second interval ticks at HH:mm:58 and the subsequent tick occurs at HH:(mm+1):01, the exact minute target is skipped and the desktop notification is permanently dropped. In addition, opening the application even 1 minute after a scheduled reminder misses the notification.  
**Fix:**
Check whether the reminder time has arrived on today's date (`timePart <= currentClock`), and track dispatched keys per day/time to guarantee delivery even if a tick is delayed:

```typescript
    const now = dayjs();
    const currentDate = now.format('YYYY-MM-DD');
    const currentClock = now.format('HH:mm');

    for (const item of notifications.items) {
      if (item.category !== 'reminder' || !item.date) continue;
      const parts = item.date.split(' ');
      if (parts.length === 2) {
        const [timePart, datePart] = parts;
        if (datePart === currentDate && timePart <= currentClock) {
          const reminderKey = `${item.id}:${datePart}:${timePart}`;
          if (notifiedRemindersRef.current.has(reminderKey)) continue;

          try {
            const notif = new window.Notification(item.title, {
              body: item.subtitle || 'Đã đến giờ nhắc nhở!',
              icon: '/task-management/favicon.ico',
              requireInteraction: settingsData.settings.requireInteractionEnabled,
            });

            notif.onclick = () => {
              window.focus();
              notif.close();
            };

            notifiedRemindersRef.current.add(reminderKey);
          } catch (err) {
            console.warn('Live reminder notification failed:', err);
          }
        }
      }
    }
```

### WR-02: Race condition in `saveSettings` can overwrite stored settings before `useLiveQuery` resolves

**File:** `src/components/settings/NotificationSettingsCard.tsx:58-77`  
**Issue:** `saveSettings` reads `settings` directly from component scope. On initial render, `useLiveQuery` returns `undefined` while querying IndexedDB asynchronously, causing `settings` to fall back to `DEFAULT_NOTIFICATION_SETTINGS`. If a user toggles any switch immediately after opening settings, previously saved custom thresholds or category toggles in IndexedDB can be overwritten by the defaults.  
**Fix:**
Read the latest record directly from `db.settings` inside `saveSettings`:

```typescript
  const saveSettings = async (partial: Partial<NotificationSettings>) => {
    const record = await db.settings.get(NOTIFICATION_SETTINGS_KEY);
    const existing =
      record?.value && typeof record.value === 'object'
        ? (record.value as Partial<NotificationSettings>)
        : {};
    const updated: NotificationSettings = {
      ...DEFAULT_NOTIFICATION_SETTINGS,
      ...existing,
      ...partial,
      enabledCategories: {
        ...DEFAULT_NOTIFICATION_SETTINGS.enabledCategories,
        ...(existing.enabledCategories ?? {}),
        ...(partial.enabledCategories ?? {}),
      },
    };
    await db.settings.put({
      key: NOTIFICATION_SETTINGS_KEY,
      value: updated,
    });
    if (partial.browserNotificationsEnabled !== undefined) {
      await db.settings.put({
        key: 'browserNotificationsEnabled',
        value: partial.browserNotificationsEnabled,
      });
    }
  };
```

### WR-03: `TaskTable` deadline sorter places tasks without deadline at the top on descending sort

**File:** `src/components/tasks/TaskTable.tsx:626`  
**Issue:** `sorter: (a, b) => (a.deadline || '9999-99-99').localeCompare(b.deadline || '9999-99-99')`. Because Ant Design inverts comparator output for descending sort, sentinel `'9999-99-99'` becomes the largest value, sorting tasks without deadlines to the top of the table rather than keeping them at the bottom.  
**Fix:**
Explicitly sort nullish values so undefined deadlines stay at the bottom:

```typescript
      sorter: (a, b) => {
        if (!a.deadline && !b.deadline) return 0;
        if (!a.deadline) return 1;
        if (!b.deadline) return -1;
        return a.deadline.localeCompare(b.deadline);
      },
```
