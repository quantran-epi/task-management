    1. In src/types/notifications.ts:
       - Export NOTIFICATION_SETTINGS_KEY = 'notification_settings'.
       - Export interface NotificationCategoryConfig:
         { overdue: boolean; dueSoon: boolean; overload: boolean; stale: boolean; reminders: boolean; timer: boolean; }.
       - Export interface NotificationSettings:
         {
           browserNotificationsEnabled: boolean;
           requireInteractionEnabled: boolean;
           dueSoonDays: number; // 1, 2, 3, 5 (default: 1)
           staleTaskDays: number; // 3, 5, 7, 14 (default: 5)
           capacityOverloadThreshold: number; // 100, 110, 120 (default: 100)
           enabledCategories: NotificationCategoryConfig;
         }.
       - Export DEFAULT_NOTIFICATION_SETTINGS: NotificationSettings with:
         browserNotificationsEnabled: false,
         requireInteractionEnabled: true,
         dueSoonDays: 1,
         staleTaskDays: 5,
         capacityOverloadThreshold: 100,
         enabledCategories: { overdue: true, dueSoon: true, overload: true, stale: true, reminders: true, timer: true }.
    2. In src/utils/notifications.ts:
       - Update EvaluateNotificationsOptions to accept optional settings?: NotificationSettings.
       - Inside evaluateNotifications:
         a) Use effectiveSettings = options.settings || DEFAULT_NOTIFICATION_SETTINGS.
         b) For Overdue tasks (Priority 1): skip if !effectiveSettings.enabledCategories.overdue.
         c) For Capacity overload (Priority 2): skip if !effectiveSettings.enabledCategories.overload. When calculating daily load ratio, compare plannedWorkMinutes against (capacityMinutes * (effectiveSettings.capacityOverloadThreshold / 100)).
         d) For Due-soon tasks (Priority 3): skip if !effectiveSettings.enabledCategories.dueSoon. Compute cutoff window using effectiveSettings.dueSoonDays instead of hardcoded 1 day (today/tomorrow).
         e) For Stale tasks (Priority 4): skip if !effectiveSettings.enabledCategories.stale. Compare activity difference against effectiveSettings.staleTaskDays instead of hardcoded 5 days.
         f) For Custom reminders (Priority 5): skip if !effectiveSettings.enabledCategories.reminders.
    3. In src/hooks/useNotifications.ts:
       - In the useLiveQuery promise batch, query targetDb.settings.get(NOTIFICATION_SETTINGS_KEY).
       - Parse setting record value as NotificationSettings, falling back to DEFAULT_NOTIFICATION_SETTINGS if absent.
       - Pass settings to evaluateNotifications({ ..., settings: resolvedSettings }).
  </action>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12.2-04 | Denial of Service | `useDesktopNotification.ts` | mitigate | Throttle startup notification to once per browser session via `sessionStorage` and minute-boundary deduplication for live reminders to prevent notification floods |
| T-12.2-05 | Information Disclosure | `useDesktopNotification.ts` | mitigate | Aggregate startup notification bodies into generic counts without disclosing sensitive task details; individual reminder notifications only expose item name and custom note |
| T-12.2-06 | Tampering | `NotificationSettingsCard.tsx` | mitigate | Strict type constraints on threshold selects (1/2/3/5 for dueSoon, 3/5/7/14 for staleTaskDays, 100/110/120 for capacityOverloadThreshold) prevent arbitrary value injection |
| T-12.2-SC | Tampering | npm dependencies | mitigate | Zero new dependencies added; builds strictly on existing audited packages |
</threat_model>
