# Phase 13.1: Code Review Report

**Reviewed:** 2026-10-01T21:50:00Z
**Depth:** standard
**Files Reviewed:** 53
**Status:** issues_found

## Summary

Phase 13.1 implements timer pause timestamps with discrete segment tracking, safe status automation, Jira Epic project mapping, sticky notes with markdown and image attachments, weekly actual worklog planner with midnight splitting, and desktop OS Keychain credential persistence.

Review identified critical data loss and regression issues:
1. `BackupProjectRecordSchema` omits `jiraEpicKey`, causing Zod schema stripping and permanent loss of Jira Epic mappings during backup restore.
2. `BackupWorkSessionRecordSchema` omits `segments`, stripping all pause timestamps upon backup import.
3. Pre-import snapshot rollback (`rollbackToSnapshot`) ignores `notes` and `noteAttachments`, corrupting database state on import reversal.
4. Editing work sessions in `WorkSessionDetailModal` preserves stale `segments`, causing the Actual Worklog planner table to ignore user-edited durations and times.
5. `TaskDrawer` crashes with an unhandled TypeError when passed a mock database without a `notes` table.
6. Multiple test suites broke due to outdated assertions following Phase 13.1 UI refactoring.

## Critical Issues

### CR-01: Backup payload validation strips `jiraEpicKey` from Project records

**File:** `src/validation/backupSchemas.ts:42-57`
**Issue:** `BackupProjectRecordSchema` was not updated to include `jiraEpicKey`. Because Zod's `z.object` strips unlisted properties during `safeParse`, any exported backup containing `jiraEpicKey` on projects has that field stripped during `validateBackupPayload()` in `src/services/backup/validateBackup.ts`. When restoring via `restoreBackupPayload()`, all Jira Epic mappings on all projects are permanently deleted.
**Fix:**
```typescript
export const BackupProjectRecordSchema = z.object({
  id: uuidSchema,
  name: z.string().trim().min(1, 'Name is required').max(120, 'Name must be 120 characters or less'),
  description: z.string().optional(),
  deadline: calendarDateSchema.optional(),
  notes: z.string().optional(),
  status: z.enum(PROJECT_STATUSES),
  jiraEpicKey: jiraKeySchema.optional(),
  opsOwners: tagListSchema.optional(),
  businessAnalysts: tagListSchema.optional(),
  documentLinks: z.array(linkSchema).optional(),
  reminderDate: reminderDateSchema.optional(),
  reminderNote: reminderNoteSchema,
  reminders: remindersArraySchema,
  createdAt: z.string(),
  updatedAt: z.string(),
});
```

### CR-02: Backup payload validation strips `segments` from WorkSession records

**File:** `src/validation/backupSchemas.ts:122-145`
**Issue:** `BackupWorkSessionRecordSchema` does not include `segments`. Any backup containing timer pause timestamps (`segments: TimerSegment[]`) has `segments` stripped during `validateBackupPayload()`. Restoring the backup wipes out all discrete segment intervals on work sessions, causing permanent data loss and breaking midnight segment splitting in the Actual Worklog Planner.
**Fix:**
```typescript
export const BackupWorkSessionRecordSchema = z
  .object({
    id: uuidSchema,
    taskId: uuidSchema,
    startTime: z.string().datetime({ message: 'startTime must be a valid ISO 8601 string' }),
    endTime: z.string().datetime({ message: 'endTime must be a valid ISO 8601 string' }).optional(),
    date: calendarDateSchema,
    durationMinutes: z.number().int().min(1).max(1440),
    segments: z.array(timerSegmentSchema).optional(),
    note: z.string().trim().max(500, 'Note must be 500 characters or less').optional(),
    createdAt: z.string(),
    updatedAt: z.string(),
  })
```

### CR-03: Pre-import rollback (`rollbackToSnapshot`) fails to clear and restore Notes and Note Attachments

**File:** `src/services/backup/restoreBackup.ts:77-100, 191-240`
**Issue:** In `restoreBackupPayload`, when capturing pre-import snapshot, `noteAttachments` is omitted from `snapshot.tables`. In `rollbackToSnapshot`, the transaction only opens `[projects, milestones, tasks, capacityRules, capacityOverrides, plannedAllocations, workSessions, activeTimers, settings, backupMetadata]`. It does NOT clear `targetDb.notes` or `targetDb.noteAttachments`, and does NOT restore `notes` or `noteAttachments` from snapshot. If a user rolls back an import, the imported notes/attachments remain orphaned and pre-import notes are lost.
**Fix:**
In `src/services/backup/restoreBackup.ts`:
1. Include `noteAttachments` in `snapshot.tables` during `restoreBackupPayload`.
2. In `rollbackToSnapshot`:
```typescript
    await targetDb.transaction(
      'rw',
      [
        targetDb.projects,
        targetDb.milestones,
        targetDb.tasks,
        targetDb.capacityRules,
        targetDb.capacityOverrides,
        targetDb.plannedAllocations,
        targetDb.workSessions,
        targetDb.activeTimers,
        targetDb.notes,
        targetDb.noteAttachments,
        targetDb.settings,
        targetDb.backupMetadata,
      ],
      async () => {
        // 1. Clear current domain tables, notes, and attachments
        await Promise.all([
          targetDb.projects.clear(),
          targetDb.milestones.clear(),
          targetDb.tasks.clear(),
          targetDb.capacityRules.clear(),
          targetDb.capacityOverrides.clear(),
          targetDb.plannedAllocations.clear(),
          targetDb.workSessions.clear(),
          targetDb.activeTimers.clear(),
          targetDb.notes.clear(),
          targetDb.noteAttachments.clear(),
        ]);

        // 2. Restore records from snapshot
        // ... bulkAdd existing tables ...
        if (snapshot.tables.notes && snapshot.tables.notes.length) {
          await targetDb.notes.bulkAdd(snapshot.tables.notes);
        }
        if (snapshot.tables.noteAttachments && snapshot.tables.noteAttachments.length) {
          await targetDb.noteAttachments.bulkAdd(snapshot.tables.noteAttachments);
        }
```

### CR-04: Work session editing in `WorkSessionDetailModal` preserves stale `segments`, causing Actual Worklog planner to ignore user edits

**File:** `src/components/planner/WorkSessionDetailModal.tsx:145-156`, `src/db/repositories/workSessionRepo.ts:93-120`
**Issue:** When a user edits a work session's time range, date, or duration in `WorkSessionDetailModal`, `updateWorkSession` updates `startTime`, `endTime`, `durationMinutes`, and `note`. However, `editingSession.segments` is preserved as-is. In `aggregateTaskActualMinutesByDate` (`src/utils/worklog.ts`), if `session.segments` is present, it computes actual minutes strictly by splitting the old `segments`, ignoring the edited start/end times and duration. As a result, user edits in `WorkSessionDetailModal` have zero effect on the weekly Actual Worklog table and variance totals.
**Fix:**
When saving an edited session in `WorkSessionDetailModal.tsx`, update `segments` to reflect the new time boundaries:
```typescript
      if (editingSession) {
        await updateWorkSession(
          editingSession.id,
          {
            startTime: startTimeIso,
            endTime: endTimeIso,
            durationMinutes,
            segments: [{ startTime: startTimeIso, endTime: endTimeIso }],
            note,
          },
          db
        );
        message.success('Đã cập nhật phiên làm việc');
      }
```

### CR-05: `TaskDrawer` unhandled crash when mock or partial DB without `notes` table is passed

**File:** `src/components/tasks/TaskDrawer.tsx:124-130`
**Issue:** `TaskDrawer` queries `targetDb.notes.where('entityId')...` without verifying that `targetDb.notes` exists. When rendering `TaskDrawer` in tests or contexts with a partial/mock DB that does not define `notes`, it throws `TypeError: Cannot read properties of undefined (reading 'where')`, crashing the entire component and causing 3 test failures in `TaskDrawerWorkSessions.test.tsx`.
**Fix:**
```typescript
  const taskNotesCount = useLiveQuery(
    async () => {
      if (!taskId) return 0;
      const targetDb = db || (await import('../../db')).db;
      if (!targetDb?.notes) return 0;
      return await targetDb.notes
        .where('entityId')
        .equals(taskId)
        .filter((n) => n.entityType === 'task')
        .count();
    },
    [taskId, db]
  );
```

### WR-01: `toCalendarDateString` in `workSessionRepo.ts` timezone shift on date strings

**File:** `src/db/repositories/workSessionRepo.ts:13-19`
**Issue:** `toCalendarDateString("2026-10-01")` executes `new Date("2026-10-01")`. In JavaScript, date-only strings parse as UTC midnight. Calling `d.getFullYear()`, `d.getMonth()`, `d.getDate()` in local time zones west of UTC (e.g. UTC-5) produces the previous day (`"2026-09-30"`). When `getWorkSessionsForWeek` is called with date strings, it shifts the query window boundary by one day.
**Fix:**
```typescript
function toCalendarDateString(dateInput: string | Date): string {
  if (typeof dateInput === 'string' && /^\d{4}-\d{2}-\d{2}$/.test(dateInput)) {
    return dateInput;
  }
  const d = typeof dateInput === 'string' ? new Date(dateInput) : dateInput;
  const year = d.getFullYear();
  const month = String(d.getMonth() + 1).padStart(2, '0');
  const day = String(d.getDate()).padStart(2, '0');
  return `${year}-${month}-${day}`;
}
```

### WR-02: `openJiraExternalUrl` security fallback bypasses Tauri URL scheme validation

**File:** `src/services/jira/jiraApi.ts:21-31`
**Issue:** In `openJiraExternalUrl`, if Tauri `open_external_url` rejects a URL (e.g. because it is blocked as a non-http/https URL in `jira_proxy.rs`), the `catch` block logs a warning and falls back to `window.open(url, '_blank')`, effectively bypassing the Tauri protocol restriction for blocked URLs.
**Fix:**
```typescript
export async function openJiraExternalUrl(url: string): Promise<void> {
  const trimmed = url.trim();
  if (!trimmed.startsWith('http://') && !trimmed.startsWith('https://')) {
    console.warn('Blocked: only http:// and https:// URLs are allowed');
    return;
  }
  if (isTauriApp()) {
    try {
      await tauriInvoke('open_external_url', { url: trimmed });
      return;
    } catch (err) {
      console.warn('Failed to open URL via Tauri native opener, falling back to window.open:', err);
    }
  }
  window.open(trimmed, '_blank', 'noopener,noreferrer');
}
```

### WR-03: `DEFAULT_STATUS_MAPPINGS` in `TaskJiraSection.tsx` maps status ID `'3'` to `'In Progress'` instead of `'Done'`

**File:** `src/components/tasks/TaskJiraSection.tsx:59-66`
**Issue:** `DEFAULT_STATUS_MAPPINGS` hardcodes status ID `'3'` under `'In Progress'`. In Jira default workflows (and in test suites), status ID `'3'` is frequently `Done`. When transitioning a task whose destination status ID is `'3'`, `resolveLocalStatusFromMapping('3', mappings)` resolves to `'In Progress'`. If the local task was already `'In Progress'`, change detection (`resolvedLocal !== task.status`) evaluates to false and `onUpdateTask` is never invoked, failing to mark the task `Done`.
**Fix:** Map `'3'` to `Done` in `DEFAULT_STATUS_MAPPINGS`, or check `statusCategory` as a fallback when `jira_status_mappings` is unconfigured.
