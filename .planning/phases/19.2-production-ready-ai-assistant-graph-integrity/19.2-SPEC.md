## 2. Background & Problem Statement

Commit `471320f` addressed early architectural misalignments, but live audit and Phase 19.1 UAT revealed critical gaps blocking production deployment:
1. **Intent Classification & Fail-Closed UX:** The client router historically relied on keyword lists (`DEFAULT_OPERATIONAL_VERBS`, `DEFAULT_KNOWLEDGE_HINTS`). When LLM routing failed or clarification was needed, the UI bypassed the LLM via generic route chips, fell into infinite degraded loops, or concatenated accumulated stream buffers (`fullResponse`) across tool-loop turns. When the LLM was unreachable, the client failed open into degraded tool calls or ungrounded BM25 synthesis instead of halting cleanly.
2. **Grounded Answer Truthfulness:** Synthesis validation frequently crashed with `Kết quả tổng hợp không khớp với bằng chứng xác thực`. When synthesis succeeded, responses often lacked citations. Hypotheses were conflated with verified facts, and ordinary Vietnamese phrasing (`thay thế`) was misclassified as ontology-backed supersession.
3. **Graph Ingestion & Runtime DI:** `main.ts` instantiated components with missing methods or unsafe casts (`as unknown as RetrievalIndexGateway`). Prose extraction functions (`collectUncoveredProse`, `extractProseCandidatesOnce`) existed but were never wired into `GraphBuildService`. Rebuilds were hardcoded to SHB credit card table schemas, causing non-SHB documents to extract 0 relations and 0 evidence. Active graph snapshots were replaced immediately without candidate verification or rollback capability.
4. **Neo4j Traversal & Evidence Closure:** The graph repository ignored the `LogicalQueryPlan` traversal steps and executed an undirected one-hop catch-all Cypher query. Traversed edges had no persisted links to supporting chunk IDs. Ambiguous identifiers (`60000006`) were filtered with hardcoded keyword heuristics (`container`) rather than dynamic LLM-based disambiguation.
5. **TaskMate ↔ Knowledge Links:** Entity links between TaskMate tasks/projects and knowledge graph URNs were ad-hoc, not persisted as first-class relational entities in IndexedDB, and not carried into backup exports or scoped retrieval context.
6. **Live Verification Gaps:** Phase 19.1 UAT recorded 2 major/blocker issues, 4 blocked tests, and 3 skipped tests (Tests 5–13). These unverified capabilities must be imported into Phase 19.2 and formally proven against real Neo4j, existing document sets, and real 9router endpoints.

### System Invariants

1. **Storage Authority:** Local browser IndexedDB is the sole canonical authority for TaskMate work data and document Markdown. Neo4j is a secondary, rebuildable knowledge projection. Destruction or unavailability of Neo4j must never compromise TaskMate data or local note editing/BM25 search.
2. **LLM Primacy:** Every natural-language user turn must enter `routeIntent()` through the LLM. No verb lists, keyword matching, or regex shortcuts are permitted to bypass intent reasoning.
3. **Fail-Closed Intent:** If the LLM is unconfigured, unreachable, or fails schema validation after one repair attempt, the turn halts immediately with an accessible `AI unavailable` state. No fallback tool execution, no fake AI responses, and no mutations may execute.
4. **Daemon-Down Graceful Degradation:** If the LLM is operational but the knowledge daemon or Neo4j is unreachable, the client falls back to local IndexedDB BM25 search over local notes. The response is explicitly labeled as `Local Document Evidence`.
5. **Mutation Safety:** All mutations (`operate_taskmate`, `mixed` mutations, `link_knowledge_entity`) require explicit user confirmation via modal preview before Dexie write. Read operations (`query_taskmate`, `query_knowledge`) execute without confirmation.
6. **Snapshot Immutability:** Graph queries execute against an explicitly pinned `snapshotId`. Traversal never crosses snapshot boundaries or reads uncommitted candidate data.
7. **Two-Phase Publication:** New graph snapshots are prepared, embedded, and verified as candidate snapshots (`READY`) before activation. Activation is an atomic compare-and-swap (CAS). Instant rollback to the prior active snapshot is guaranteed during a configurable grace period.
8. **Truthful Grounding:** Material claims require immutable citation references linking to specific chunk IDs and document offsets. Unsupported assertions move to `unsupportedParts`. Speculation is strictly quarantined to a dedicated `hypotheses` field and permitted only upon explicit user request.
9. **Provider Neutrality:** The system communicates with LLM backends strictly via the existing provider-neutral 9router / OpenAI-compatible client. No vendor-specific SDKs (e.g., Anthropic SDK) are introduced.

## 4. Client Intent State Machine & Fail-Closed Semantics

### Intent Taxonomy

The intent space is locked to five mutually exclusive categories:
- `operate_taskmate`: Mutate personal work data (create/update/delete task, project, milestone, timer, allocation).
- `query_taskmate`: Read personal work data or inspect status/progress (e.g., "tình hình click to pay như nào rồi", "tasks due today").
- `query_knowledge`: Ask questions regarding documented technical processes, architecture, business flows, or data objects.
- `mixed`: Requests combining both TaskMate operations/reads and knowledge lookup (e.g., "Tạo task review theo quy trình 60000006").
- `clarify`: Requests that are genuinely ambiguous, underspecified, or lacking necessary context to safely act.

### Technical Identifiers Rule

Technical identifiers (e.g., `MAIN1.FCL_CYCLE_COUNTER`, `PRC_CONTAINER:60000006`, `AC_ACCT_NO`) must be classified by the LLM as `query_knowledge`. The LLM system prompt includes explicit few-shot examples establishing this rule. The knowledge server provides a deterministic identifier fast-path **only after** intent routing has classified the query as `query_knowledge`.

### Clarification Protocol

1. Transient state `ClarificationContext` is stored in the chat drawer:
   ```typescript
   interface ClarificationContext {
     originalQuery: string;
     clarifyQuestion: string;
     cycleCount: number; // Max 2 cycles before hard abort
   }
   ```
2. The UI renders the assistant message containing the exact `clarifyQuestion` accompanied by an ARIA live region (`role="status"`).
3. Generic route buttons (e.g., "Tra cứu tài liệu", "Thao tác TaskMate") are eliminated.
4. When the user submits their answer, the next routing payload concatenates the context:
   ```
   Original user request: {originalQuery}
   Follow-up clarification from user: {userResponse}
   ```
5. If `cycleCount >= 2` and the model still returns `clarify`, the system halts with an actionable error: *"Yêu cầu chưa đủ rõ ràng sau 2 lần làm rõ. Vui lòng đặt lại câu hỏi với thông tin cụ thể hơn."*

### Tool Loop Buffer Isolation

To prevent repeated degraded error text across tool turns:
1. In `AIChatDrawer.tsx`, the tool loop must reset `fullResponse = ''` at the start of each iteration.
2. Redundant post-tool synthesis passes are eliminated if the tool execution already generated a definitive terminal response.
3. If an operational tool loop encounters an error, the error is surfaced directly without silently wrapping it in conversational filler.

## 5. Grounded-Answer Truth Contract & Speculation Policy

### Grounded Answer Schema

New synthesis writes schema version 2. Persisted historical messages remain readable through a discriminated union: `GroundedAnswerSchemaV1 | GroundedAnswerSchemaV2`. The read normalizer maps v1 messages to the display model with `confidence: 'unknown'`, a historical-schema confidence reason, and `hypotheses: []`; it does not rewrite stored v1 payloads. `GroundedAnswerSchemaV2` alone is used for new model output.

```typescript
export interface GroundedClaim {
  id: string; // Regex: ^C[1-9][0-9]*$
  text: string;
  classification: 'DIRECT' | 'INFERRED';
  citationIds: string[]; // Min 1, max 8, Regex: ^(S|L)[1-9][0-9]*$
  pathId: string | null;  // Required if INFERRED, null if DIRECT
}

export interface GroundedHypothesis {
  id: string; // Regex: ^H[1-9][0-9]*$
  text: string;
  basis: string; // Why this speculation was formed
  confidence: 'low'; // Invariant: Hypotheses must always be low confidence
}

export interface GroundedAnswer {
  schemaVersion: 2;
  language: string;
  conclusion: string;
  claims: GroundedClaim[];
  hypotheses: GroundedHypothesis[]; // Permitted ONLY when speculation_requested = true
  unsupportedParts: string[];
  confidence: 'high' | 'medium' | 'low' | 'unknown';
  confidenceReason: string;
}
```

### Speculation Rules

1. `speculation_requested` is detected by the LLM during `routeIntent()` and passed via `IntentResult.speculation_requested: boolean`.
2. If `speculation_requested === false`:
   - `hypotheses` must be an empty array `[]`.
   - Any model speculation in `claims` that lacks supporting citation IDs is rejected during Zod validation and moved to `unsupportedParts`.
3. If `speculation_requested === true`:
   - Hypotheses are permitted strictly in the `hypotheses` field.
   - Every hypothesis must carry `confidence: 'low'` and an explanatory `basis`.
   - Hypotheses must never be assigned citation IDs or graph path IDs.
   - UI renders hypotheses in a distinct visual section labeled: *"Giả thuyết / Phỏng đoán (Chưa có bằng chứng xác thực)"*.

### Zero-Evidence Behavior

When retrieval yields zero matching chunks and zero graph entities:
- Persisted grounding outcome must be `NO_EVIDENCE`.
- `claims` must be empty `[]`.
- `conclusion` must explicitly explain what information was searched and missing.
- `confidence` must be `'unknown'`.
- If speculation was explicitly requested, labeled hypotheses may appear in `hypotheses`. Otherwise, `hypotheses` must be empty.
- Inventing facts or hallucinating citations under zero-evidence conditions is a hard contract failure.

### Citation Repair & Integrity

1. Citations in `citationIds` must reference verified IDs present in the `EvidencePack` (`S1..Sn` for server chunks, `L1..Ln` for local chunks).
2. Plan 19.2-03 deletes current `fallbackCitationId` behavior in `src/services/ai/groundedSynthesis.ts` that injects the first allowed citation into an uncited claim or constructs a default `C1` from the conclusion. No replacement may attach `S1`/`L1` merely because it exists.
3. Normalization may fix formatting issues (e.g., converting `[S1]` to `S1`) only when the normalized ID is already allowlisted.
4. Runtime may perform one bounded repair using validation errors and the original citation/path allowlist. If closure still fails, reject raw output and render safe synthesis failure plus validated evidence; never invent citations. Unsupported requested portions may appear in `unsupportedParts` only when model output itself remains schema- and closure-valid.

### Relation-Backed Supersession

Supersession claims (e.g., "Quy trình B thay thế Quy trình A") must be backed by structured document-set `scopeProof.overrideRelation === 'SUPERSEDES'` whose citations intersect the claim, or cited evidence classified as a policy change, release note, or migration record. `SUPERSEDES` is not a domain edge in `RelationTypeSchema`. Generic linguistic markers such as *"thay thế"* never prove supersession by themselves; unsupported wording causes closure repair or safe rejection.

### Safe Snapshot Cleanup

Old snapshots are cleaned up only after:
1. `rollbackGraceExpiry` has elapsed.
2. Active query lease count on `priorSnapshotId` drops to 0.
3. Cleanup executes an idempotent Cypher transaction deleting all nodes and relationships partitioned by `(graphSnapshotId = :expiredSnapshotId)`.

## 7. General Document Extraction

### Elimination of Document-Specific Heuristics

The extraction engine in `knowledge-server/src/graph/extraction.ts` must be completely decoupled from SHB-specific constants:
- Delete hardcoded column matchers: `Chu kỳ tính lãi`, `Hạch toán`, `Tên trường dữ liệu`.
- Delete hardcoded procedure URN prefixes or name patterns.
- Entity values and relationships must be derived from Markdown table headers and section hierarchies, then mapped only to the existing closed ontology. Extraction must not invent new entity or relation types dynamically.

### Generic Table & Header Parser

1. When a Markdown table is encountered, the parser analyzes header row cells to determine semantic roles (e.g., Code, Name, Type, Description, Parent, Step, Condition).
2. Relationships are derived only when a recognized generic table/header schema provides the required roles; unrecognized tables pass to bounded prose extraction instead of filename/domain special cases.
3. Section hierarchy (H1 -> H2 -> H3) supplies structural context and container boundaries only through relation types already present in the ontology.

### Prose Fact & Relation Extraction

For all non-tabular Markdown sections (paragraphs, callouts, bullet lists):
1. The build pipeline invokes `collectUncoveredProse()` to extract contiguous text blocks not parsed by the table engine.
2. Uncovered blocks are processed by `extractProseCandidatesOnce()` via the LLM extraction prompt:
   - Input: Text chunk, section path, existing resolved entities.
   - Output: Strict JSON array of extracted Entities, Events, and Facts adhering to the closed ontology.
   - Constraint: Every extracted fact must cite the exact verbatim text quote within the chunk.
3. Extracted entities without confident identifier resolution are routed to a snapshot-scoped quarantine store (`QUARANTINED` status) rather than polluting the core graph.

## 8. Plan-Driven Neo4j Traversal, Indexes & Evidence Closure

### Neo4j Index Schema

The Neo4j database must enforce idempotent constraints and indexes scoped by `graphSnapshotId`:

```cypher
// Composite existence & uniqueness constraints
CREATE CONSTRAINT c_snapshot_entity_urn IF NOT EXISTS
FOR (e:Entity) REQUIRE (e.graphSnapshotId, e.urn) IS NODE KEY;

CREATE CONSTRAINT c_snapshot_chunk_id IF NOT EXISTS
FOR (c:Chunk) REQUIRE (c.graphSnapshotId, c.chunkId) IS NODE KEY;

CREATE CONSTRAINT c_snapshot_fact_key IF NOT EXISTS
FOR (f:Fact) REQUIRE (f.graphSnapshotId, f.factKey) IS NODE KEY;

// Lookup & retrieval indexes
CREATE INDEX idx_entity_name IF NOT EXISTS
FOR (e:Entity) ON (e.graphSnapshotId, e.canonicalName);

CREATE INDEX idx_entity_normalized IF NOT EXISTS
FOR (e:Entity) ON (e.graphSnapshotId, e.normalizedKey);

CREATE INDEX idx_chunk_doc_range IF NOT EXISTS
FOR (c:Chunk) ON (c.graphSnapshotId, c.documentId, c.lineStart, c.lineEnd);

// Vector search index
CREATE VECTOR INDEX chunk_embeddings IF NOT EXISTS
FOR (c:Chunk) ON (c.embedding)
OPTIONS {indexConfig: {
  `vector.dimensions`: 384,
  `vector.similarity_function`: 'cosine'
}};
```

### Fact ↔ Chunk Evidence Closure

To ensure every traversed fact can be cited:
1. During graph construction, each `Fact` node is connected to the exact `Chunk` node(s) containing its source text via a directed relationship:
   ```cypher
   (:Fact {graphSnapshotId: $snap, factKey: $key})-[:SUPPORTED_BY]->(:Chunk {graphSnapshotId: $snap, chunkId: $cid})
   ```
2. When a graph path is traversed, the query joins `Fact` nodes to their `SUPPORTED_BY` chunks, returning chunk IDs and published content hashes along with the graph edges.

### Plan-Driven Traversal Execution

The `traverse()` method in `Neo4jRepository` must execute the validated steps of `LogicalQueryPlan.traversalSteps`:
1. **Parameterized Cypher Templates:** Traversal queries use pre-compiled static templates from a secure catalog. User-provided strings and dynamic relation names are never interpolated directly into Cypher.
2. **Step Execution:**
   - Multi-hop traversal follows only relation types allowlisted by `RelationTypeSchema`, including `CONTAINS_STEP`, `PRECEDES`, `CALLS`, `INVOKES`, `READS_FROM`, `WRITES_TO`, `EMITS`, `CONSUMES`, `USES_TYPE`, and `HAS_STATUS`.
   - Traversal enforces edge direction (`OUTGOING`, `INCOMING`, `BOTH`).
   - Traversal obeys per-step hop limits, depth limits (max 3 hops), and node/edge caps.
   - Cycle prevention is enforced via the simple-path rule (`ALL(x IN nodes(p) WHERE single(y IN nodes(p) WHERE y = x))`).
3. **Traversal Path Record:** Returns structured `GraphTraversalPathRecord` containing aligned node URNs, fact keys, evidence classifications (`OBSERVED`, `INFERRED`, `BUSINESS_APPROVED`), supporting chunk IDs, and conflict flags.
4. The legacy catch-all undirected one-hop query is completely removed.

### LLM-Based Disambiguation

1. `processKeywords`, `stepKeywords`, and hardcoded keyword-to-kind mapping tables are deleted from `queryPlanning.ts`.
2. Exact single-entity token matches resolve deterministically to that entity URN.
3. When an identifier or phrase matches multiple candidate entities (e.g., `60000006` matching both `PRC_CONTAINER:60000006` and `PRC_PROCESS:60000006`):
   - All server-resolved candidates (URN, kind, canonical name, and a 1-hop summary) are passed to the 9router query planner.
   - The query planner selects the target entity URN based on query context.
   - If the planner cannot resolve the ambiguity with high confidence after one repair attempt, it returns `NEEDS_CLARIFICATION` with safe candidate options.

## 10. Observability, Deployment & CI

### Structured Logging Substrate

Unified structured logging is enforced across client and server using `createPhaseLogger`:
- **Standard Phase Tags:**
  - `[ROUTE]`: Client intent routing (latency, intent, confidence, language, query length).
  - `[RETRIEVE]`: Retrieval execution (modality statuses, returned chunks, traversed edges, snapshot ID).
  - `[TOOL]`: Operational tool calls (tool name, parameters, execution outcome, mutation confirmation).
  - `[SYNTHESIS]`: Grounded synthesis (claim count, citation count, hypothesis count, confidence).
  - `[PUBLISH]`: Graph build lifecycle (candidate preparation, validation, activation, rollback).
- **Correlation ID:** Generated on the client per user turn (`x-correlation-id`) and propagated across all HTTP requests and server logs.
- **Data Privacy Invariant:** Raw prompts, user queries, full document excerpts, credentials, and DLP findings must never be logged. Only safe identifiers, counts, statuses, and durations are recorded.

### Kubernetes Deployment Configuration

Update `k8s/knowledge-server.yaml`:
1. **Embedding Model:** Configure explicit embedding parameters via ConfigMap/Secret. Default to local ONNX (`Xenova/multilingual-e5-small`).
2. **Prose Extraction:** Configure remote endpoint, model, and API key via Secret.
3. **Health Probes:**
   - **Liveness:** Simple HTTP `/health/liveness` verifying the Node.js process is responsive.
   - **Readiness:** HTTP `/health/readiness` verifying active Neo4j connectivity and vector index status without leaking sensitive database metadata.

### Smoke Acceptance CLI

Implement a headless CLI runner in `knowledge-server/src/acceptance/cli.ts` using Node `util.parseArgs`:
```bash
npm --prefix knowledge-server run smoke:cli -- --endpoint http://localhost:8080 --set-id <SET_UUID> --strict
```
- Parses `--endpoint`, one or more `--set-id`, `--strict`, optional output path, and safe timeout/budget flags.
- Executes `runSmokeCases` using the real federated request shape: `setTierAssignments`, per-set/global budgets, and comparison mode.
- Strictly parses every response with the shared retrieval response schema before assertions.
- In `--strict` mode, asserts each case's `expectedIntent`, `expectedFastPath`, expected outcome, required path presence/order, and fact-to-chunk citation closure. Current `smokeRunner.ts` omission of `expectedIntent` checks must be fixed.
- Outputs metadata-only JSON results (zero queries, excerpts, credentials, or document bodies).
- Returns process exit code 0 only when all assertions pass; returns 1 on schema or expectation mismatch and 2 on CLI/config misuse.

1. Upgrade GitHub Actions runners to Node.js 24 LTS.

## 11. Security Constraints & DLP Safeguards

1. **Client-Side DLP Scan:** Document publishing strictly requires a pre-send DLP scan for credit card PANs, CVVs, credentials, and private keys. All detected findings must be confirmed by the user before any content is transmitted to the knowledge daemon.
2. **Secret Redaction:** Passwords, API tokens (9router, Neo4j, GitHub), and DLP match values must never appear in application logs, error traces, or serialized JSON files.
3. **Host Allowlists & CORS:** The knowledge server enforces strict origin allowlists for browser clients and validates remote endpoint URLs against an approved host allowlist.
4. **Cypher Injection Prevention:** Traversal queries use pre-compiled static templates with strictly parameterized inputs. String concatenation of Cypher queries is prohibited.
5. **Snapshot Isolation:** Queries are pinned to authorized snapshot IDs. No query may inspect uncommitted candidate data or other document sets.

## 12. Real-Data Canary Protocol & Acceptance Verification Matrix

Verification must be conducted against real Neo4j 5.x, real 9router endpoints, and existing pilot documents. Synthetic mocks alone are insufficient for phase sign-off.

### Canary Publication Protocol

1. **Baseline Audit (Read-Only):** Record existing active snapshot ID, entity/relation counts, and index statuses.
2. **Canary Set Creation:** Create a new dedicated Document Set with a distinct UUID (e.g., `canary-validation-set`).
3. **DLP & Prepare:** Run client DLP check, upload documents, and trigger candidate preparation.
4. **Candidate Verification:** Verify vector embeddings are generated (384 dimensions), prose extraction produces inferred facts, and candidate retrieval succeeds without modifying the production active snapshot.
5. **Activation & Rollback Test:** Activate the canary set, verify retrieval against the new active snapshot, trigger an immediate rollback to the previous snapshot, confirm rollback success, and finally re-activate the verified candidate.
6. **Restart Target:** When authenticated remote `KUBECONFIG` is available, restart the Kubernetes Deployment/StatefulSet and verify persistence. Otherwise, use authorized local Docker/process restart of knowledge-server and Neo4j. Record which target ran; absence of both targets blocks UAT-07 rather than silently skipping it.

## 13. Release Gates & Production-Ready Definition

### Release Gates

All seven release gates must be fully satisfied before Phase 19.2 is approved:

1. **Build Gate:** `npm run build` (root) and `npm --prefix knowledge-server run build` compile cleanly with zero TypeScript errors.
2. **Automated Unit & Integration Gate:** `npm run test:all` executes all root and server Vitest test suites with 100% passing tests (zero skipped due to regressions, zero pre-existing test failures tolerated).
3. **Browser E2E Gate:** Playwright test suite passes covering client intent state machine, clarification loop, mutation confirmation modal, grounded citation clicks, and daemon-down local fallback.
4. **Smoke CLI Gate:** Headless acceptance CLI passes against real 9router and real Neo4j, emitting a clean `19.2-SMOKE-EVIDENCE.json` artifact.
5. **Canary Lifecycle Gate:** Canary document set build, validation, activation, rollback, and re-activation succeed without mutating the production active snapshot.
6. **Live Acceptance Matrix Gate:** All 16 live test scenarios (T1–T16) pass against real infrastructure.
7. **Security & Privacy Gate:** Automated audit confirms zero logged secrets/tokens, zero raw query leaks in metadata, parameterized Cypher verification, and successful encrypted backup round-trip with the `knowledgeLinks` schema migration.

### Policy on Production-Ready Claims

> **Mandatory Policy:** Under no circumstances shall Phase 19.2, its pull requests, documentation, or commit messages declare the AI Assistant or GraphRAG system "production-ready" until all seven release gates above have been executed and verified. Any outstanding red gate or unverified scenario blocks phase completion.

## 14. Error Taxonomy

| Error Code | Layer | Root Cause | Recovery / System Action | User Facing Message |
|---|---|---|---|---|
| `INTENT_LLM_UNAVAILABLE` | Client | 9router unreachable or unconfigured | Fail-closed: halt turn, abort tools | *"Tính năng AI hiện không khả dụng do không thể kết nối tới máy chủ AI. Vui lòng kiểm tra cài đặt hoặc thử lại sau."* |
| `INTENT_SCHEMA_INVALID` | Client | LLM output violates Zod taxonomy after 1 retry | Fail-closed: halt turn, log validation issue | *"Không thể xác định mục đích yêu cầu. Trạng thái an toàn đã được kích hoạt."* |
| `CLARIFY_CYCLE_EXCEEDED` | Client | Ambiguous query persists after 2 clarify turns | Halt clarify loop; prompt user for full restatement | *"Yêu cầu chưa đủ rõ ràng sau 2 lần làm rõ. Vui lòng đặt lại câu hỏi với thông tin cụ thể hơn."* |
| `MUTATION_REJECTED` | Client | User cancels mutation confirmation modal | Abort Dexie transaction; retain chat context | *"Đã hủy thao tác theo yêu cầu của bạn."* |
| `DAEMON_UNREACHABLE` | Client | Knowledge server down; LLM alive | Fallback: execute local IndexedDB BM25 | *"Máy chủ tri thức không khả dụng. Đang hiển thị kết quả từ tài liệu cục bộ."* |
| `SYNTHESIS_VALIDATION_FAILED` | Client | LLM claims lack matching evidence citations | Move invalid claims to unsupportedParts; retry once | *"Kết quả tổng hợp được bảo đảm dựa trên bằng chứng đã xác minh."* |
| `CANDIDATE_BUILD_FAILED` | Server | AST error, embedding failure, or index offline | Retain active snapshot; mark candidate FAILED | *"Quá trình biên dịch đồ thị thất bại. Phiên bản hiện tại vẫn được giữ an toàn."* |
| `ROLLBACK_EXPIRED` | Server | Rollback requested after grace period has elapsed | Reject rollback request; require rebuild | *"Thời hạn hoàn tác phiên bản đồ thị đã hết hạn."* |
| `ENTITY_AMBIGUOUS_UNRESOLVED` | Server | Multiple URNs match; planner cannot resolve | Emit `NEEDS_CLARIFICATION` with safe options | *"Phát hiện nhiều đối tượng phù hợp. Vui lòng làm rõ ngữ cảnh."* |
| `CYPHER_TRAVERSAL_TIMEOUT` | Server | Graph traversal exceeds configured timeout | Truncate traversal; return partial path with flag | *"Truy vấn đồ thị vượt quá thời gian cho phép; hiển thị kết quả một phần."* |
