## 1. System Classification & Architectural Boundaries

### 1.1 Classification
- **System Type:** Hybrid Natural-Language Intent Router + Deterministic Tool Orchestrator + Plan-Driven Multi-Modal GraphRAG + Grounded Synthesis Engine.
- **Audience:** Single personal user interacting in natural Vietnamese or English.
- **Provider Protocol:** Provider-neutral OpenAI-compatible HTTP interface via 9router (`/v1/chat/completions`). Uses strict JSON schema structured outputs (`response_format: { type: "json_schema", json_schema: { strict: true, ... } }`).
- **Core Value:** Eliminate heuristic bypasses; guarantee LLM-first intent classification; enforce evidence-backed grounded truth; prevent hallucination through strict schema closure; maintain local offline resilience.

### 1.2 Separation of Model Responsibilities vs. Deterministic Validation

To prevent prompt drift and silent corruption, the system enforces a strict boundary between probabilistic model inference and deterministic runtime guards:

| Subsystem | Model Responsibility (Probabilistic) | Deterministic Validation & Runtime Guard (Strict) |
|---|---|---|
| **Intent Routing** | Classifies query into exactly one of 5 canonical intents; extracts entities; detects language; formulates clarification question; detects explicit speculation request. | Validates strict JSON schema with Zod; enforces single schema-repair retry; stops pipeline on failure with `IntentRouterUnavailableError`; blocks keyword/verb list fallbacks; sanitizes clarify state. |
| **Clarification Loop** | Generates natural follow-up question in user's language specifying missing information. | Caps clarification loop at maximum 2 turns; preserves full transcript; merges follow-up with original query; suppresses manual bypass chips; renders live accessible status. |
| **Tool Orchestration** | Proposes function call names and arguments matching schema. | Identifies mutation tools via `isMutationTool`; intercepts and prompts for explicit user confirmation via `describeToolMutationWithContext`; manages Dexie IndexedDB transactions; resets streaming buffer per iteration; prevents post-tool duplicate synthesis. |
| **Query Planning & Disambiguation** | Evaluates candidate entities provided by server; selects best matching URN from candidate allowlist; determines traversal direction and step count. | Rejects URNs not in candidate allowlist; enforces traversal step cap (max 5); validates Cypher template whitelist; parameters only, zero string interpolation. |
| **Grounded Synthesis** | Synthesizes response from supplied evidence pack; aligns conclusions with claims; flags speculation into `hypotheses` array when requested. | Enforces `GroundedAnswerSchema` (v2); validates citation closure (`S*`/`L*`); validates path derivation (`P*`); demotes uncited claims to `unsupportedParts`; blocks `hypotheses` if `speculation_requested=false`; validates relation-backed supersession. |
| **Data Authority & Storage** | Summarizes personal task data and knowledge graph projections. | IndexedDB is canonical TaskMate store; Neo4j is derived rebuildable projection; TaskMate↔Knowledge links use stable UUIDs with cascade deletion; server validates hinted URNs against active snapshot. |
| **Observability** | None. | Redacts API keys, bearer tokens, passwords, and DLP sensitive data; emits structured metadata logs with correlation IDs; blocks raw query/document logging in release artifacts. |

## 2. Intent Routing Contract & Schema

Every user interaction begins with LLM intent reasoning. No regex, verb list, keyword heuristic, or manual route bypass button may circumvent this gate.

### 2.1 Fixed App Taxonomy

The intent taxonomy is strictly fixed to five values:
1. `operate_taskmate`: Mutate personal work data (create/update/delete task, project, milestone, timer, allocation, knowledge link).
2. `query_taskmate`: Read/query personal work data or progress status (e.g., "tình hình click to pay như nào rồi", "what is due today").
3. `query_knowledge`: Read documented processes, technical flows, architectures, database objects, or bare technical identifiers (e.g., `MAIN1.FCL_CYCLE_COUNTER`, `60000006`).
4. `mixed`: Query combining both personal task/project state and documented knowledge (e.g., "xem quy trình 60000006 rồi tạo task review cho tôi").
5. `clarify`: Ambiguous or underspecified queries requiring user disambiguation before action can be taken.

### 2.2 Strict Intent JSON Schema

```typescript
import { z } from 'zod';

export const INTENT_TAXONOMY = [
  'operate_taskmate',
  'query_taskmate',
  'query_knowledge',
  'mixed',
  'clarify',
] as const;

export type IntentLabel = (typeof INTENT_TAXONOMY)[number];

export const IntentResultSchema = z.strictObject({
  intent: z.enum(INTENT_TAXONOMY),
  confidence: z.number().min(0).max(1),
  entities: z.array(z.string().trim().min(1).max(200)).max(20),
  language: z.string().trim().min(2).max(16),
  needs_clarification: z.boolean(),
  clarify_question: z.string().trim().min(1).max(500).nullable(),
  speculation_requested: z.boolean(),
});

export type IntentResult = z.infer<typeof IntentResultSchema>;
```

### 2.4 One-Attempt Repair & Fail-Closed Semantics

1. **Attempt 0 (Standard Execution):** Send user query with `INTENT_SYSTEM_PROMPT` and `response_format`.
2. **Attempt 1 (Repair Prompt):** If JSON parsing fails or Zod validation fails, send original messages plus repair prompt:
   `"Your previous reply violated the strict JSON schema. Return ONLY a valid JSON object matching the required schema with keys: intent, confidence, entities, language, needs_clarification, clarify_question, speculation_requested."`
3. **Fail-Closed Gate:** If Attempt 1 fails, or if 9router endpoint is unreachable, timed out, or unconfigured:
   - Throw `IntentRouterUnavailableError`.
   - UI catches `IntentRouterUnavailableError` immediately.
   - Halt turn execution: **DO NOT** fall back to BM25, **DO NOT** execute tools, **DO NOT** mutate database.
   - Display accessible error message: *"Trợ lý AI hiện không khả dụng. Vui lòng kiểm tra cấu hình kết nối AI."* with retry and settings action.

## 3. Clarification Transcript & State Machine

Clarification must engage the user naturally through dialogue without manual route buttons.

### 3.1 Clarification State Schema
```typescript
export interface ClarifySessionState {
  originalQuery: string;
  clarifyQuestion: string;
  turnCount: number; // Max 2
  detectedLanguage: string;
}
```

### 3.2 Clarification Lifecycle & Max-Loop Guard
1. **Trigger:** `routeIntent()` returns `{ intent: "clarify", needs_clarification: true, clarify_question: "..." }`.
2. **Display:** Present assistant message containing exact `clarify_question` with `role="status"` and live region announcement.
3. **Capture User Response:** The next user message is treated as clarification input:
   - Increment `turnCount` after each user clarification answer.
   - Allow at most 2 clarification answers. If routing still returns `clarify` after the second answer (`turnCount >= 2`), abort with: *"Không thể xác định yêu cầu sau 2 lần làm rõ. Vui lòng đặt lại câu hỏi đầy đủ hơn."* Clear state.
   - Form merged query: `${state.originalQuery}\n[Thông tin bổ sung]: ${userReply}`.
4. **Re-Entry:** Merged query re-enters standard `routeIntent()` pipeline.
5. **Route Chip Deletion:** Generic operational and knowledge route-picker chips (`routeOverride`) are completely removed from UI. The LLM remains sole arbiter of intent.

## 4. Tool & Mutation Execution Policy

### 4.1 Categorization: Read Tools vs. Mutation Tools

| Tool Category | Tools | Execution Policy |
|---|---|---|
| **Read Tools** | Existing non-mutating tools, including `query_tasks`, `query_projects`, `query_milestones`, `get_item_details`, `query_worklogs`, `get_active_timer`, `get_daily_schedule`, `get_analytics_summary`, `query_notes`, `get_item_insight`, `generate_standup_report`, and knowledge read tools | **Direct Execution:** Executes immediately against IndexedDB or approved read-only retrieval; no user confirmation prompt required. |
| **Mutation Tools** | Existing tools recognized by `isMutationTool`, including `create_task`, `update_task`, `delete_task`, `reparent_task`, project/milestone changes, `plan_allocation`, work-session/timer changes, capacity changes, note/document changes, reminders, and `link_document`/`unlink_document`; Phase 19.2 adds `link_knowledge_entity`/`unlink_knowledge_entity` to the same registry | **Confirmation Gate:** Execution HALTS before invoking tool. Renders interactive confirmation card via `describeToolMutationWithContext`. Executes ONLY upon explicit user approval button click. |

### 4.2 Stable TaskMate ↔ Knowledge Links

Knowledge links connect TaskMate items (`task`, `project`, `milestone`) to knowledge documents and Neo4j graph entities.

```typescript
export interface KnowledgeLink {
  id: string; // crypto.randomUUID()
  entityType: 'task' | 'project' | 'milestone';
  entityId: string; // UUID of TaskMate item
  knowledgeSetId: string; // UUID of DocumentSet
  graphUrn?: string | undefined; // Stable URN (e.g., "urn:plannermate:smartvista:PRC_PROCESS:60000006")
  documentId?: string | undefined; // UUID of source document
  displayLabel: string;
  createdAt: string; // ISO 8601
  updatedAt: string; // ISO 8601
}
```

- **Tools Added:**
  - `link_knowledge_entity(entityType, entityId, knowledgeSetId, graphUrn, documentId, displayLabel)` (Mutation)
  - `unlink_knowledge_entity(linkId)` (Mutation)
- **Cascade Behavior:** Deleting a task deletes its links in the same Dexie transaction. Deleting a milestone or project deletes links for that entity and every descendant milestone/task in the same transaction, matching existing domain cascade semantics.
- **Retrieval Context:** When user chats with an active task/project scope, linked URNs are passed to `/api/v1/retrieve` as candidate hints. Server verifies hinted URNs against active snapshot; stale hints degrade gracefully to standard resolution.

### 4.3 Streaming Buffer & Multi-Turn Hygiene
- Reset streaming text buffer at the start of each tool execution cycle.
- When tool returns final answer or execution completes, suppress redundant secondary post-tool synthesis calls to eliminate duplicate responses in chat drawer.

## 5. Grounded Synthesis Contract & Schema

Grounded synthesis translates retrieved chunks and graph paths into an immutable, verifiable response.

### 5.1 Grounded Answer Schema (v2)

All new synthesis output MUST use v2. Persisted reads use `z.discriminatedUnion('schemaVersion', [GroundedAnswerSchemaV1, GroundedAnswerSchemaV2])`; historical v1 messages normalize only for display with `confidence: 'unknown'`, a historical-schema reason, and `hypotheses: []`. Stored historical payloads remain unchanged.

```typescript
import { z } from 'zod';

export const ConfidenceLevelSchema = z.enum(['high', 'medium', 'low', 'unknown']);

export const GroundedClaimSchemaV2 = z.strictObject({
  id: z.string().regex(/^C[1-9][0-9]*$/),
  text: z.string().min(1).max(1000),
  classification: z.enum(['DIRECT', 'INFERRED']),
  citationIds: z.array(z.string().regex(/^(S|L)[1-9][0-9]*$/)).min(1).max(8),
  pathId: z.string().regex(/^P[1-9][0-9]*$/).nullable(),
});

export const HypothesisClaimSchema = z.strictObject({
  id: z.string().regex(/^H[1-9][0-9]*$/),
  text: z.string().min(1).max(1000),
  justification: z.string().min(1).max(500),
});

export const GroundedAnswerSchemaV2 = z.strictObject({
  schemaVersion: z.literal(2),
  language: z.string().min(2).max(16),
  conclusion: z.string().min(1).max(2000),
  confidence: ConfidenceLevelSchema,
  confidenceReason: z.string().min(1).max(500),
  claims: z.array(GroundedClaimSchemaV2).max(15),
  hypotheses: z.array(HypothesisClaimSchema).max(5),
  unsupportedParts: z.array(z.string().min(1).max(500)).max(5),
});

export type GroundedAnswerV2 = z.infer<typeof GroundedAnswerSchemaV2>;
```

### 5.2 Deterministic Schema Closure & Validation Rules

1. **Path Closure:**
   - If `claim.classification === 'INFERRED'`, `claim.pathId` MUST be non-null and match a validated path `P*` in `EvidencePack`.
   - If `claim.classification === 'DIRECT'`, `claim.pathId` MUST be null.
2. **Citation Closure:**
   - Every citation ID in `claim.citationIds` MUST exist in `EvidencePack.citations` (`S1..Sn` for server, `L1..Ln` for local).
   - Plan 19.2-03 removes `fallbackCitationId` injection and default `C1` generation from `src/services/ai/groundedSynthesis.ts`. Missing citations never inherit the first allowlisted ID.
   - One bounded repair may use closure errors and the unchanged allowlist. If output remains invalid, reject raw answer and render safe synthesis failure plus validated evidence; do not fabricate a claim or citation.
3. **Speculation Closure:**
   - If `speculation_requested === false`: `hypotheses` array MUST be empty (`[]`). Any hypothesis returned by the model is stripped or triggers repair.
   - If `speculation_requested === true` and `hypotheses.length > 0`: `confidence` MUST be `'low'`. Hypotheses are rendered under a separate "Giả thuyết / Suy đoán" badge and NEVER receive citation IDs.
4. **No-Evidence Contract:**
   - When `EvidencePack.citations.length === 0`:
     - `conclusion` MUST clearly state no evidence was found in available documents or graph.
     - `confidence` MUST be `'unknown'`.
     - `claims` MUST be `[]`.
     - If `speculation_requested === false`, `hypotheses` MUST be `[]`.
     - Zero hallucinated facts permitted.
5. **Supersession Validation:**
   - Ordinary linguistic markers (e.g., Vietnamese "thay thế", English "replaces") DO NOT validate supersession.
   - A supersession claim requires structured document-set `scopeProof.overrideRelation === 'SUPERSEDES'` with intersecting citations, or cited evidence classified as a policy change, release note, or migration record. `SUPERSEDES` is scope metadata, not a domain relation in `RelationTypeSchema`.

```markdown
You are the Grounded Synthesis Engine for TaskMate. Your sole job is to answer the user query STRICTLY based on the provided EVIDENCE PACK.
You must return a valid JSON object matching GroundedAnswerSchemaV2 (schemaVersion: 2).
Never guess or introduce external training facts not present in EVIDENCE.

INPUT STRUCTURE:
- QUERY: User's question.
- SPECULATION_REQUESTED: true | false.
- EVIDENCE:
  - Citations: [ { id: "S1", title: "...", excerpt: "..." }, ... ]

RULES:
1. "language": Respond in the query's language ("vi" or "en"). Source code, URNs, technical identifiers, and direct quotes must remain verbatim.
2. "conclusion": High-level synthesis directly answering the query.
3. "confidence":
   - "high": Query answered completely with direct evidence from authoritative documents or verified graph paths.

   - If SPECULATION_REQUESTED is false, this array MUST be empty [].
   - If SPECULATION_REQUESTED is true, you may propose reasonable hypotheses based on domain context, each with a "justification". Hypotheses have NO citationIds.
7. "unsupportedParts": Information requested by user that has no supporting evidence in the pack.

NO-EVIDENCE RULE:
If EVIDENCE is empty or contains no relevant facts:
```

## 6. Safe Observability & DLP Logging Standards

All logging must be strictly safe for banking-adjacent and private personal environments.

### 6.1 Phase Logger Chokepoints

Structured logs are emitted via `createPhaseLogger` across 5 designated chokepoints:
1. `[ROUTE]`: Client intent routing entry, schema outcome, repair status, latency.
2. `[RETRIEVE]`: Client retrieval request, set IDs, candidate URNs, modality return status.
3. `[TOOL]`: Client tool execution start, mutation gate prompt, user decision, execution result status.
4. `[SYNTHESIS]`: Client synthesis attempt, token usage, closure validation outcome, confidence rating.
5. `[SERVER_RETRIEVE] / [SERVER_PUBLISH]`: Knowledge server query planning, candidate disambiguation, candidate build, activation/rollback.

### 6.2 Data Sanitization & Redaction Rules
- **API Keys / Bearer Tokens:** Replaced with `'***'` via `redactApiKey()`. Never logged in headers, bodies, or query strings.
- **DLP / Document Excerpts:** Full document text, sensitive table rows, and raw prompt bodies MUST NOT be written to console or persistent log stores.
- **Allowed Safe Log Metadata:**
  - `correlationId`: UUID tracing the user turn across client and server.
  - `phase`: Chokepoint name.
  - `intent`: One of 5 taxonomy strings.
  - `confidence`: Numeric score or enum.
  - `latencyMs`: Elapsed milliseconds.
  - `tokenUsage`: `{ inputTokens: number, outputTokens: number }`.
  - `counts`: Number of citations, claims, entities, paths, hypotheses.
  - `errorCodes`: Standard error enums (`MODEL_UNAVAILABLE`, `SCHEMA_REJECTED`, `TIMEOUT`, `NO_EVIDENCE`).

### 7.3 Failure Modes & Recovery Catalog

### 8.2 Canary Document Set & Safe Rollback Protocol

To protect the active production graph:
1. **Canary Set Creation:** Create dedicated Document Set with new UUID (`canary-set-id`).
2. **Import & DLP Check:** Import pilot documents into canary set; execute client-side DLP check (0 leaks).
3. **Candidate Build:** Run `prepareCandidate` without activating. Verify:
   - Nonzero entities, facts, and chunks created.
   - Vector embeddings generated for chunks using production embedding provider.
   - Inferred facts produced via prose extraction for table-less text.
4. **Candidate Verification:** Run retrieval acceptance checks against candidate snapshot ID directly.
5. **Atomic Activation:** Compare-and-swap candidate snapshot to `ACTIVE`. Store previous snapshot ID.
6. **Rollback Exercise:** Invoke `rollbackCandidate`. Verify previous snapshot immediately restored.
7. **Reactivation:** Reactivate accepted candidate snapshot.
