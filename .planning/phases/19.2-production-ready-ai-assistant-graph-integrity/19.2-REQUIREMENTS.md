## 1. Executive Summary

Phase 19.2 turns TaskMate's AI assistant and hybrid graph retrieval into a production-ready, trustworthy system for one personal user. Every user turn starts with LLM intent reasoning against a strict 5-intent contract (`operate_taskmate`, `query_taskmate`, `query_knowledge`, `mixed`, `clarify`) with no heuristic keyword/verb shortcuts. Material claims require immutable citations. Honest uncertainty produces explicit `NO_EVIDENCE`, and hypotheses are isolated to explicit user requests. Graph rebuilds enforce embedding/prose injection, two-phase candidate activation, and rollback. Plan-driven Neo4j traversal traverses validated paths with real chunk closure. TaskMate tasks link durably to knowledge entities. Real Neo4j and 9router live acceptance gates—including all 9 failed, blocked, or skipped gates from Phase 19.1 UAT—must pass before completion.

## 3. Detailed Requirements & Acceptance Criteria

### 3.1. LLM-First Intent Routing & Conversational State Machine (`INTENT-*`)

- **INTENT-01: Mandatory LLM-first intent classification with fixed 5-intent taxonomy**  
  Every user message in AI Chat Drawer must be classified by an LLM reasoning call into exactly one intent: `operate_taskmate`, `query_taskmate`, `query_knowledge`, `mixed`, or `clarify`. There shall be zero keyword lists, verb lists, regex rules, or deterministic heuristics for intent classification. Technical identifiers (e.g., `MAIN1.FCL_CYCLE_COUNTER`) are classified as `query_knowledge` via prompt instructions and few-shot examples.  
  *Acceptance Criteria:*
  1. Automated tests verify `DEFAULT_OPERATIONAL_VERBS`, `DEFAULT_KNOWLEDGE_HINTS`, and `matchTerms` do not exist in the codebase.
  2. Queries in Vietnamese, English, and technical shorthand route to the correct intent using LLM reasoning only.
  3. Technical identifiers without surrounding text route to `query_knowledge` (not `clarify`).

- **INTENT-02: Fail-closed behavior on LLM unavailability**  
  If the LLM endpoint is unconfigured, unreachable, or returns invalid schema after one bounded repair attempt, the turn halts immediately. The UI renders an accessible error state (`AI unavailable`) with retry/settings action. No tools, mutations, or local BM25 synthesis execute when the LLM is down.  
  *Acceptance Criteria:*
  1. When LLM returns HTTP 5xx, network error, or invalid JSON after 1 retry, `IntentRouterUnavailableError` halts the turn.
  2. Zero TaskMate tool calls, zero mutations, and zero IndexedDB BM25 synthesis calls occur.
  3. The chat UI clearly indicates AI services are unavailable and provides an actionable retry/config button.

- **INTENT-03: Graceful local BM25 fallback on knowledge server / Neo4j failure**  
  If LLM intent succeeds as `query_knowledge` or `mixed`, but the knowledge server or Neo4j is disabled, unreachable, or times out, the assistant falls back to local IndexedDB BM25 search over local notes/documents. The synthesized answer or evidence card must visibly state its local authority provenance (`[L#]` citations, Local badge).  
  *Acceptance Criteria:*
  1. Stopping the knowledge server daemon while LLM is active results in successful local BM25 retrieval without unhandled errors.
  2. Local evidence is rendered with distinct `Local` authority tags and local chunk identifiers.
  3. Offline search remains functional when daemon is completely absent.

- **INTENT-04: Exact conversational clarification loop without route bypass**  
  When intent is `clarify`, the assistant displays the model's exact `clarify_question` with `role="status"` live announcement. Generic operational/knowledge route chips and `routeOverride` are removed. When the user responds, their answer is combined with the original query (`{originalQuery}\n\nBổ sung: {answer}`) and re-enters the standard LLM intent classifier. Clarification turns are capped at 2 before terminating with actionable guidance.  
  *Acceptance Criteria:*
  1. Chat UI renders the exact string returned in `clarify_question` without generic chip buttons.
  2. Submitting an answer preserves both turns and submits combined context to `routeIntent`.
  3. Exceeding 2 successive `clarify` turns terminates the loop with an explicit guidance message.

- **INTENT-05: Single read tool path and tool-loop buffer hygiene**  
  When intent is `query_taskmate`, the system executes exactly one read tool path without redundant re-synthesis passes. The assistant text buffer resets cleanly on each tool iteration so intermediate messages do not duplicate or corrupt the final displayed response.  
  *Acceptance Criteria:*
  1. Status questions (e.g., "tình hình click to pay như nào rồi") trigger read tools without initiating knowledge-server retrieval.
  2. Response text contains zero duplicate sentences or merged multi-iteration buffer fragments.
  3. Completed tool responses display final synthesized text once.

### 3.2. Grounded Answer Synthesis & Truthfulness Contract (`TRUTH-*`)

- **TRUTH-01: Immutable chunk and range citations for material claims**  
  Every material factual claim synthesized by the assistant must reference valid, verified evidence chunks with source document title, published content hash, and source line/offset ranges.  
  *Acceptance Criteria:*
  1. Claims cite valid normalized citation IDs (`S#` for server evidence or `L#` for local evidence) present in the evidence pack.
  2. Interactive citation click opens `QuickPreviewDrawer` highlighting the exact source range from the published snapshot.
  3. Citations retain snapshot provenance across local document edits.

- **TRUTH-02: Structured answer confidence derived from evidence with historical compatibility**  
  New synthesis output schema v2 must produce `confidence` (`high | medium | low | unknown`) and concise evidence-based justification. Persisted reads accept historical v1 and new v2 grounded answers through a discriminated union; v1 normalizes for display to `unknown` confidence and empty hypotheses without rewriting stored history.  
  *Acceptance Criteria:*
  1. Output schema enforces `confidence` enum (`high`, `medium`, `low`, `unknown`) and `confidenceReason: string`, matching the normative AI schema.
  2. Conflicting sources or partial evidence automatically downgrade confidence to `medium` or `low`.
  3. Answers with zero evidence must report confidence `unknown`.

- **TRUTH-03: Explicit-only hypotheses and speculation isolation**  
  Speculative reasoning or hypotheses are isolated in a separate `hypotheses` array in the synthesis schema. Hypotheses are generated **only** if the user's prompt explicitly requests speculation (`speculation_requested: true` detected in intent). Hypotheses must carry `LOW` confidence, be visually labeled as unverified hypotheses, and never carry factual citations.  
  *Acceptance Criteria:*
  1. When `speculation_requested` is false, `hypotheses` is empty. Any speculative text in factual claims is rejected.
  2. When `speculation_requested` is true, generated hypotheses are rendered in a distinct visually tagged speculation block.
  3. Zero factual citations are attached to items in `hypotheses`.

- **TRUTH-04: Explicit abstention on missing evidence**  
  When retrieval returns no relevant evidence and the user did not request speculation, the assistant returns outcome `NO_EVIDENCE` with confidence `unknown`. The response explicitly states what information is missing and offers suggested refinements, without inventing or hallucinating facts.  
  *Acceptance Criteria:*
  1. Unreferenced queries (e.g., SWIFT MT103 in the pilot corpus) return `NO_EVIDENCE` without generating fictional entities or procedures.
  2. Output clearly indicates the lack of documented knowledge in the indexed set.

- **TRUTH-05: Strict citation repair without arbitrary fallback**  
  Output normalization may repair minor formatting inconsistencies (e.g., bracket syntax or whitespace) for valid cited chunk IDs, but shall never assign an arbitrary citation to an ungrounded claim. Invalid output receives at most one bounded closure repair; if still invalid, raw prose is rejected. Supersession requires structured document-set `scopeProof.overrideRelation === 'SUPERSEDES'` or cited policy/release/migration evidence, not mere lexical matches like `thay thế`.  
  *Acceptance Criteria:*
  1. Current `fallbackCitationId` injection and default `C1` generation in `groundedSynthesis.ts` are removed; claims citing nonexistent or absent evidence IDs are repaired against the unchanged allowlist or rejected, never assigned `S1`/`L1` automatically.
  2. After one bounded closure repair, remaining invalid raw output is rejected and safe validated evidence remains available; arbitrary claim demotion must not make invalid model output appear verified.
  3. `thay thế` in claim prose does not prove supersession unless matching structured document-set `SUPERSEDES` metadata or allowlisted cited evidence exists.

### 3.3. Graph Build Runtime, Two-Phase Activation & General Extraction (`BUILD-*`)

- [x] **BUILD-01: Explicit dependency injection for graph build runtime**  
  `GraphBuildService` in `knowledge-server` must receive explicit dependencies on initialization: `GraphRepository`, `SnapshotStore`, `EmbeddingProvider` (configured identically to the retrieval provider), and `ProseExtractionConfig`. Test-only fallback constructors with dummy providers are prohibited in the production runtime path.  
  *Acceptance Criteria:*
  1. `startKnowledgeServer` fails to start if vector embeddings are enabled but no valid `EmbeddingProvider` is injected.
  2. Prose extraction endpoint and credentials must be validated on startup when prose extraction is enabled.
  3. No unconfigured or silent in-memory stubbing occurs in production mode.

- [x] **BUILD-02: Two-phase candidate build and atomic pointer swap**  
  Graph rebuilds must execute in two distinct phases:
  1. `prepareCandidate`: Extracts structured tables and uncovered prose, generates vector embeddings, validates indexes, and marks candidate snapshot `READY`.
  2. `activateCandidate`: Atomic compare-and-swap promotes candidate snapshot to `ACTIVE` only after candidate retrieval smoke checks pass.  
  *Acceptance Criteria:*
  1. Rebuilding a graph does not alter the `ACTIVE` snapshot pointer until all validation steps pass.
  2. Candidate snapshot can be queried in isolation during pre-activation smoke checks.
  3. Failed candidate builds leave the prior `ACTIVE` snapshot intact and fully queryable.

- [x] **BUILD-03: Authenticated candidate rollback and grace period**  
  The system must retain the prior active snapshot during a configurable rollback grace period exposed by server status. No client-side default duration is assumed. An authenticated, idempotent API endpoint (`POST /api/v1/sets/:setId/graph/rollback`) allows an operator to instantly revert the active pointer to the previous snapshot.  
  *Acceptance Criteria:*
  1. Executing rollback swaps the active pointer back to the previous snapshot ID immediately.
  2. Retrieval queries immediately reflect the reverted snapshot without service restart or re-indexing.
  3. Rollback endpoint rejects requests once the grace period expires or if no prior snapshot exists.

- [x] **BUILD-04: Non-destructive snapshot cleanup with lease safety**  
  Cleanup routines must never delete snapshot entities, facts, evidence records, or chunks while active read leases or rollback grace windows remain active. Deletion must cleanly remove all snapshot-scoped entities without leaving orphan nodes.  
  *Acceptance Criteria:*
  1. Rebuild cleanup queries verify zero active leases and expired rollback grace before deleting prior snapshot data.
  2. Deletion Cypher queries remove nodes, relationships, and vector embeddings scoped strictly to the target snapshot ID.
  3. Production and sibling document set snapshots are never affected by cleanup operations.

- **BUILD-05: General document extraction without hardcoded constants**  
  Remove hardcoded procedure names, container constants, and pilot-specific shortcuts from `knowledge-server/src/graph/extraction.ts`. Deterministic extraction must parse structured tables based on heading and column schema. Uncovered paragraphs and tables must route through prose extraction with closed ontology constraints and exact quote evidence.  
  *Acceptance Criteria:*
  1. Grep verification confirms zero hardcoded procedure names (e.g. `PRC_FCL_CALCULATE_LIMIT`) exist in extraction code.
  2. Non-SHB and table-less Markdown fixtures extract valid entities, facts, and evidence chunks.
  3. Extracted prose facts carry `INFERRED` classification and exact source line/offset ranges.

### 3.4. Plan-Driven Neo4j Traversal & Disambiguation Integrity (`RETR-*`)

- **RETR-06: Idempotent Neo4j schema constraints and retrieval indexes**  
  Neo4j initialization must create idempotent constraints and indexes: composite keys for `(graphSnapshotId, urn)`, `(graphSnapshotId, normalizedKey)`, canonical names, fact keys, evidence facts, and full-text/vector indexes on chunks.  
  *Acceptance Criteria:*
  1. `initializeSchemaConstraints` executes idempotently without errors on existing or restarted databases.
  2. Full-text index on chunks supports technical identifier lookup.
  3. Native Neo4j vector index matches embedding provider model dimensions (e.g. 384 for `multilingual-e5-small`).

- **RETR-07: Fact-to-chunk evidence closure (`SUPPORTED_BY`)**  
  During candidate graph build, every evidence record must be linked to its overlapping immutable evidence chunks (same document and line/offset range) via snapshot-scoped `SUPPORTED_BY` edges or persisted chunk-key links.  
  *Acceptance Criteria:*
  1. Every traversed fact edge returned by Neo4j resolves to at least one valid chunk ID.
  2. Retrieval responses contain full chunk metadata (document title, hash, line numbers) for every graph step.
  3. No citationless graph edges are returned in path traversal cards.

- **RETR-08: Plan-driven multi-hop Cypher traversal**  
  Neo4j traversal must strictly execute the steps declared in `LogicalQueryPlan.traversalSteps`, adhering to relation type, direction (`OUTGOING`, `INCOMING`, `BOTH`), target kind, step hops, overall depth (<= 3), and snapshot pin. Remove all undirected catch-all 1-hop queries. Cypher queries must use parameterized templates with distinct-path semantics and node/edge caps (`maxNodes=100`, `maxEdges=200`).  
  *Acceptance Criteria:*
  1. Flow queries execute ordered `CONTAINS_STEP -> INVOKES -> CALLS` paths matching plan definitions.
  2. Impact queries traverse incoming dependency edges up to 3 hops.
  3. Undirected fallback queries are deleted from `neo4jRepository.ts`.

- **RETR-09: LLM entity candidate disambiguation without keyword filters**  
  Remove hardcoded keyword lists (`processKeywords`, `stepKeywords`, keyword->kind maps) from `queryPlanning.ts`. When an entity query yields multiple candidate URNs, the candidates (URN, kind, canonical name, safe 1-hop summary) are passed to the 9router planner's strict JSON schema. The planner selects from the candidate list or returns `NEEDS_CLARIFICATION`.  
  *Acceptance Criteria:*
  1. Grep verifies `processKeywords` and `stepKeywords` are deleted from `queryPlanning.ts`.
  2. Ambiguous terms (e.g., colliding process and container numeric IDs) are disambiguated by the LLM planner using context.
  3. If disambiguation is not possible, the planner returns `NEEDS_CLARIFICATION` with safe candidate URNs.

- **RETR-10: Cross-lingual Vietnamese ↔ English semantic retrieval**  
  Semantic vector retrieval must retrieve relevant English documentation from Vietnamese queries (and vice versa) using the multilingual embedding model (`multilingual-e5-small` or remote equivalent).  
  *Acceptance Criteria:*
  1. Natural-language Vietnamese queries over English documents return relevant English evidence chunks with high RRF ranking.
  2. Modality status reports `semanticStatus: 'ok'` with provider and model metadata.
  3. Synthesized answer is delivered in Vietnamese while preserving exact English quotes in citations.

### 3.5. First-Class TaskMate ↔ Knowledge Entity Links (`LINK-*`)

- **LINK-01: Dexie SCHEMA_V11 migration for `KnowledgeLink`**  
  Introduce a dedicated IndexedDB table `knowledgeLinks` in `SCHEMA_V11`, migrating from verified live `SCHEMA_V10`, with fields: `id` (UUID), `entityType` (`task | project | milestone`), `entityId` (UUID), `setId` (UUID), `graphUrn` (optional string), `documentId` (optional UUID), `displayLabel` (string), `createdAt`, `updatedAt`. Migration preserves all existing local data. If another change occupies V11 before execution, Plan 19.2-07 must stop and rebase the reserved migration version.  
  *Acceptance Criteria:*
  1. Dexie upgrades smoothly from V10 to V11 without data loss or schema errors.
  2. Multi-entry indexes allow fast querying by `entityId`, `entityType`, and `setId`.
  3. Unit tests verify migration, CRUD operations, and transaction boundaries.

- **LINK-02: Cryptographic backup round-trip and cascade cleanup**  
  `KnowledgeLink` records must serialize in cryptographic backup exports with schema validation and restore cleanly. Deleting a task, project, or milestone cascades to delete all associated knowledge links.  
  *Acceptance Criteria:*
  1. Backup export includes `knowledgeLinks` store; backup import validates records with Zod.
  2. Deleting a Task cascades deletion to its associated `KnowledgeLink` entries.
  3. Restoring backup into a clean database restores all link relationships.

- **LINK-03: AI linking tools with mutation confirmation**  
  Provide explicit AI tools (`link_taskmate_to_knowledge`, `unlink_taskmate_knowledge`) enabling the assistant to create or remove links between TaskMate items and knowledge documents or graph URNs. Linking actions must trigger the existing mutation confirmation dialog before execution.  
  *Acceptance Criteria:*
  1. The assistant can propose linking a task to a documented procedure or graph URN.
  2. The mutation preview modal displays entity details, target URN/document, and requires explicit user approval.
  3. No link is persisted until user confirms the dialog.

- **LINK-04: UI management in `LinkedKnowledgeSection`**  
  Enhance `LinkedKnowledgeSection` across Task, Project, and Milestone drawers to display linked documents and linked graph entities with badges, preview drawers, and unlink controls.  
  *Acceptance Criteria:*
  1. Task drawer lists linked knowledge entities with clear icons for documents vs graph URNs.
  2. Clicking a linked document opens `QuickPreviewDrawer`; clicking a graph URN displays entity summary.
  3. User can manually add or remove knowledge links via the UI.

- **LINK-05: Context retrieval hints and mixed evidence packs**  
  When AI chat is scoped to an item with knowledge links, the linked document IDs and graph URNs are passed as retrieval context hints. The server validates hinted URNs against the active snapshot; stale links degrade safely to standard resolution. Synthesized responses cleanly combine live TaskMate data with knowledge citations, explicitly labeling TaskMate facts as `Local TaskMate`.  
  *Acceptance Criteria:*
  1. Scoped chat requests include `contextUrns` derived from active knowledge links.
  2. Stale or deleted URNs in links do not cause server query failures.
  3. Mixed responses clearly distinguish TaskMate task attributes from external knowledge citations.

### 3.6. Observability, Kubernetes Probes & Test Automation Gates (`OPS-*`)

- **OPS-01: Structured logging chokepoints with strict secret redaction**  
  Implement structured logging using `createPhaseLogger` across key client chokepoints (`[ROUTE]`, `[RETRIEVE]`, `[TOOL]`, `[SYNTHESIS]`) and server chokepoints (`[RETRIEVE]`, `[PUBLISH]`). Every request generates and propagates a correlation ID. Logs contain timestamps, phase, outcome, latency, counts, and safe IDs only. Log redaction tests prove zero tokens, document excerpts, prompts, or DLP findings enter logs.  
  *Acceptance Criteria:*
  1. Correlation ID is generated on the client and forwarded via `X-Correlation-ID` header through retrieval and graph operations.
  2. Automated tests assert API keys, bearer tokens, passwords, and sensitive text are redacted.
  3. Structured logs can be parsed as JSON in production monitoring.

- **OPS-02: Kubernetes manifest hardening and readiness semantics**  
  Update `k8s/knowledge-server.yaml` and runbooks. Probes must separate liveness from readiness: readiness probe verifies Neo4j connectivity, required model availability, and online vector indexes via an internal authenticated health endpoint without leaking secret details. Restart acceptance supports two authorized targets: remote Kubernetes when authenticated `KUBECONFIG`/network access exists, or local Docker/process restart of both daemon and Neo4j. Execution evidence records the target used; no available target blocks the gate rather than converting it to a pass. TCP-only readiness is replaced.  
  *Acceptance Criteria:*
  1. Kubernetes manifests declare explicit readiness probe verifying internal services.
  2. Manifests contain zero plaintext or base64 passwords/tokens; secrets load from Kubernetes Secrets.
  3. Deployment runbook documents secret creation and manifest apply order.

- **OPS-03: Standalone metadata-only acceptance CLI**  
  Provide executable `knowledge-server/src/acceptance/cli.ts` using `node:util` `parseArgs` (zero external dependencies). CLI sends real federated requests with `setTierAssignments`, budgets, and comparison mode; strictly parses shared retrieval response schema; and asserts each case's expected intent, fast-path flag, outcome, required ordered paths, and fact-to-chunk closure. Output remains metadata-only.  
  *Acceptance Criteria:*
  1. Running `npm --prefix knowledge-server run smoke:cli -- --endpoint <url> --set-id <uuid> --strict` executes all smoke cases against configured server.
  2. `--strict` checks `expectedIntent` and `expectedFastPath` as well as citations, path order, closure, and outcome; any schema/expectation mismatch returns exit code 1.
  3. CLI/config misuse returns exit code 2.
  4. Output JSON contains timings, counts, safe IDs, and snapshot IDs with zero query text, excerpts, document bodies, or credentials.

- **OPS-04: Playwright browser end-to-end test suite**  
  Add Playwright as a dev dependency to validate critical browser UI flows: AI settings configuration, LLM intent state machine, clarification flow, AI unavailable state, TaskMate read/mutation confirmation dialogs, interactive citations, and daemon-down local BM25 fallback.  
  *Acceptance Criteria:*
  1. Playwright tests execute in headless Chromium in CI without flakiness.
  2. Tests verify user can complete clarification, confirm a mutation, and click a citation pill to open preview.
  3. Daemon unreachable scenario is verified end-to-end in real browser DOM.

## 4. Non-Functional & Security Requirements

1. **Local-First & Zero-Trust Runtime**: IndexedDB remains the canonical store for all personal data. Neo4j is strictly an optional projection. Credentials (API keys, tokens, passwords) never enter client storage, client bundles, or unredacted logs.
2. **Deterministic Cypher Safety**: Neo4j Cypher queries must exclusively use static parameterized templates. String interpolation of user input or relation types into Cypher statements is strictly prohibited.
3. **Bounded Latency**: LLM intent classification must complete within 2.5 seconds on standard network. Retrieval over Neo4j must complete within 1.5 seconds.
4. **Clean Code & Test Coverage**: Zero TypeScript build errors across root and `knowledge-server`. Full Vitest test suites green with no skipped or pre-existing failures. Zero compiler warnings on `strict: true`.
