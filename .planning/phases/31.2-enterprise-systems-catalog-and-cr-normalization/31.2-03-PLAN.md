<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| UI/Zod → repo | Repo is the last line of defence; UI-only checks are not trusted |
| repo → Dexie transaction | Multi-table writes must be atomic or a partial cascade orphans rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31.2-07 | Tampering | `systemRepo.createSystem`/`updateSystem` | mitigate | Parent-type, cycle and parent-has-no-repo assertions run on every write, so a direct repo call cannot create the illegal shapes the UI hides |
| T-31.2-08 | Tampering | `taskRepo.createTask`/`updateTask` | mitigate | `assertSystemInCrTargets` loads the CR and checks membership, so a stale subsystem id cannot be attached to a task |
| T-31.2-09 | Tampering | `changeRequestRepo` targets | mitigate | Existence + `isSubsystem` + uniqueness validated before write; a parent id can never enter `cr.targets` |
| T-31.2-10 | Denial of service | `deleteSystem` / `removeSubsystemFromChangeRequest` | mitigate | Both run in a single `db.transaction` over systems/changeRequests/tasks, so a partial failure cannot leave tasks pointing at a removed target |
| T-31.2-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this phase |
</threat_model>
