# Phase 31.2: Code Review Report

**Reviewed:** 2026-11-08
**Depth:** standard
**Files Reviewed:** 38
**Status:** issues_found

## Summary

Phase 31.2 collapses `Project`/`Milestone` into a CR-centric model and re-axes tasks onto `crId`/`systemId`. The repository layer does enforce D-24/D-25/D-26 on the *write* paths it owns, and the AI mutation surface still routes through the confirmation gate. But the phase leaves several invariant and data-safety holes:

- The Dexie v16 migration deletes tasks (and orphans their allocations, sessions and notes) with no user-visible warning, and leaves legacy `entityType`/`taskMateEntityType` values that the new backup schema rejects — so the app can produce a backup it cannot re-import.
- `updateChangeRequest` replaces `cr.targets` without clearing `task.systemId`, and `ChangeRequestModal` always re-sends targets without `featureBranch`, so any CR edit silently violates D-26 and wipes per-target feature branches.
- Backup import validates shape but not the new invariants, and the pre-import snapshot download writes every setting — including API tokens and passphrases — as plaintext JSON.
- SDLC workflow persistence now writes `sdlc_workflow:<crId>:<crId>` while the restore path and the chat drawer use `sdlc_workflow:<crId>:<threadId>`, so restored workflow state is invisible and checkpoint recovery never fires.
- Two navigation/selection bugs open the wrong CR (`SystemDetailView`) and the wrong repository (`Step3CodeGuideView`).

## Critical Issues

### CR-01: Replacing CR targets leaves tasks pointing at a subsystem that is no longer a target (D-26 broken)

**File:** `src/db/repositories/changeRequestRepo.ts:110-112` (also `:86-88`)
**Issue:** `updateChangeRequest` validates that the *new* targets are subsystems, then overwrites `updated.targets`. It never clears `Task.systemId` for tasks whose subsystem was removed. `removeSubsystemFromChangeRequest` does this correctly, but the general update path — used by `ChangeRequestModal`, `SdlcSidebar`, `CRExplorer`, `SystemDetailView` and the AI `update_change_request` tool — does not. After removing a subsystem from a CR, its tasks still carry `systemId` outside `cr.targets`, violating D-26 and producing a Select value that is not in `subsystemOptions` (`ChangeRequestDetailView.tsx:185-191`).
**Fix:** perform the target replacement and the task cleanup in one transaction, mirroring `removeSubsystemFromChangeRequest`:
```ts
if (validated.targets !== undefined) {
  const removed = existing.targets
    .map((t) => t.systemId)
    .filter((id) => !validated.targets!.some((t) => t.systemId === id));
  updated.targets = applyFeatureBranchDefaults(validated.targets, updated.code);
  await db.transaction('rw', [db.changeRequests, db.tasks], async () => {
    for (const systemId of removed) {
      await db.tasks.where('crId').equals(id)
        .filter((t: Task) => t.systemId === systemId)
        .modify((t: Task) => { delete t.systemId; });
    }
    await db.changeRequests.put(updated);
  });
  return updated;
}
```

### CR-02: Any CR edit through `ChangeRequestModal` resets every per-target feature branch

**File:** `src/components/changeRequests/ChangeRequestModal.tsx:213`
**Issue:** The modal always submits `targets: (values.targets ?? []).map((systemId) => ({ systemId }))` — `featureBranch` is never carried. `updateChangeRequest` then re-derives defaults for every target (`changeRequestRepo.ts:30-39,110-112`), so branches written by Step 3 (`ChangeRequestSdlcView.tsx:847-855`) are silently replaced with `feature/{code}` whenever the user edits the CR name, status or description. The repo comment at `:108-109` states the opposite intent.
**Fix:** preserve the existing branch per target when the modal did not change it:
```ts
// in updateChangeRequest
updated.targets = validated.targets.map((t) => {
  const prior = existing.targets.find((p) => p.systemId === t.systemId);
  return { systemId: t.systemId, featureBranch: t.featureBranch ?? prior?.featureBranch ?? `feature/${updated.code}` };
});
```

### CR-03: Dexie v16 migration silently deletes tasks that have no resolvable CR

**File:** `src/db/index.ts:327-346`
**Issue:** `Task.projectId` was optional in the pre-31.2 model, so standalone tasks (quick-add, tasks whose project was deleted) have no `projectId`. The migration deletes every such row (`tasksTable.delete(id)`) and reports it only via `console.warn`. There is no user confirmation and no snapshot is taken before an upgrade. This directly contradicts the phase's data-safety goal ("must not lose surviving rows").
**Fix:** do not delete. Park unresolvable tasks under a generated recovery CR (or keep them and let the UI surface them):
```ts
const fallbackId = 'legacy-unassigned';
if (!crIds.has(fallbackId)) {
  await changeRequestsTable.add({ id: fallbackId, code: 'CR-LEGACY-UNASSIGNED', name: 'Legacy unassigned tasks',
    status: 'Open', type: 'ENHANCEMENT', targets: [], createdAt: now, updatedAt: now });
  crIds.add(fallbackId);
}
task.crId = projectId !== undefined && crIds.has(projectId) ? projectId : fallbackId;
```

### CR-04: v16 leaves legacy `entityType` / `taskMateEntityType` values that the v11 backup schema rejects

**File:** `src/db/index.ts:312-402`; `src/validation/backupSchemas.ts:149,521`
**Issue:** The migration purges legacy chat threads and SSH settings but never rewrites `notes.entityType` (`'project'`/`'milestone'`) or `knowledgeLinks.taskMateEntityType` (`'project'`/`'milestone'`). The backup schemas only accept `['task','cr','system']`, so `exportBackupPayload` emits rows that `validateBackupPayload` rejects. The user's own backup becomes unimportable after the upgrade.
**Fix:** add a migration step that detaches or remaps those rows:
```ts
await tx.table('notes').toCollection().modify((n: Record<string, unknown>) => {
  if (n.entityType === 'project' || n.entityType === 'milestone') { delete n.entityType; delete n.entityId; }
});
await tx.table('knowledgeLinks').toCollection().modify((l: Record<string, unknown>) => {
  if (l.taskMateEntityType === 'project' || l.taskMateEntityType === 'milestone') l.taskMateEntityType = 'cr';
});
```

### CR-05: `BackupNoteRecordSchema` omits the `'diagram'` note type — diagram notes break backup round-trip

**File:** `src/validation/backupSchemas.ts:145`
**Issue:** `NoteType` includes `'diagram'` (`src/types/models.ts:192`) and diagrams are persisted with `type: 'diagram'` (`ItemInsightView.tsx:189-196`, `TaskDrawer.tsx:167-179`). The backup schema only allows `['quick_note','document','folder']`, so any workspace containing a diagram exports a backup that fails its own validation.

### CR-06: Backup import never validates D-24/D-25/D-26 — restore writes invariant-violating rows

**File:** `src/services/backup/validateBackup.ts:210-215, 222-560`
**Issue:** `systems` and `changeRequests` are shape-validated only. There is no check that (a) every `cr.targets[].systemId` exists and is a subsystem, (b) `task.systemId` belongs to `task.crId`'s targets, (c) `task.crId` exists, (d) a `LOGICAL_GROUP` has no `sshConfigId`/`remoteRepoPath`/`defaultBaseBranch` and no `parentId`, (e) a subsystem's `parentId` resolves to a `LOGICAL_GROUP`. `replaceTables` then `bulkAdd`s the rows, bypassing every repository guard. A hand-edited or older payload can therefore install a state the repo layer would refuse to create.
**Fix:** add a Stage 4 before returning `valid: true`:
```ts
const systemById = new Map((systems ?? []).map((s) => [s.id, s]));
for (const cr of changeRequests ?? []) {
  for (const t of cr.targets) {
    const sys = systemById.get(t.systemId);
    if (!sys) errors.push({ table: 'changeRequests', recordId: cr.id, field: 'targets', message: `Unknown systemId ${t.systemId}` });
    else if (sys.type === 'LOGICAL_GROUP') errors.push({ table: 'changeRequests', recordId: cr.id, field: 'targets', message: 'Parent system cannot be a CR target' });
  }
}
for (const t of tasks) {
  const cr = (changeRequests ?? []).find((c) => c.id === t.crId);
  if (!cr) errors.push({ table: 'tasks', recordId: t.id, field: 'crId', message: 'Unknown crId' });
  else if (t.systemId && !cr.targets.some((x) => x.systemId === t.systemId))
    errors.push({ table: 'tasks', recordId: t.id, field: 'systemId', message: 'systemId is not a target of the task CR' });
}
```

### CR-07: `deleteTaskWithAllocations` deletes chat threads but not their tabs

**File:** `src/db/repositories/cascadeRepo.ts:90-139`
**Issue:** The transaction table list (lines 92-101) omits `db.chatTabs`, and lines 115-120 delete `chatMessages` and `chatThreads` for `task:<id>` without deleting the matching tabs. `chatRepo.clearAllChatHistory` documents exactly why this is fatal: "a surviving tab with a deleted threadId makes the app's own backup fail validation (`ChatTab references threadId ... not found`)". `deleteChangeRequestWithCascade` does include `chatTabs`, so the omission is an inconsistency, not a design choice.

```ts
db.chatTabs, // add to the transaction table list

await db.chatTabs.where('threadId').anyOf(threadIds).delete();
```

### CR-08: Pre-import snapshot download writes all settings — including tokens and passphrases — as plaintext JSON

**File:** `src/services/backup/restoreBackup.ts:172-191, 291-295`
**Issue:** `captureSnapshot` reads `targetDb.settings.toArray()` unfiltered, so the snapshot contains `github_token`, `github_passphrase`, `backup_passphrase`, `jira_api_token`, `ninerouter_api_key`, `knowledge_server_token`, `image_api_key`, and `ssh_configurations`. `downloadSnapshotFile` then `JSON.stringify`s that snapshot straight to disk. `exportBackupPayload` deliberately filters these via `isSafeBackupSetting`; the snapshot path does not. This breaks the project's "never store passphrase / encrypt backup artifact" rule for a file the UI invites the user to download (`SettingsView.tsx:120`, `SnapshotRollbackCard.tsx:75`).
**Fix:** filter at capture time and never persist secrets in the snapshot:
```ts
const settings = (await targetDb.settings.toArray()).filter((s) => isSafeBackupSetting(s.key));
```
and re-apply `isSafeBackupSetting` in `downloadSnapshotFile` as a second line of defence.

### CR-09: SDLC workflow persistence key no longer matches the restore path or the chat drawer

**File:** `src/services/wizard/workflowCoordinator.ts:36-38`; `src/views/ChangeRequestSdlcView.tsx:409`; `src/services/backup/restoreBackup.ts:253-260`; `src/components/ai/AIChatDrawer.tsx:917,934,958`
**Issue:** `projectId` and `activeCrId` are now both CR ids (`ChangeRequestSdlcView.tsx:88,100`), so `workflowStorageKey(projectId, crId)` produces `sdlc_workflow:<crId>:<crId>`. The restore path writes `sdlc_workflow:<crId>:<threadId>` and the drawer reads that same `<crId>:<threadId>` form for checkpoint recovery and missing-source detection. The two key families are disjoint: after a backup restore the SDLC view sees no workflow state (and can re-commit v1), while the drawer's checkpoint banner never fires for live state. `SystemDetailView.tsx:219` (`split(':').pop()`) also maps the `<crId>:<threadId>` form to a threadId, so the progress column reads 0.
**Fix:** make the key contract single-sourced on the thread id and use it everywhere:
```ts
// workflowCoordinator.ts
export function workflowStorageKey(changeRequestId: string, threadId: string): string {
  return `sdlc_workflow:${changeRequestId}:${threadId}`;
}
// ChangeRequestSdlcView saveState/loadState/deleteState
key: workflowStorageKey(projectId, threadIdRef.current)
```

### CR-11: Step 3 overwrites the selected subsystem's SSH/repo with the first SSH profile's defaults

**File:** `src/components/sdlc/steps/Step3CodeGuideView.tsx:104-113, 155-180`
**Issue:** The subsystem-derived effect (declared at line 104) runs before `loadInitial` (declared at line 155) on mount. `loadInitial` unconditionally sets `selectedSshConfigId = configs[0].id` and `remoteRepoPath = configs[0].defaultRemotePath`, clobbering the values just derived from the selected subsystem. Branch listing, dirty checks, diff and Change Pack then run against the wrong repository. A second defect: when the user switches to a subsystem without `sshConfigId`/`remoteRepoPath`, the effect only assigns when the field exists, so the previous subsystem's SSH host and repo path remain and are used for the new subsystem.
**Fix:** make `loadInitial` fall back only when the subsystem has no binding, and reset on every switch:

```ts
useEffect(() => {

  setLoadedRepoPath(selectedSystem?.remoteRepoPath ?? '');

}, [selectedSystem]);
// loadInitial: only seed when no subsystem is selected
if (!selectedSystemId && configs[0]) { ... }
```

### CR-12: `generate_file` executes model-supplied JavaScript with page-global scope and no confirmation

**File:** `src/services/ai/aiTools.ts:4492-4515`; `src/utils/dynamicFileSandbox.ts:47-58`
**Issue:** The `script` branch builds an `AsyncFunction` from the model's string and runs it in the page realm — `fetch`, `localStorage`, `indexedDB`, and the Dexie handle are all reachable. `generate_file` is absent from `MUTATION_TOOLS` (`aiTools.ts:4690-4731`), so `isMutationTool` returns false and the orchestrator never asks for approval. Chained with the unconfined `read_file` tool (`aiTools.ts:3356-3400`, arbitrary Tauri path), a prompt injection in an imported document or task note can read a local secret file and POST it out.
**Fix:** add `'generate_file'` to `MUTATION_TOOLS` (or gate the `script` branch behind explicit confirmation), and run the script in a Worker with no `fetch`/storage access:
```ts
const MUTATION_TOOLS = new Set([..., 'generate_file']);
```

### CR-13: `createTask` / `reparentTask` / `updateTask` never verify the CR exists

**File:** `src/db/repositories/taskRepo.ts:16-27, 36, 297`
**Issue:** `assertSystemInCrTargets` returns immediately when `systemId === undefined`, so `createTask({ crId: 'does-not-exist', ... })` succeeds. The same hole exists in `reparentTask` and in `updateTask` when only `crId` changes. `validateBackup` also never checks `task.crId` against `changeRequests`, so the orphan row round-trips through export/import invisibly and is unreachable from every CR view.
**Fix:** always resolve the CR, regardless of `systemId`:
```ts
async function assertSystemInCrTargets(crId: string, systemId: string | undefined, db: TaskPlannerDatabase) {
  const cr = await db.changeRequests.get(crId);
  if (!cr) throw new Error('Change Request không tồn tại.');
  if (systemId !== undefined && !cr.targets.some((t) => t.systemId === systemId)) {
    throw new Error('Subsystem của tác vụ phải thuộc CR đã chọn.');
  }
}
```

### CR-14: v16 deletes tasks but leaves their allocations, sessions, timers and notes orphaned

**File:** `src/db/index.ts:327-346`
**Issue:** The migration deletes unresolvable tasks (`tasksTable.delete(id)`) and touches nothing else. `plannedAllocations`, `workSessions`, `activeTimers` and task-scoped `notes` keep pointing at deleted task ids. `validateBackup` Stage 3 rejects exactly these references (`validateBackup.ts:229-252, 258-285`), so the workspace exports a backup that fails its own import validation, and the Planner shows allocations for tasks that no longer exist.
**Fix:** delete the dependants in the same migration step:
```ts
await tx.table('plannedAllocations').where('taskId').equals(id).delete();
await tx.table('workSessions').where('taskId').equals(id).delete();
await tx.table('activeTimers').delete(id);
await tx.table('notes').where('entityId').equals(id)
  .modify((n: Record<string, unknown>) => { delete n.entityType; delete n.entityId; });
```

## Warnings

### WR-01: CR `code` is optional in the form but required by the schema — creating a CR without a code silently does nothing

**File:** `src/components/changeRequests/ChangeRequestModal.tsx:265-270, 219-225`

```ts
} catch (err) {
```

### WR-02: `TaskDrawer` save swallows repository invariant errors

**File:** `src/components/tasks/TaskDrawer.tsx:407-411`

### WR-06: `CRExplorer` produces duplicate tree keys and opens an arbitrary CR for a subsystem

**File:** `src/workbench/toolwindows/CRExplorer.tsx:265-266, 372-376`

### WR-07: "Mở SDLC tại subsystem này" does not preselect the subsystem

### WR-09: `openTerminal` throws and two callers invoke it unguarded

**File:** `src/components/sdlc/SubsystemContextBar.tsx:103`; `src/components/sdlc/SubsystemsReposPanel.tsx:166`; `src/workbench/hooks/useSystemActions.ts:40-51`
**Issue:** `openTerminal` throws `Error('Đường dẫn repo không hợp lệ.')` for a non-absolute path or control characters. The two panel callers pass it straight into `onClick`, so the exception escapes the React handler (uncaught, no user feedback). `CRExplorer` and `SystemDetailView` wrap it; these do not.
**Fix:** wrap in try/catch and `message.error(...)`, or make `openTerminal` return a result instead of throwing.

### WR-10: Unique-index collisions on `systems.code` / `changeRequests.code` are not pre-validated

**File:** `src/db/repositories/systemRepo.ts:62-89`; `src/db/repositories/changeRequestRepo.ts:41-73`; `src/db/index.ts:358-370`
**Issue:** Both tables declare `&code`. Duplicate codes surface as a raw Dexie `ConstraintError` (or, in the v16 backfill, abort the whole upgrade transaction and leave the DB blocked). The v16 backfill also generates `CR-LEGACY-N` without checking for an existing code with that value.
**Fix:** check for an existing row with the same code before `add`/`put` and throw a localised message; in the migration, skip codes already taken.

### WR-11: v16 converts `targetSystemIds` into `targets` without validating existence or subsystem-ness

**File:** `src/db/index.ts:350-357`
**Issue:** Legacy `targetSystemIds` may contain ids of `LOGICAL_GROUP` rows or ids that no longer exist. The migration copies them verbatim, so D-25 is violated immediately after upgrade and `assertTargetsAreSubsystems` is never re-run.
**Fix:** resolve each id against the `systems` table inside the migration and drop non-subsystem/missing entries (logging the count).

### WR-12: Import clears the whole `settings` table; rollback cannot restore the secrets it drops

**File:** `src/services/backup/restoreBackup.ts:223, 249, 286`
**Issue:** `targetDb.settings.clear()` wipes `github_token`, `github_passphrase`, `backup_passphrase`, `jira_api_token`, `ninerouter_api_key`, `knowledge_server_token`, `image_api_key` on every import. The rollback path re-adds settings only through `isSafeBackupSetting`, so those secrets are permanently lost even after a "safe" rollback. `ssh_configurations` survives only because its key happens to pass the filter.
**Fix:** never clear settings wholesale — delete only the keys present in the payload, and restore the snapshot's unsafe keys from the in-memory snapshot when rolling back.

### WR-13: Creating a task from the CR detail persists an empty row before the drawer is filled

**File:** `src/views/ChangeRequestDetailView.tsx:138-150`

**Fix:** create the task on drawer save, or delete the placeholder when the drawer closes without a save.

### WR-14: SDLC sidebar falls back to another CR when the active CR is gone

**File:** `src/components/sdlc/SdlcSidebar.tsx:65-66`
**Issue:** `crs.find(...) ?? crs[0]` — if `activeCrId` points at a deleted CR, the sidebar renders the first CR's code, targets and progress while the workspace shows the empty state.
**Fix:** render the empty state when the requested id does not resolve.

### WR-15: Global localStorage auto-approve fallback bypasses confirmation for CR mutations

**File:** `src/components/ai/AIChatDrawer.tsx:1459-1466`
**Issue:** When a tab has no `config.autoApproveMutations`, the turn falls back to `localStorage['planner:ai_auto_approve_mutations']`. No current UI writes that key (the toggle writes per-tab config), so it is dead — but if it is ever set (or set by an older build), `create/update/delete_change_request` execute without any prompt.
**Fix:** remove the global fallback; per-tab config is the only source.

### WR-16: `legacyTabRows` is unreachable and would emit rows the validator rejects

**File:** `src/services/backup/restoreBackup.ts:60-166`
**Issue:** It only runs when `tables.chatTabs === undefined`, but pre-v11 payloads are rejected at the envelope stage and v11 exports always include `chatTabs`. If it ever ran, it would set `tab.scopeKey` to a thread scope containing `:chat:` (`:123`), which `validateBackup.ts:379-385` rejects on the next round-trip.
**Fix:** delete the dead path, or strip the `:chat:` suffix when it builds the tab scope.

### WR-17: Snapshot is captured outside the replace transaction

**File:** `src/services/backup/restoreBackup.ts:276-278`
**Issue:** `captureSnapshot` runs before `replaceTables` opens its transaction. A write landing between the two is neither in the snapshot nor in the restored data — it is silently lost with no rollback path.
**Fix:** capture the snapshot inside the same `rw` transaction as the clear/add.

### WR-18: Recurring spawn copies `systemId` without re-checking the CR targets

**File:** `src/utils/recurrence.ts:110`
**Issue:** `if (task.systemId !== undefined) nextTask.systemId = task.systemId;` — if the CR's targets changed since the template was created, the spawned instance violates D-26.
**Fix:** resolve the CR and drop `systemId` when it is no longer a target.

### WR-19: AI tool surface has no CR-scope guard

**File:** `src/services/ai/aiTools.ts:2104-2110`
**Issue:** `executeAiTool` receives no scope, so a CR-scoped turn can call `query_tasks`, `update_task`, `delete_change_request`, etc. against any other CR. Grounding itself is correctly scoped (`contextGrounding.ts:213-275`), but the tool layer is not. Mutations still require confirmation, so this is a leakage/UX risk rather than an unguarded write.
**Fix:** pass the active scope into `executeAiTool` and reject entity ids outside it for CR-scoped turns (or at least annotate the confirmation summary with the owning CR).

### WR-20: Export leaks absolute local paths and the SSH host inventory

**File:** `src/services/backup/exportBackup.ts:219-228, 35-48`
**Issue:** `noteAttachments` export `filePath` (absolute local paths, or a synthesized path), and `isSafeBackupSetting` lets `ssh_configurations` through, so the backup artifact carries hostnames, usernames and key paths. The payload is encrypted only when the GitHub path is used; the manual JSON export is plaintext.
**Fix:** drop `filePath` from the export (restore already synthesizes one) and add `ssh_configurations` to `UNSAFE_OR_EPHEMERAL_SETTING_KEYS`.
