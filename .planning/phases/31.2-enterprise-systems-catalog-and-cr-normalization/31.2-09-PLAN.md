<objective>
Bump the backup envelope to version 11, drop the project/milestone tables, and reject legacy payloads before any write.

Purpose: D-49. A backup is the one path that can inject rows the new model forbids; rejecting at the envelope stage (not mapping) is the only safe behaviour, and it must leave local data untouched.
Output: a version-11 envelope with no project/milestone tables and an explicit, tested rejection path.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-supplied backup file → IndexedDB | The highest-risk trust boundary in the app; a crafted file must not be able to write rows the model forbids |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31.2-23 | Tampering | `validateBackupPayload` | mitigate | `assertNoLegacyTables` runs before any per-table validation and before any write, so a `projects`/`milestones` payload cannot be mapped into the new model |
| T-31.2-24 | Denial of service (data loss) | `restoreBackup` | mitigate | Rejection happens during validation, before the snapshot/clear/add sequence, so local data is provably untouched on a legacy payload (asserted by a test that pre-seeds a CR) |
| T-31.2-25 | Tampering | `BackupTaskRecordSchema` | mitigate | `crId` is required at the schema level, so a hand-edited backup cannot create a task with no CR |
| T-31.2-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this phase |
</threat_model>
