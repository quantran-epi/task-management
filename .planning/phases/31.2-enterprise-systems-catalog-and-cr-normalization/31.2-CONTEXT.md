# Phase 31.2: Enterprise Systems Catalog and CR Normalization - Context

**Gathered:** 2026-11-07
**Status:** Ready for planning

<domain>
## Phase Boundary

TaskMate xoay quanh **Change Request (CR)**. Một CR = một vòng đời SDLC. Phase này chuẩn hoá toàn diện mô hình dữ liệu, điều hướng và SDLC Studio để mô hình đó hiển thị nhất quán, không còn tàn dư `Project`/`Milestone`, và không còn hai nơi cùng cấu hình SSH/Repo.

Phạm vi:
1. **Zero-Legacy**: xoá sổ `projects`, `milestones`, mọi component/test/view cũ. `Task` trỏ trực tiếp `crId` + `systemId?`. Đổi luôn mọi surface daily (Tasks view, filter, drawer, chat scope, backup, notifications, planner, palette, export) sang CR/Subsystem.
2. **System Catalog chuẩn**: Logical Parent chỉ để phân nhóm, không có repo/SSH/CR. Subsystem là deployment unit, mỗi Subsystem gắn đúng 1 repo remote SSH.
3. **SystemDetailView** dạng tab, phân biệt rõ Parent vs Subsystem, 1-click mở Git Explorer / SSH Terminal.
4. **CR Detail View** mới + CR Explorer viết lại thật (không còn re-export dummy).
5. **SDLC Studio**: bỏ hẳn màn cấu hình Repo & SSH; thêm view quan sát read-only "Subsystems & Repos"; Subsystem Context Bar; Step 2 phân tách giải pháp theo Subsystem; Step 4 pack theo từng Subsystem + Pack All.
6. **AI đề xuất Subsystem**: khi phân tích SOLUTION, nếu CR chưa gán (hoặc gán thiếu) subsystem, AI đề xuất danh sách subsystem ảnh hưởng kèm lý do; user xác nhận thì mới gắn vào CR.
</domain>

<decisions>
## Implementation Decisions

### 1. Data Model — nguồn sự thật duy nhất

**D-24 — `systems` (một bảng, hai vai trò phân biệt bằng `type`)**
```
System {
  id: uuid
  code: string          // unique, UPPER_SNAKE
  name: string
  type: 'LOGICAL_GROUP' | 'SERVICE' | 'SCHEMA' | 'UI' | 'WORKER'
  parentId: string | null   // null = root; chỉ được trỏ tới LOGICAL_GROUP
  description?: string
  // Chỉ có nghĩa với type !== LOGICAL_GROUP:
  sshConfigId?: string      // FK -> settings (ssh config)
  remoteRepoPath?: string   // đúng 1 repo / subsystem
  defaultBaseBranch?: string // mặc định 'origin/main'
}
```
Bất biến (enforce ở repo + Zod, không chỉ ở UI):
- `type === 'LOGICAL_GROUP'` ⇒ `parentId === null`, `sshConfigId/remoteRepoPath/defaultBaseBranch` đều `undefined`.
- `type !== 'LOGICAL_GROUP'` ⇒ `parentId` phải trỏ tới một `LOGICAL_GROUP` (hoặc null nếu chưa phân nhóm).
- Không cho `parentId` tạo chu trình; không cho subsystem làm cha của subsystem.

**D-25 — `changeRequests` là trung tâm**
```
ChangeRequest {
  id: uuid
  code: string
  name: string
  type: 'NEW_FEATURE' | 'ENHANCEMENT' | 'BUGFIX'
  status: 'Open' | 'Pending' | 'In Progress' | 'Done' | 'Cancelled'
  targets: CrTarget[]        // thay cho targetSystemIds: string[]
  description?, deadline?, jiraEpicKey?, documentLinks[],
  opsOwners[], businessAnalysts[], reminders[]
}

CrTarget {
  systemId: string           // CHỈ subsystem (type !== LOGICAL_GROUP)
  featureBranch?: string     // branch làm việc của CR trên subsystem này
}
```
Bất biến:
- `targets[].systemId` unique trong một CR, tồn tại, và `type !== 'LOGICAL_GROUP'`.
- `featureBranch` mặc định `feature/{cr.code}` khi gắn subsystem (nếu CR đã có `code`); user sửa được; lưu tường minh, không suy ra lúc chạy.
- `baseBranch` **không** thuộc CR — luôn đọc từ `system.defaultBaseBranch`.
- Khi xoá subsystem: gỡ target khỏi mọi CR và set `tasks.systemId = undefined`.
- Khi đổi `cr.code`: **không** tự đổi `featureBranch` đã lưu (tránh đổi branch đang làm việc); UI chỉ gợi ý khi branch còn trống.

**D-26 — `tasks` trỏ trực tiếp CR, tùy chọn trỏ Subsystem**
```
Task {
  id: uuid
  crId: string          // BẮT BUỘC (thay projectId)
  systemId?: string     // tuỳ chọn; nếu có phải ∈ cr.targets.map(t => t.systemId)
  title, status, estimatedHours, dueDate, checklist...
}
```
Bất biến: `systemId` không được trỏ ra ngoài `cr.targets`. Khi gỡ subsystem khỏi CR ⇒ các task của subsystem đó về `systemId = undefined` (không xoá task).

**D-27 — Không còn `milestones`, không còn `projects`**
Xoá bảng khỏi Dexie. Reset data test được phép. Không giữ alias ngầm.

**D-28 — SDLC artifacts thuộc CR, không thuộc subsystem**
`workflowState` (INTAKE → SOLUTION → CODE_GUIDE → CHANGE_PACK → TECH_DOCS → CAB) lưu theo `crId`. Nội dung bên trong được phép phân mục theo subsystem (Step 2, Step 4), nhưng không tách thành nhiều workflow.

### 2. Điều hướng & Workbench

**D-29 — CR Explorer là tool window mặc định (Alt+1)**
Cây: `CR (code · type tag · status)` → các `Subsystem pill` → `Task` trực tiếp (không còn tầng Milestone). Context menu trên CR: Mở CR Detail, Mở SDLC Studio, Sửa, Xoá. Context menu trên Subsystem trong CR: Mở Git Explorer, Mở SSH Terminal, Mở SDLC tại subsystem đó, Gỡ khỏi CR.

**D-30 — Systems Explorer (Alt+6)**
Cây: `Logical Parent` → `Subsystem`. Parent: chỉ có "Thêm subsystem", "Sửa", "Xoá", "Xem chi tiết" — **không có "Tạo CR"**. Subsystem: có "Tạo CR" (auto-select chính nó), "Mở Git", "Mở Terminal".

**D-31 — Click CR mở tab `ChangeRequestDetailView`**
Không mở popup, không swap inline. Tab CR Detail có nút nổi bật "Mở SDLC Studio".

### 3. ChangeRequestDetailView

**D-32 — Bố cục CR Detail (một màn, không tab con)**
- Header: `code` + tên + type tag (#1677ff / #52c41a / #faad14) + status + target subsystem pills + nút `Mở SDLC Studio` / `Sửa` / `Xoá`.
- Dải tiến độ SDLC: 6 bước rút gọn, bước nào xong thì tick, click nhảy thẳng vào bước đó trong SDLC Studio.
- Bảng Task phẳng: cột `Task | Subsystem | Status | Ước lượng | Hạn`. Cột Subsystem là tag chọn được, dropdown chỉ liệt kê subsystem thuộc CR + "Chung (không gắn)".
- Khối phụ (thu gọn được): Jira Epic, tài liệu liên kết, nhắc nhở.

### 4. SystemDetailView

**D-33 — Tabbed Rich View**
- *Overview*: thông tin, type badge, mô tả; với Subsystem thêm SSH host, repo path (copyable), base branch, trạng thái kết nối.
- *Subsystems*: chỉ với Logical Parent — bảng subsystem con + 1-click Git/Terminal + "Thêm subsystem".
- *Impacted CRs*: danh sách CR có `targets` chứa system này (với Parent: hợp của các subsystem con), kèm type/status/tiến độ.
- *Git & Branches*: chỉ với Subsystem — branch list + commit gần nhất qua SSH, có trạng thái loading/lỗi rõ ràng; ẩn hoàn toàn với Parent.

**D-34 — Tạo CR từ Subsystem**
Nút "Tạo CR" chỉ xuất hiện ở Subsystem (Catalog row, Detail header, Explorer menu). Mở `ChangeRequestModal` với `targets = [{ systemId: subsystem.id, featureBranch: `feature/${cr.code}` }]` đã điền sẵn, khóa mềm (vẫn cho thêm subsystem khác).

### 5. 1-Click Git & Terminal

**D-35 — Hành vi chính xác**
- *Mở Git Explorer*: set `activeRemoteTarget(sshConfigId, remoteRepoPath, defaultBaseBranch)` rồi mở **left tool window `remote_explorer`** (Remote Git Explorer), tự load branch/tree. **Amended 2026-11-07:** the original wording said "bottom tool window Remote Git", but no such bottom id exists — Remote Git is a left tool window. The user chose to reuse the left panel rather than build a new bottom one; no new bottom panel is created.
- *Mở SSH Terminal*: mở bottom tool window Terminal, tạo session SSH tới đúng profile và `cd <remoteRepoPath>`.
- Nếu subsystem thiếu `sshConfigId` hoặc `remoteRepoPath`: nút bị disable + tooltip "Chưa cấu hình SSH/Repo — mở System Catalog", click tooltip mở modal sửa subsystem.

### 6. SDLC Studio

**D-36 — Bố cục 3 vùng, một CR duy nhất**
- Sidebar trái: CR picker (đổi CR = đổi vòng đời), card CR context, danh sách 6 bước, và mục **"Subsystems & Repos"** (read-only).
- Workspace: Subsystem Context Bar (chỉ hiện khi CR có ≥ 2 subsystem) + nội dung bước + chat panel của bước.
- Không còn tab "Cấu hình Repo & SSH" (`RepoConfigView` gỡ khỏi SDLC).

**D-37 — "Subsystems & Repos" là view quan sát read-only**
Mỗi dòng: code, tên, type badge, SSH `user@host:port` (hoặc "Chưa cấu hình"), repo path, base branch, chấm trạng thái kết nối. Không có input nào. Có link "Chỉnh sửa trong System Catalog" mở modal subsystem. Có nút 1-click Git/Terminal mỗi dòng.

**D-38 — Subsystem Context Bar là state dùng chung của Step 3 & Step 4**
Một `selectedSystemId` ở cấp SDLC view (không phải state riêng từng step). Đổi subsystem ⇒ Step 3 nạp lại diff/branch của repo đó; Step 4 focus card của subsystem đó. Subsystem đang chọn được đánh dấu rõ. Nếu CR chỉ có 1 subsystem thì ẩn bar (không chiếm chỗ).

**D-38b — Branch lấy từ CR target, không dò lại**
Step 3 đọc `cr.targets.find(t => t.systemId === selectedSystemId)?.featureBranch`; `baseBranch` đọc từ `system.defaultBaseBranch`. Không còn logic `branchList.find(b => b.name.includes(crCode))`. Nếu `featureBranch` trống, Step 3 hiện ô chọn branch và lưu lại vào target khi user xác nhận. Danh sách branch remote vẫn tải để user chọn, nhưng không tự đoán.

**D-39 — Step 2: solution phân tách theo Subsystem**
Composer thêm segment yêu cầu cấu trúc đầu ra:
```
### [<SYSTEM_CODE>] <tên subsystem>
- Thay đổi ...
- File dự kiến ...
```
Mỗi subsystem trong CR phải có đúng một mục. Nếu AI cho rằng CR không chạm subsystem nào đã gán, nó phải nói rõ thay vì bịa mục rỗng. Conventions vẫn nạp theo từng repo, mỗi block có header định danh subsystem.

**D-40 — Step 4: pack theo từng Subsystem + Pack All**
Mỗi subsystem một Card: trạng thái snapshot/diff, nút `Pack` riêng, kết quả pack hiển thị tại chỗ. Nút `Pack All` chạy tuần tự từng subsystem, hiển thị tiến độ từng card, dừng được; subsystem lỗi không chặn các subsystem còn lại nhưng tổng kết phải nêu rõ cái nào fail. Drift matrix vẫn là một bảng chung, có cột Subsystem.

### 7. AI đề xuất Subsystem ảnh hưởng

**D-41 — Đề xuất là artifact có cấu trúc, không phải văn xuôi**
Sau khi phân tích SOLUTION (hoặc ở đầu Step 2 khi CR chưa có `targets`), AI có thể phát ra `subsystemProposal`:
```
{ items: [{ systemId, code, confidence: 'high'|'medium'|'low', reason }], evidence: string[] }
```
Chỉ được chọn `systemId` từ System Catalog; không được bịa code mới.

**D-42 — Không bao giờ tự gắn**
Card đề xuất hiển thị checkbox từng subsystem + lý do + độ tin cậy, kèm nút `Thêm vào CR` và `Bỏ qua`. Chỉ khi user xác nhận mới ghi `targets`. Đề xuất đã bỏ qua không hiện lại trong cùng CR trừ khi user yêu cầu phân tích lại.

**D-43 — Đề xuất bổ sung được, không chỉ khi CR trống**
Nếu CR đã có subsystem nhưng AI phát hiện thiếu (ví dụ solution có file thuộc repo khác), card ghi rõ "Đề xuất bổ sung" và chỉ list phần thiếu.

### 9. Luồng daily — các surface còn dính Project/Milestone

**D-46 — Tasks toàn cục vẫn tồn tại, nhưng đổi trục**
Tab `Tasks` (center) giữ nguyên vị trí. Bỏ `projectId`/`milestoneId` khỏi filter và form. Trục mới:
- Bộ lọc: `CR` (chọn 1 CR) + `Subsystem` (chỉ liệt kê subsystem thuộc CR đã chọn).
- `TaskTable` cột: `Task | CR | Subsystem | Status | Ước lượng | Hạn`.
- `TaskDrawer` form: `CR` bắt buộc (Select), `Subsystem` tuỳ chọn, danh sách subsystem lọc theo CR đang chọn; đổi CR thì reset subsystem nếu không còn thuộc CR mới.
- `QuickAddBar`: thêm nhanh task vào CR đang lọc (nếu có), ngược lại bắt chọn CR.
- `TaskFilterBar`: bỏ `projectId`/`milestoneId`, thêm `crId`/`systemId`.

**D-47 — ItemInsightView thu gọn còn task và CR**
`itemType` bỏ `'project'` và `'milestone'`, thêm `'cr'` và `'system'`. View CR hiển thị task của CR; view task hiển thị CR cha + subsystem.

**D-48 — Chat scope**
`ChatScopeType` bỏ `'project'` và `'milestone'`, thêm `'cr'` và `'system'`. `scopeKey` dạng `cr:<crId>` / `system:<systemId>`. Thread chat cũ scope `project:*`/`milestone:*` **bị xoá khi upgrade** (app đang ở giai đoạn test, chấp nhận mất). `AIChatDrawer` và `ScopePickerModal` cập nhật theo.
