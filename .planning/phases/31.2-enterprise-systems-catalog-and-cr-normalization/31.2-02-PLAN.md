    In `src/db/schema.ts`: add `export const SCHEMA_V16` spreading `SCHEMA_V15` but with `tasks` re-declared as `'id, crId, systemId, status, priority, deadline, workType, jiraKey, reminderDate, *opsOwners, *businessAnalysts'`. `projects` and `milestones` must be absent from the resulting object — add a comment stating that Dexie's `deleteRemovedTables` drops both object stores and their data atomically. Keep `systems` and `changeRequests` index strings unchanged.

    In `src/db/index.ts`: delete the two Dexie class properties `projects!: Table<Project, string>` and `milestones!: Table<Milestone, string>` (lines 48-49) and the `Project` / `Milestone` members of the `import type { ... } from '../types/models'` block (lines 19-20). Plan 01 deletes both types, so leaving the properties in place makes `src/db/index.ts` fail to compile with TS2305. Do not touch the remaining table properties.

    Then add `this.version(16).stores(SCHEMA_V16).upgrade(async (tx) => { ... })` after the V15 block. Inside the upgrade, in this order:
    1. Read all `changeRequests` rows and build a `Set` of their ids.
    2. Rewrite tasks: for each task, if `typeof task.projectId === 'string'` and that id is in the CR id set, set `task.crId = task.projectId`; otherwise (no `projectId`, or the id has no CR row) delete the task via `tx.table('tasks').delete(task.id)`. Always `delete task.projectId` and `delete task.milestoneId`. Leave `systemId` undefined. Count deletions and `console.warn` a single line `[db v16] deleted N orphan tasks` when N > 0.
    3. Rewrite CRs: if `cr.targets === undefined`, set `cr.targets = Array.isArray(cr.targetSystemIds) ? cr.targetSystemIds.map((systemId) => ({ systemId })) : []`; then `delete cr.targetSystemIds`. For every CR whose `code` is missing or empty, assign `CR-LEGACY-<n>` where `<n>` is a 1-based counter over CRs sorted by `id` ascending (deterministic). Do this in one pass after the targets rewrite.
    4. Purge legacy chat: collect `chatThreads` whose `scopeKey` starts with `project:` or `milestone:`; delete their `chatMessages` by `threadId`, their `chatTabs` by `threadId`, then the threads themselves.
    5. Purge legacy settings: delete every `settings` row whose `key` starts with `project_ssh_repo:` or `project_repo_ssh_binding:`.
    Do not add a placeholder CR and do not block the upgrade on orphans — the locked decision is delete.

    **Historical upgrade hooks (V2/V6/V15) are left intact.** They call `tx.table('projects')` / `tx.table('milestones')` in string form, which no `tsc` or grep gate can see. That is deliberate: a hook only runs when a user upgrades *from* that version, and Dexie materialises the store for the duration of the hook, so `tx.table('projects')` resolves against the pre-V16 schema of that step rather than against `SCHEMA_V16`. Deleting the calls would silently skip the `opsOwners`/`businessAnalysts` backfill and the V15 project→CR copy for anyone on an old database. Do not add existence guards — a guard would turn a real schema regression into a silent no-op. Add a one-line comment above the V16 block stating that the V2/V6/V15 hooks intentionally reference the pre-V16 stores.
