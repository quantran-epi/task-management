# Phase 31.2 Plan 01: Domain Types & Zod Trust Boundary Summary

**CR-centric domain contract: `CrTarget[]` targets, required CR code, required `Task.crId`, `Project`/`Milestone` deleted, and D-24 shape invariants enforced at the Zod boundary with the exact UI-SPEC Vietnamese messages.**

## Accomplishments

- `CrTarget` exists and `ChangeRequest.targets: CrTarget[]` replaces `targetSystemIds`; `code` is now required and uppercase-normalized.
- `Task.crId` is required and `Task.systemId` optional; `projectId`/`milestoneId` are gone.
- `Project` and `Milestone` (and their four Zod schemas plus two status tuples) are deleted outright — no aliases, per D-27.
- `SystemInputSchema`/`SystemUpdateSchema` reject a `LOGICAL_GROUP` carrying SSH/repo/base-branch fields or a non-null `parentId`, and reject a relative `remoteRepoPath`.
- `ChangeRequestInputSchema`/`ChangeRequestUpdateSchema` reject duplicate `systemId` targets.
- `NoteEntityType`, `ChatScopeType`, `TaskMateEntityType` narrowed to `task`/`cr`/`system` (+ `global`/`document` for chat scope).

## Files Created/Modified

- `src/types/models.ts` — `CrTarget` added; `ChangeRequest.targets`/required `code`; `Task.crId`/`systemId`; `Project`/`Milestone` deleted; three unions narrowed; `System` doc comment records the D-24 invariant and the `parentId` comment reworded.
- `src/validation/schemas.ts` — `CrTargetSchema`/`CrTargetInput`, `refineSystemShape`, `refineUniqueTargets`, `remoteRepoPathSchema`; Project/Milestone schemas and status tuples deleted; `TaskInputSchema.crId` required; `NOTE_ENTITY_TYPES` narrowed.

## Decisions Made

- CR code normalization is a Zod `.transform`, so the modal, the repo, and any future import path all produce the same uppercase code.
- One `refineSystemShape` helper serves both System schemas; duplicating the rules per schema would let them drift.
- `backupSchemas` inlines the CR status enum rather than importing a replacement tuple — plan 09 rewrites that file wholesale and the inline enum cannot go stale in the interim.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `backupSchemas.ts` imported the two deleted status tuples**
- **Found during:** Task 2 (Zod invariants)
- **Issue:** `src/validation/backupSchemas.ts` imported `PROJECT_STATUSES`/`MILESTONE_STATUSES` and used them in `z.enum(...)`. Deleting the tuples made the module throw at import time (`Cannot convert undefined or null to object`) — every suite importing `schemas.ts` transitively failed to collect, so the plan's own verify command could not run.
- **Fix:** Dropped the two imports and inlined the identical five-member status enum in both legacy record schemas. Plan 09 deletes those schemas entirely.
- **Files modified:** `src/validation/backupSchemas.ts`
- **Verification:** `npx vitest run tests/validation/domainSchemas.test.ts` collects and passes; `npx tsc --noEmit` reports no error in the file.
- **Committed in:** `c8ffed3a`

**2. [Rule 3 - Blocking] `tests/db/schemaV15Migration.test.ts` asserted the removed CR input shape**
- **Found during:** Task 2 verification
- **Issue:** The suite called `ChangeRequestInputSchema.parse` with `targetSystemIds` and no `code`, both removed by this plan. The failure was inside the file's "validates System and ChangeRequest input schemas" case — a live input-contract assertion, not the historical V14→V15 fixture data that plan 19 protects.
- **Fix:** Retargeted only that case at `code` + `targets` (with real UUIDs, since `CrTargetSchema.systemId` is a UUID). The V14→V15 migration assertions and `Project One`/`Project Two` fixture rows are untouched.
- **Files modified:** `tests/db/schemaV15Migration.test.ts`
- **Verification:** `npx vitest run tests/db/schemaV15Migration.test.ts` — 2 passed.
- **Committed in:** `7764fe51`
