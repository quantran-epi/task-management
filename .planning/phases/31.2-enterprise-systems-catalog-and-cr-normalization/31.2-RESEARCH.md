# Phase 31.2: Enterprise Systems Catalog and CR Normalization - Research

**Researched:** 2026-11-07
**Domain:** Destructive domain-model refactor (Dexie/IndexedDB + React 19 + Ant Design 6 + Tauri), SDLC Studio re-architecture
**Confidence:** HIGH on current-state facts (all read from source this session); MEDIUM on migration/ordering strategy (derived from Dexie source + code inspection, not from official docs — WebFetch/WebSearch were unavailable this session)

## Summary

Phase 31.2 is a **destructive, zero-legacy refactor**: `Project` and `Milestone` are deleted from the Dexie schema, from `src/types/models.ts`, from Zod, from every repository, view, util, AI tool, backup path, and test. `Task` gains a required `crId` and optional `systemId`. `ChangeRequest.targetSystemIds: string[]` becomes `targets: CrTarget[]`. `System` gains enforced parent/subsystem invariants. Then six UI surfaces are built or rebuilt on top: CR Explorer (real rewrite), ChangeRequestDetailView (new), tabbed SystemDetailView, SDLC Studio without `RepoConfigView`, and an AI subsystem-proposal approval gate.

The current state is **worse than CONTEXT.md assumes in some places and better in others**:

- **Better:** `systems` and `changeRequests` tables already exist at Dexie version 15 with `parentId`, `type: SystemType`, `sshConfigId`, `remoteRepoPath`, `defaultBaseBranch` already on the model. `TargetSystemsSelector`, `SystemModal`, `SystemTable`, `SystemCatalogView`, `SystemsExplorer`, `ChangeRequestModal`, `ChangeRequestTable` all exist and work. `loadMultiRepoConventions` already aggregates per-system CONVENTIONS.md with a `systemCode` header. `setActiveRemoteTarget` already exists with the exact signature D-35 needs.
- **Worse:** `System` invariants are **not enforced anywhere** — `systemRepo` only guards "cannot delete a parent with children". Worse, five call sites classify a node as a parent via `parentId === null || type === 'LOGICAL_GROUP'`, which means an **unparented subsystem is treated as a parent** and becomes non-selectable in `TargetSystemsSelector`. That is a live bug directly against D-24/D-25.
- **Worse:** the SDLC layer reads `db.projects` in **three** files, not one. CONTEXT D-52 says `ProjectSdlcView.tsx` reads it at lines 66, 81, 137. Actual: line 66 (`db.projects.toArray()`), line 137 (`db.projects.get(projectId)`); line 81 is a derived `allProjects[0]` use, not a table read. And `Step1IntakeView.tsx:66` also reads `db.projects.toArray()`. `conventionService.ts:174` and `Step3CodeGuideView.tsx:162,203` and `Step4ChangePackView.tsx:254` and `SdlcSidebar.tsx:94` all read the **legacy `project_ssh_repo:` settings binding**, which is a second SSH/repo config path that D-36 says must not exist.
- **Worse:** the blast radius is ~120 source files and ~113 test files, not ~60. `src/services/ai/aiTools.ts` alone has 123 project/milestone references and exposes `query_projects`, `query_milestones`, `create_project`, `update_project`, `delete_project`, `create_milestone`, `update_milestone`, `delete_milestone` as AI tools.

**Primary recommendation:** Execute D-52's 7 steps, but split step 1 into 1a (schema/types/Zod/repo invariants + `CrTarget`) and 1b (Dexie v16 that drops `projects`/`milestones` and drops legacy chat scopes), and add a **step 1.5 "fix parent classification"** before any UI work, because the `parentId === null || type === 'LOGICAL_GROUP'` predicate is used by 5 files and will silently corrupt the new invariant model if carried forward.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-24 — `systems` (one table, two roles distinguished by `type`)**
```
System {
  id: uuid
  code: string          // unique, UPPER_SNAKE
  name: string
  type: 'LOGICAL_GROUP' | 'SERVICE' | 'SCHEMA' | 'UI' | 'WORKER'
  parentId: string | null   // null = root; only allowed to point at LOGICAL_GROUP
  description?: string
  // Only meaningful when type !== LOGICAL_GROUP:
  sshConfigId?: string      // FK -> settings (ssh config)
  remoteRepoPath?: string   // exactly 1 repo / subsystem
  defaultBaseBranch?: string // default 'origin/main'
}
```
Invariants (enforce in repo + Zod, not only UI):
- `type === 'LOGICAL_GROUP'` ⇒ `parentId === null`, `sshConfigId/remoteRepoPath/defaultBaseBranch` all `undefined`.
- `type !== 'LOGICAL_GROUP'` ⇒ `parentId` must point at a `LOGICAL_GROUP` (or null if not yet grouped).
- No `parentId` cycles; a subsystem may not be the parent of a subsystem.

**D-25 — `changeRequests` is the center**
```
ChangeRequest {
  id: uuid
  code: string
  name: string
  type: 'NEW_FEATURE' | 'ENHANCEMENT' | 'BUGFIX'
  status: 'Open' | 'Pending' | 'In Progress' | 'Done' | 'Cancelled'
  targets: CrTarget[]        // replaces targetSystemIds: string[]
  description?, deadline?, jiraEpicKey?, documentLinks[],
  opsOwners[], businessAnalysts[], reminders[]
}

CrTarget {
  systemId: string           // subsystem ONLY (type !== LOGICAL_GROUP)
  featureBranch?: string     // CR's working branch on this subsystem
}
```
Invariants:
- `targets[].systemId` unique within a CR, exists, and `type !== 'LOGICAL_GROUP'`.
- `featureBranch` defaults to `feature/{cr.code}` when attaching a subsystem (if the CR already has `code`); user-editable; stored explicitly, never derived at runtime.
- `baseBranch` does **not** belong to the CR — always read from `system.defaultBaseBranch`.
- Deleting a subsystem: remove the target from every CR and set `tasks.systemId = undefined`.
- Changing `cr.code`: do **not** rewrite stored `featureBranch` (avoid changing a branch in use); UI only suggests when the branch is still empty.

**D-26 — `tasks` points directly at CR, optionally at Subsystem**
```
Task {
  id: uuid
  crId: string          // REQUIRED (replaces projectId)
  systemId?: string     // optional; if present must be ∈ cr.targets.map(t => t.systemId)
  title, status, estimatedHours, dueDate, checklist...
}
```
Invariant: `systemId` may not point outside `cr.targets`. Removing a subsystem from a CR ⇒ that subsystem's tasks go to `systemId = undefined` (tasks are not deleted).

**D-27 — No more `milestones`, no more `projects`**
Drop the tables from Dexie. Resetting test data is allowed. No implicit aliases.

**D-28 — SDLC artifacts belong to the CR, not the subsystem**
`workflowState` (INTAKE → SOLUTION → CODE_GUIDE → CHANGE_PACK → TECH_DOCS → CAB) is stored by `crId`. Content inside may be sectioned per subsystem (Step 2, Step 4), but must not split into multiple workflows.

**D-29 — CR Explorer is the default tool window (Alt+1)**
Tree: `CR (code · type tag · status)` → `Subsystem pill` → `Task` directly (no Milestone tier). CR context menu: Open CR Detail, Open SDLC Studio, Edit, Delete. Subsystem-in-CR context menu: Open Git Explorer, Open SSH Terminal, Open SDLC at that subsystem, Remove from CR.

**D-30 — Systems Explorer (Alt+6)**
Tree: `Logical Parent` → `Subsystem`. Parent: only "Add subsystem", "Edit", "Delete", "View detail" — **no "Create CR"**. Subsystem: has "Create CR" (auto-select itself), "Open Git", "Open Terminal".

**D-31 — Clicking a CR opens the `ChangeRequestDetailView` tab**
No popup, no inline swap. The CR Detail tab has a prominent "Open SDLC Studio" button.

**D-32 — CR Detail layout (one screen, no sub-tabs)**
- Header: `code` + name + type tag (#1677ff / #52c41a / #faad14) + status + target subsystem pills + `Open SDLC Studio` / `Edit` / `Delete` buttons.
- SDLC progress strip: 6 compact steps, tick when done, click jumps straight to that step in SDLC Studio.
- Flat task table: columns `Task | Subsystem | Status | Estimate | Due`. The Subsystem column is a selectable tag whose dropdown lists only the CR's subsystems + "General (unattached)".
- Secondary blocks (collapsible): Jira Epic, linked documents, reminders.

**D-33 — Tabbed Rich View (SystemDetailView)**
- *Overview*: info, type badge, description; for a Subsystem add SSH host, repo path (copyable), base branch, connection status.
- *Subsystems*: Logical Parent only — child subsystem table + 1-click Git/Terminal + "Add subsystem".
- *Impacted CRs*: CRs whose `targets` contain this system (for a Parent: union of child subsystems), with type/status/progress.
- *Git & Branches*: Subsystem only — branch list + recent commits over SSH, with explicit loading/error states; fully hidden for a Parent.

**D-34 — Create CR from a Subsystem**
The "Create CR" button appears only on a Subsystem (Catalog row, Detail header, Explorer menu). Opens `ChangeRequestModal` with `targets = [{ systemId: subsystem.id, featureBranch: 'feature/${cr.code}' }]` pre-filled, soft-locked (other subsystems can still be added).

**D-35 — Exact 1-click Git & Terminal behavior**
- *Open Git Explorer*: set `activeRemoteTarget(sshConfigId, remoteRepoPath, defaultBaseBranch)` then open the Remote Git bottom tool window, auto-loading branches/tree.
- *Open SSH Terminal*: open the Terminal bottom tool window, create an SSH session to the right profile and `cd <remoteRepoPath>`.
- If the subsystem lacks `sshConfigId` or `remoteRepoPath`: the button is disabled with tooltip "Chưa cấu hình SSH/Repo — mở System Catalog"; clicking the tooltip opens the subsystem edit modal.

**D-36 — SDLC Studio: three zones, one CR**
- Left sidebar: CR picker (changing CR = changing lifecycle), CR context card, the 6-step list, and a **"Subsystems & Repos"** section (read-only).
- Workspace: Subsystem Context Bar (only when the CR has ≥ 2 subsystems) + step content + the step's chat panel.
- No more "Repo & SSH configuration" tab (`RepoConfigView` removed from SDLC).

**D-37 — "Subsystems & Repos" is a read-only observation view**
Each row: code, name, type badge, SSH `user@host:port` (or "Not configured"), repo path, base branch, connection status dot. No inputs. A "Edit in System Catalog" link opens the subsystem modal. Each row has 1-click Git/Terminal buttons.

**D-38 — Subsystem Context Bar is shared state for Step 3 & Step 4**
A single `selectedSystemId` at the SDLC view level (not per-step state). Changing subsystem ⇒ Step 3 reloads that repo's diff/branch; Step 4 focuses that subsystem's card. The selected subsystem is clearly marked. If the CR has only 1 subsystem the bar is hidden (no reserved space).

**D-38b — Branch comes from the CR target, never re-derived**
Step 3 reads `cr.targets.find(t => t.systemId === selectedSystemId)?.featureBranch`; `baseBranch` comes from `system.defaultBaseBranch`. No more `branchList.find(b => b.name.includes(crCode))`. If `featureBranch` is empty, Step 3 shows a branch picker and saves the choice back to the target on user confirmation. The remote branch list is still loaded for the user to choose from, but nothing is guessed.

**D-39 — Step 2: solution split per Subsystem**
The composer adds a segment requiring this output structure:
```
### [<SYSTEM_CODE>] <subsystem name>
- Change ...
- Expected files ...
```
Every subsystem in the CR must have exactly one section. If the AI believes the CR touches none of the assigned subsystems, it must say so explicitly rather than fabricate an empty section. Conventions are still loaded per repo, each block headed with the subsystem identity.

**D-40 — Step 4: pack per Subsystem + Pack All**
One Card per subsystem: snapshot/diff state, its own `Pack` button, pack result shown in place. `Pack All` runs subsystems sequentially, shows per-card progress, is stoppable; a failing subsystem does not block the rest but the summary must name which failed. The drift matrix stays one shared table with a Subsystem column.

**D-41 — Proposals are a structured artifact, not prose**
After SOLUTION analysis (or at the start of Step 2 when the CR has no `targets`), the AI may emit `subsystemProposal`:
```
{ items: [{ systemId, code, confidence: 'high'|'medium'|'low', reason }], evidence: string[] }
```
Only `systemId`s from the System Catalog may be chosen; no invented codes.

**D-42 — Never auto-attach**
The proposal card shows a checkbox per subsystem + reason + confidence, with `Add to CR` and `Skip` buttons. `targets` is written only after the user confirms. A skipped proposal does not reappear in the same CR unless the user explicitly re-runs analysis.

**D-43 — Proposals may be additive, not only when the CR is empty**
If the CR already has subsystems but the AI detects missing ones (e.g. the solution touches files in another repo), the card says "Additional proposal" and lists only what is missing.

## Current Schema Reality

### Dexie version and tables

- Current version: **15** (`src/db/index.ts:272` `this.version(15).stores(SCHEMA_V15)`).
- `SCHEMA_V15` (`src/db/schema.ts:102-106`):
  ```
  systems: 'id, &code, parentId, type, sshConfigId, createdAt',
  changeRequests: 'id, &code, status, type, createdAt, updatedAt',
  ```
  Note: `changeRequests.code` is indexed as **unique** (`&code`) while `ChangeRequest.code` is optional in the type — multiple `undefined` codes are allowed by IndexedDB (undefined is not indexed), but two CRs with the same code will throw.
- `tasks` index string is still `'id, projectId, milestoneId, status, priority, deadline, workType, jiraKey, reminderDate, *opsOwners, *businessAnalysts'` (inherited from `SCHEMA_V4` via `SCHEMA_V5`…`V15`). There is **no** `crId` or `systemId` index yet.
- `projects` / `milestones` are still in the schema chain from V1 through V15.
- Existing `upgrade()` hooks: V2 (backfill owners/workType), V6 (reminderDate → reminders[]), V7 (timer segments), V9 (note type/tags), V13 (telegram maxHistoryTurns), V14 (chatThreads → chatTabs), **V15 (copy `projects` → `changeRequests`)** (`src/db/index.ts:78-304`).

### Artifact tool registration pattern (where `subsystemProposal` goes)

The `get_artifact` / `patch_artifact_section` chain has **six** registration points. Adding a `subsystemProposal` artifact/tool touches all of them:

1. **Tool definitions** — `AI_DATABASE_TOOLS` array in `src/services/ai/aiTools.ts:99+` (each entry is `{ type: 'function', function: { name, description, parameters } }`). `get_artifact` / `patch_artifact_section` live here.
2. **Mutation classification** — `MUTATION_TOOLS` set at `aiTools.ts:4990-5044`. `patch_artifact_section` is listed; `get_artifact` is not. A proposal tool that never writes should **not** be in this set.
3. **Step allowlist** — `SDLC_STEP_ALLOWED_TOOLS` in `sdlcPromptComposer.ts:66-73`. `ARTIFACT_STEP_TOOL_NAMES = ['get_artifact', 'patch_artifact_section']` is spread into `SOLUTION`, `TECH_DOCS`, `CAB` only. A proposal tool must be added to `SOLUTION` (and possibly `INTAKE`).
4. **Turn payload filter** — `getToolsForTurn` in `src/services/ai/chatTurnTools.ts:16-30` explicitly excludes `get_artifact`/`patch_artifact_section` when no allowlist is present. A new artifact tool needs the same guard or it leaks into every chat.
5. **Tool policy text** — `buildToolPolicy` in `sdlcPromptComposer.ts:90-131` derives `ownsDocuments`/`hasRead`/`hasPatch` from the allowlist and emits the two machine-parsed name lines (`Công cụ đọc cục bộ:` / `MCP đọc-only động:`). The parser requires those lines to equal the payload — **adding a tool without updating the policy text will break the parser equality check.**
6. **Dispatch** — `executeSdlcArtifactTool(toolName, args, db, context)` in `sdlcArtifactTools.ts:499-519` branches on `toolName === 'get_artifact'` else falls through to `prepareArtifactPatch`. Plus `chatTurnRuntime.ts:363` calls `preparePatch` for `PATCH_TOOL_NAME` in `onMutationCheck`, and `StepChatPanel.tsx:254` filters `onToolEvent` by name.

**Recommended shape for the proposal** (mirrors the Phase 27 approval-gate pattern already in `chatTurnRuntime.onMutationCheck` → `onAwaitingApproval` → `StepChatPanel` `patchRecords` → approval card):

- New refusal/result type `SubsystemProposalResult = { items: [{ systemId, code, confidence, reason }], evidence: string[] }`.
- Tool name e.g. `propose_subsystems`, **not** in `MUTATION_TOOLS` (it writes nothing), added to `SDLC_STEP_ALLOWED_TOOLS.SOLUTION`.
- The write happens in `SubsystemProposalCard`'s `Thêm vào CR` handler → `updateChangeRequest(crId, { targets: [...] })`. Never inside the tool.
- D-42's "skipped proposal does not reappear" needs persistence: either a `settings` key `sdlc_proposal_dismissed:${crId}` or a field on the CR. A settings key is lower-risk (no schema change).

## Migration Strategy

### What Dexie actually does when a table leaves `stores()`

Verified from the installed `dexie@4.4.6` source (`node_modules/dexie/dist/dexie.mjs`):

```js
// line 3971-3977
function deleteRemovedTables(newSchema, idbtrans) {
    [].slice
        .call(idbtrans.db.objectStoreNames)
        .forEach(function (storeName) {
        return newSchema[storeName] == null && idbtrans.db.deleteObjectStore(storeName);
    });
}
```

Called from the upgrade path at line 3871 (`deleteRemovedTables(newSchema, idbtrans)`), alongside `createMissingTables` at 3764/3895.

**Conclusion (HIGH confidence — read from installed source):** omitting `projects` and `milestones` from the new version's `stores()` **drops the object stores and all their data** as part of the IndexedDB `versionchange` transaction. No explicit `upgrade()` hook is needed to delete them. `deleteObjectStore` is synchronous and runs inside the upgrade transaction, so it is atomic with the rest of the version bump.

**Caveat:** this is Dexie's documented behavior but the doc page could not be fetched this session (WebFetch/WebSearch returned a model error). The source is authoritative for the installed version; the claim is tagged accordingly.

### Recommended migration shape

```ts
export const SCHEMA_V16 = {
  ...SCHEMA_V15,
  // projects, milestones omitted → Dexie drops both stores and their data
  tasks: 'id, crId, systemId, status, priority, deadline, workType, jiraKey, reminderDate, *opsOwners, *businessAnalysts',
  // systems/changeRequests unchanged at the index level
} as const;
```

```ts
this.version(16)
  .stores(SCHEMA_V16)
  .upgrade(async (tx) => {
    // 1. Rewrite every task: projectId -> crId (V15 gave changeRequests the same ids)
    await tx.table('tasks').toCollection().modify((task) => {
      if (task.crId === undefined && typeof task.projectId === 'string') task.crId = task.projectId;
      delete task.projectId;
      delete task.milestoneId;
      // systemId stays undefined until the user assigns one
    });

    // 2. changeRequests: targetSystemIds -> targets: CrTarget[]
    await tx.table('changeRequests').toCollection().modify((cr) => {
      if (cr.targets === undefined) {
        const ids = Array.isArray(cr.targetSystemIds) ? cr.targetSystemIds : [];
        cr.targets = ids.map((systemId) => ({ systemId }));
      }
      delete cr.targetSystemIds;
    });

    // 3. D-48: drop legacy chat threads/tabs scoped to project:/milestone:
    const legacyThreads = await tx.table('chatThreads')
      .filter((t) => typeof t.scopeKey === 'string' &&
        (t.scopeKey.startsWith('project:') || t.scopeKey.startsWith('milestone:')))
      .toArray();
    const legacyIds = new Set(legacyThreads.map((t) => t.id));
    await tx.table('chatMessages').filter((m) => legacyIds.has(m.threadId)).delete();
    await tx.table('chatTabs').filter((tab) => legacyIds.has(tab.threadId)).delete();
    await tx.table('chatThreads').bulkDelete([...legacyIds]);

    // 4. Drop legacy SSH/repo bindings (D-36 single config source)
    await tx.table('settings')
      .filter((s) => typeof s.key === 'string' &&
        (s.key.startsWith('project_ssh_repo:') || s.key.startsWith('project_repo_ssh_binding:')))
      .delete();
  });
```

**Important:** tasks with `projectId === undefined` (standalone tasks) have **no CR**. D-26 makes `crId` required. The upgrade must decide: delete orphan tasks, or leave `crId` undefined and let Zod/repo reject them later. Since D-27 allows a test-data reset, the cleanest option is to delete tasks with no resolvable `crId` inside the same upgrade and log a count. The plan should make this an explicit, tested decision.

### Does the plan need a data-migration task?

**Yes — one task, not zero.** The tables drop for free, but three data transformations are required and each is testable:

1. `tasks.projectId → tasks.crId` (and drop `milestoneId`).
2. `changeRequests.targetSystemIds → changeRequests.targets`.
3. Purge legacy chat scopes + legacy SSH bindings.

Plus a fourth decision: what to do with orphan tasks.

**Alternative considered (rejected):** keep `projects`/`milestones` in the schema and simply stop reading them. Rejected because D-27 says "no implicit aliases" and because `SCHEMA_V15.tasks` still indexes `projectId`/`milestoneId`, which would keep the dead fields queryable and invite accidental re-use. Also the backup validator would keep accepting legacy payloads, contradicting D-49.

## Invariant Enforcement Design (recommended)

Put the predicates in `systemRepo.ts` and reuse them from Zod's `superRefine` where the DB is not available:

```ts
// systemRepo.ts
export function isLogicalParent(system: Pick<System,'type'>): boolean {
  return system.type === 'LOGICAL_GROUP';
}
export function isSubsystem(system: Pick<System,'type'>): boolean {
  return system.type !== 'LOGICAL_GROUP';
}
```

- **Zod (shape-level, no DB):** `SystemInputSchema.superRefine` — reject LOGICAL_GROUP carrying `sshConfigId`/`remoteRepoPath`/`defaultBaseBranch`; reject LOGICAL_GROUP with non-null `parentId`.
- **Repo (DB-level):** `createSystem`/`updateSystem` load the target parent and assert `isLogicalParent(parent)`; walk `parentId` upward with a visited set to reject cycles; on `updateSystem` changing `type` to `LOGICAL_GROUP`, clear the three fields and `parentId`.
- **Repo (cross-entity):** `updateChangeRequest` validates every `targets[].systemId` exists and `isSubsystem`; dedupes; `featureBranch` defaults to `feature/${cr.code}` only when absent and `cr.code` exists.
- **Repo (cross-entity):** `createTask`/`updateTask` when `systemId` present load the CR and assert `cr.targets.some(t => t.systemId === systemId)`.
- **Cascade:** `removeSubsystemFromChangeRequest(crId, systemId)` → remove target, set that subsystem's tasks' `systemId = undefined` in one transaction. `deleteSystem` → for every CR containing the target, remove it; set matching tasks' `systemId = undefined`; then delete.
- **Error copy** already specified in the UI-SPEC: `Hệ thống cha không được có SSH/Repo`, `Subsystem phải trỏ tới một Logical Parent`, `Không thể tạo vòng lặp phân cấp`.

## Common Pitfalls

### Pitfall 1: Renaming the `projectId` prop but changing the persisted key format
**What goes wrong:** SDLC workflow state, draft solutions, CR lists, pack history, and step chat threads are all keyed by strings embedding the id (`sdlc_workflow:${projectId}:${crId}`, `sdlc_crs:${projectId}`, `sdlc_packs:${projectId}:${crId}`, `sdlc_draft_solution:${projectId}:${crId}`, `sdlc:${projectId}:${crId}:${step}`).
**Why it happens:** a mechanical rename of `projectId` → `changeRequestId` inside template literals looks harmless.
**How to avoid:** rename the *parameter*, keep the *value* and the key format identical. Add a test asserting `workflowStorageKey(crId, crId)` produces the same string as before.
**Warning signs:** SDLC Studio opens with an empty workflow for a CR that previously had one.

### Pitfall 2: Dropping `projects` before rewriting `deleteChangeRequest`
**What goes wrong:** CR delete stops cascading; tasks, notes, chat threads, allocations, and knowledge links are orphaned.
**Why it happens:** `deleteChangeRequest` only cascades if a matching `projects` row exists (`changeRequestRepo.ts:127`).
**How to avoid:** write `deleteChangeRequestWithCascade` in step 1, before the schema bump lands.
**Warning signs:** deleting a CR leaves its tasks visible in the Tasks view.

### Pitfall 3: `crId` required but orphan tasks exist
**What goes wrong:** the upgrade rewrites `projectId → crId`, but standalone tasks had no `projectId`. They now violate `Task.crId` required.
**Why it happens:** `Task.projectId` is optional today (`models.ts:125`).
**How to avoid:** decide explicitly in the upgrade: delete orphans (allowed by D-27) or block the upgrade. Log the count either way, and test it.
**Warning signs:** Zod throws on app boot when reading tasks; `useLiveQuery` returns nothing.

### Pitfall 4: `targets` written by the AI tool
**What goes wrong:** D-42 violated; subsystems attach without a click.
**Why it happens:** the tool dispatch path (`executeSdlcArtifactTool`) is the natural place to "just apply it".
**How to avoid:** the proposal tool returns data only; the write lives in `SubsystemProposalCard`'s confirm handler. Add a test asserting the tool never calls `updateChangeRequest`.
**Warning signs:** `cr.targets` changes after an AI turn with no user click.

### Pitfall 5: `chatTabRepo` silently downgrades `cr:` scopes to global
**What goes wrong:** CR-scoped chat tabs merge into the global thread.
**Why it happens:** `threadScopeParts` (`chatTabRepo.ts:23-31`) whitelists four scope types and returns `{ scopeType: 'global' }` for anything else.
**How to avoid:** extend the whitelist in the same commit as the `ChatScopeType` change; add a test for `cr:` and `system:`.
**Warning signs:** chat history for different CRs appears in the same thread.

### Pitfall 6: Step 3 still writes repo config
**What goes wrong:** D-36 violated; two config sources persist.
**Why it happens:** deleting `RepoConfigView` removes the *visible* config surface but `Step3CodeGuideView` calls `saveProjectRepoSshBinding` in five places.
**How to avoid:** grep for `saveProjectRepoSshBinding` after step 5 and assert zero non-test hits.
**Warning signs:** `project_ssh_repo:*` keys reappear in `settings` after using Step 3.

### Pitfall 7: `buildToolPolicy` parser equality break
**What goes wrong:** the step chat refuses to run or advertises tools that are not in the payload.
**Why it happens:** `sdlcPromptComposer.ts:110-111` emits two lines the parser compares against the actual tool payload.
**How to avoid:** when adding the proposal tool, update `SDLC_STEP_ALLOWED_TOOLS` and `buildToolPolicy` together and run `tests/unit/sdlc/StepChatPanelToolPolicy.test.tsx`.
**Warning signs:** that test fails with a name-mismatch assertion.

### Pitfall 8: Pack All partial failure loses per-card state
**What goes wrong:** a failed subsystem's card shows no error, or the whole run aborts.
**Why it happens:** `handlePackageFromSnapshot` sets a single `errorMsg` / `packagingStepStatus` for the whole view.
**How to avoid:** per-subsystem state map (`Record<systemId, {status, error?, packHash?}>`), sequential `for…of` with `try/catch` per iteration, and a summary that enumerates failed codes (UI-SPEC copy: `Đóng gói hoàn tất một phần: {ok}/{n}…`).
**Warning signs:** one failure blanks the whole Step 4.

### Pitfall 9: `RemoteGitExplorer` does not follow a second 1-click
See Ordering Hazard H5. Add a `key`-based remount or unconditional sync.

### Pitfall 10: Deleting `aiTools` project/milestone tools without replacement
**What goes wrong:** the AI loses the ability to answer "what CRs exist" / "create a CR".
**Why it happens:** 8 tools are defined and referenced in `MUTATION_TOOLS` and `pruneToolsForContext`.
**How to avoid:** decide in the plan whether to rename them (`query_change_requests`, `query_systems`, `create_change_request`, `update_change_request`, `delete_change_request`) or descope. Update `MUTATION_TOOLS` and `pruneToolsForContext`'s hardcoded name list in the same change.

```ts
// src/db/repositories/systemRepo.ts
export function isLogicalParent(s: Pick<System, 'type'>): boolean {
  return s.type === 'LOGICAL_GROUP';
}

async function assertParentIsLogicalGroup(parentId: string | null, db: TaskPlannerDatabase): Promise<void> {
  if (parentId === null) return;
  const parent = await db.systems.get(parentId);
  if (!parent) throw new Error('Hệ thống cha không tồn tại.');
  if (!isLogicalParent(parent)) throw new Error('Subsystem phải trỏ tới một Logical Parent');
}

async function assertNoCycle(id: string | null, parentId: string | null, db: TaskPlannerDatabase): Promise<void> {
  const seen = new Set<string>();
  let cursor = parentId;
  while (cursor) {
    if (cursor === id) throw new Error('Không thể tạo vòng lặp phân cấp');
    if (seen.has(cursor)) throw new Error('Không thể tạo vòng lặp phân cấp');
    seen.add(cursor);
    cursor = (await db.systems.get(cursor))?.parentId ?? null;
  }
}
```

## Open Questions

1. **Where should the Remote Git panel live for D-35?**
   - What we know: only `'terminal'` exists as a bottom id; `RemoteGitExplorer` is a left tool window.
   - What's unclear: whether "open bottom tool window Remote Git" means a new bottom panel or the existing left explorer.
   - Recommendation: add a `'remote_git'` bottom id rendering `RemoteGitExplorer` (faithful to D-35 + UI-SPEC copy), and keep the left explorer as-is.

2. **How should the terminal `cd <remoteRepoPath>` handoff work?**
   - What we know: `BottomToolWindow` keeps tabs in local state; `RemoteTerminalPanel` ignores its `repoPath` prop.
   - What's unclear: whether to add a store field or reuse `sessionStorage`.
   - Recommendation: add `pendingTerminalTarget: { sshConfigId, repoPath } | null` to `layoutStore`; `BottomToolWindow` consumes and clears it on mount, then `writePtyInput(sessionId, 'cd ' + path + '\n')` after the PTY connects.

3. **Should `Task.crId` be required at the type level immediately, or optional-then-required?**
   - What we know: D-26 says required; orphan tasks exist today.
   - What's unclear: whether the user wants a one-time "assign orphans to a CR" flow.
   - Recommendation: required immediately; delete orphans in the V16 upgrade and log the count (D-27 permits reset).

4. **Does `ChangeRequest.code` become required?**
   - What we know: D-25's shape says `code: string` (not optional); the current type has `code?`; the Dexie index is `&code` unique.
   - What's unclear: whether existing CRs without a code should be blocked.
   - Recommendation: keep optional in the type to avoid breaking migrated CRs, but require it in `ChangeRequestModal` for new CRs (needed for `feature/{cr.code}` defaults).

5. **Should `sdlcCrManager` be deleted entirely?**
   - What we know: `listCrs`/`getActiveCr`/`createNewCr`/`completeCr` are the legacy settings-backed CR store; `getStepThread` and the pack helpers are still needed.
   - What's unclear: whether `Step6CabView.completeCr` should map to `updateChangeRequest(status: 'Done')`.
   - Recommendation: delete the CR-list functions, keep `getStepThread` + pack helpers, and map `completeCr` → `updateChangeRequest(crId, { status: 'Done' })`.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Shell injection via `remoteRepoPath` or `featureBranch` in the new per-subsystem Git/pack commands | Tampering / Elevation | Always route through `escapeShellArg` (`gitRemoteService.ts:13`); `createChangePackFromSnapshot` already rejects control characters in `baseRef` and paths — extend the same check to `featureBranch` |
| Path traversal in `remoteRepoPath` | Tampering | `SystemModal` already requires an absolute path starting with `/`; keep that validator and add it to the Zod schema (currently UI-only) |
| Legacy backup used to inject `projects`/`milestones` rows and bypass the new model | Tampering | D-49: reject the payload at envelope stage before any table validation; never map |
| AI-proposed `systemId` pointing at a non-existent or parent system | Spoofing / Tampering | Proposal tool must validate every `systemId` against `db.systems` and `isSubsystem`; card must re-validate on confirm |
| Unescaped markdown from AI solution rendered in Step 2 | Cross-site scripting | Existing `renderSafeMarkdown` (`Step2SolutionView.tsx:21,307`) — keep it; do not introduce `dangerouslySetInnerHTML` on the new per-subsystem section renderer |
| SSH PTY orphan processes on subsystem switch | Denial of service (resource leak) | Claude's Discretion item; `closePtySession` exists — wire it to tab close and subsystem switch |
| `project_ssh_repo:` legacy settings surviving the migration and being re-read | Information disclosure (stale config) | Purge in the V16 upgrade (see Migration Strategy step 4) |
| Terminal `cd` command built from unvalidated `remoteRepoPath` | Tampering | Validate absolute path + reject control chars before writing to the PTY |
