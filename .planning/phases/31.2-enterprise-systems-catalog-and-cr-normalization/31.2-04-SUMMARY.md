# Phase 31.2 Plan 04: Repository Re-Axis off projects/milestones Summary

Seven repositories re-axed onto CR/System so no Dexie transaction names a store dropped by SCHEMA_V16, with CR-scoped chat threads, CR-backed tag aggregation and document links, and a CR spent-minutes rollup.

## What Was Built

**Task 1 — chat scope plumbing.** `chatRepo.buildScopeKey` now derives its prefix straight from `ChatScopeType`, producing `cr:<id>` / `system:<id>`. `chatTabRepo.threadScopeParts` whitelists `task | cr | system | document`; `cr` and `system` can no longer silently degrade to the shared `global` thread (T-31.2-11). The SDLC thread/tab bootstrap keys on `cr:<id>` and adopts an unclaimed `<scopeKey>` thread instead of orphaning it. `getProjectThreads` became `getCrThreads`; `getOrCreateSdlcThread` / `createChatTabThread` take a `crId`. The wizard↔thread guard now compares against `scopeType === 'cr'` while keeping the `WIZARD_PROJECT_MISMATCH` code that four test suites assert on.

**Task 2 — remaining repositories.** `tagRepo` unions ops owners and business analysts over `changeRequests` + `tasks` only, replacing the `orderBy(...).uniqueKeys()` + WebKit-fallback pair with a single `toArray()` pass (changeRequests has no multiEntry tag index). `documentLinkRepo` names `db.changeRequests` in both transactions, writes `cr.documentLinks`, and `getBacklinksForDoc` returns `changeRequests` instead of `projects`. `documentSetRepo` exposes `getOrCreateCrSdlcSetInTransaction` and persists `sdlc.changeRequestId`. `notificationRepo` drops the `project`/`milestone` reminder branches and adds `cr`. `workSessionRepo` replaces `getProjectSpentMinutes`/`getMilestoneSpentMinutes` with a single `getCrSpentMinutes(crId)` joining tasks by `crId`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `SdlcDocumentSetMetadataSchema` still required `projectId`**
- **Found during:** Task 2
- **Issue:** `documentSetRepo` parses every set through `DocumentSetSchema`, which embeds `SdlcDocumentSetMetadataSchema` as a `z.strictObject({ projectId, purpose })`. Renaming the stored key to `sdlc.changeRequestId` without touching the schema made `DocumentSetSchema.parse` reject the new shape.
- **Fix:** Renamed the schema field to `changeRequestId` in `src/services/ai/wizardSchemas.ts`. The persisted key string is unchanged in format, only the field name moved.
- **Files modified:** `src/services/ai/wizardSchemas.ts`
- **Commit:** b1614c57

**2. [Rule 3 - Blocking] `artifactRepo` still imported the removed function name**
- **Found during:** Task 2 verification
- **Issue:** `src/services/wizard/artifactRepo.ts` (owned by plan 23, wave 7) imported and called `getOrCreateProjectSdlcSetInTransaction`, which this plan renames. Leaving it would have been a compile break in a file this plan does not own.
- **Fix:** Renamed the import and both call sites to `getOrCreateCrSdlcSetInTransaction`. The `input.projectId` argument is untouched — plan 23 renames that field.
- **Files modified:** `src/services/wizard/artifactRepo.ts`
- **Commit:** 7f0a88f5

**3. [Rule 1 - Bug] Error code rename would have desynchronised two callers**
- **Found during:** Task 2
- **Issue:** The first pass renamed `DUPLICATE_PROJECT_SDLC_SET` to `DUPLICATE_CR_SDLC_SET` inside `documentSetRepo`, but `src/services/wizard/sdlcWizardRuntime.ts` (plan 23) throws and matches on the original string.
- **Fix:** Reverted to `DUPLICATE_PROJECT_SDLC_SET`. The plan mandates no error-code rename, only the function and metadata-key rename.
- **Files modified:** `src/db/repositories/documentSetRepo.ts`
- **Commit:** 7f0a88f5
