<objective>
Make the concurrency limit real: route the batch through the scheduler, honour live limit changes, and make stop/abort cover the queue. Remove the batch cap so the scheduler is the only rule.

Purpose: AIO-RUNTIME-05 and AIO-GROUP-04 are the same change seen from two sides — once a scheduler exists, the batch cap has no job left. AIO-LEAD-05's stop/abort must reach queued agents, otherwise the queue is invisible and unstoppable.
Output: scheduler-gated `runBatch`, `stopAgent`/`abortAll` queue semantics, `MAX_BATCH_SIZE` deleted, drawer control for `concurrencyLimit`, and a visible queued state per agent.

| user Stop → running provider requests | a UI action must reach every in-flight request |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-37-10 | Denial of Service | unbounded `delegate_batch` | high | mitigate | With `MAX_BATCH_SIZE` removed the only protection is the scheduler: at most `concurrencyLimit` runtimes exist at once, so a 100-item batch opens at most 12 provider streams per team. The limit-2/5-assignment test is the regression proof. |
| T-37-11 | Denial of Service | leaked slot | high | mitigate | `scheduler.release` runs in `startEmployeeTurn`'s `finally` after `settleAgent`; `release` is idempotent (37-02), so a double settle cannot corrupt the count. |
| T-37-12 | Repudiation | stopped-but-silent work | medium | mitigate | Every stop writes a ledger row with a `stopReason`, and the batch result carries `incomplete`, so partial work can never be presented as complete (D-14). |
| T-37-13 | Tampering | `concurrencyLimit` mid-run | low | accept | The limit is a local resource control for one user; a nonsense value is clamped to 1..12 and cannot escalate anything. |
| T-37-SC | Tampering | npm/pip/cargo installs | high | mitigate | No dependency is added; the scheduler stays hand-written (D-07). |
